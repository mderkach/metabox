# metabox frontend rules

Shared repository rules are in the root [`AGENTS.md`](../../AGENTS.md). This file covers only `apps/web/`.

## When to read the guides

A guide is read by the condition from the table, **in full** and before making a change. What each document covers: [`docs/README.md`](./docs/README.md).

| Read in full before you                                          | Document                                                                                                  |
| ---------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| create or change application code in `src`                       | [Architecture&Style.md](./docs/guides/Architecture&Style.md): FSD, Public API, naming, components, styles |
| create or change visual UI, layout, typography, colors or motion | [DESIGN.md](./DESIGN.md): panel design system, alongside the architecture and style guide                 |
| create or change a store, a selector, any state code             | [StateManagement.md](./docs/guides/StateManagement.md)                                                    |
| write a fetch function, a query key, a query hook or a mutation  | [Query.md](./docs/guides/Query.md)                                                                        |
| write a form or a Zod schema                                     | [Form&Validation.md](./docs/guides/Form&Validation.md)                                                    |
| create or change a list, a table, its columns and filtering      | [Tables.md](./docs/guides/Tables.md)                                                                      |
| write or edit tests                                              | [testing/README.md](./docs/guides/testing/README.md): which level, then the guide of that level           |
| write or edit Russian text in an `i18n/ru.json` dictionary       | [Glossary.md](./docs/guides/Glossary.md)                                                                  |
| claim, measure or fix a performance problem                      | [Performance.md](./docs/guides/Performance.md)                                                            |
| hand in a frontend change                                        | [ReviewChecklist.md](./docs/guides/ReviewChecklist.md): go through the checklist                          |

## Changes in `apps/web/`

- `src/shared/ui/**` is the `ui` segment of the `shared` layer. shadcn primitives live in `src/shared/ui/shadcn/` and are generated by the CLI: do not edit or rename them; naming and project rules do not apply to them. The segment's own code lives one level up and follows the project rules, with styling classes in `styles.ts`. The segment is exposed through `src/shared/ui/index.ts`.
- `src/shared/api/generated.ts` is a `tools/schemagen` artifact and is not edited by hand. The same goes for `src/shared/api/daemon.generated.ts`: it is written by the daemon's `cmd/contractgen` and rebuilt with `make schema-daemon`.
- `src/i18n.generated.d.ts` is the i18next namespace map, an artifact of `tools/i18n.ts`. It is rebuilt with `pnpm --filter web gen:i18n`, and automatically by the dev server and the build.
- A new or changed daemon endpoint the panel calls gets a handler in `createMissingHandlers` (`src/test/handlers.ts`, the mock stand) in the same PR; `tools/mockStand.test.js` compares the stand with the routes in `apps/metaboxd/internal/httpapi/httpapi.go` and names a missing one.
- Formatting and lint: `pnpm format`, `pnpm lint`. Do not align style by hand.
- A change visible in the panel is confirmed before the PR by going through its user scenario in a browser on the mock stand: an e2e scenario (`pnpm --filter web test:e2e`, [ADR-0075](../../docs/adr/ADR-0075-run-end-to-end-scenarios-with-playwright-test-on-the-mock-stand-and-the-live-daemon.md)) or by hand through the Playwright MCP. Unit and component tests do not replace it. The PR description lists what was checked in the browser and what was not, such as a live daemon or a narrow screen.
- A change visible in the panel goes through the Impeccable skill (`/impeccable`; its context is [`PRODUCT.md`](./PRODUCT.md) and [`DESIGN.md`](./DESIGN.md), the decision is [ADR-0078](../../docs/adr/ADR-0078-gate-panel-design-with-the-impeccable-detector-a-brief-and-an-independent-critique.md)):
  - The design detector is clean: `pnpm --filter web check:design`, which pre-push and CI run on the sources. An intended exception is recorded with `impeccable ignores` and a `--reason` in `.impeccable/config.json`.
  - A new screen, a new block of a screen or a redesign starts with a design brief (`/impeccable shape`) posted in its issue. The brief says which question of the user the block answers; code starts after the repository owner approves it.
  - A new or changed form, component or interaction is reviewed with `/impeccable critique` by an agent or a person who did not write it, on the mock stand at desktop width and 375 px. The findings go into the PR as a comment; one that is not fixed becomes an issue. The findings decide, the score does not.
- One component per file. A screen or form file holds its own component; its fields, blocks and sections are neighbouring files of the same `ui` segment, named with the slice prefix (`EditorRuleSearch`, `RuleOutboundField`). Helpers with domain knowledge go to `model`, without it to `lib`; a `ui` file does not collect them at its bottom. Markup is not kept in variables to be passed around: a piece of JSX that goes into a slot or repeats is a component rendered in place (`actions={<EditorRuleActions … />}`).
