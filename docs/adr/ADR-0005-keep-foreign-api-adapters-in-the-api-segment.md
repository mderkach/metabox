# ADR-0005. Держать адаптеры чужих API в `api`-сегменте слайса, а не отдельным слоем `src/adapters`

- Статус: Proposed
- Дата: 2026-09-12
- Ответственные: владелец репозитория

## Контекст и постановка проблемы

[PRD, A.2](../PRD.md) задаёт трёхслойную модель конфига: схема форка → адаптер → модель приложения. Экран зависит от модели приложения, поэтому ломающее изменение схемы форка не доходит до экранов. Требование это не отменяется — вопрос только в том, где живёт средний слой.

Гайд [Architecture&Style](../../apps/web/docs/guides/Architecture%26Style.md) до этого решения обещал каталог `src/adapters/` вне слоёв FSD: «при ломающем изменении API форка правится только он». Алиас `@adapters` объявлен в `vite.config.ts`, `tsconfig.json`, `tsconfig.app.json`, `tsconfig.mocks.json` и в списке слоёв линтера границ `tools/fsdBoundaries.js`.

Фактически за шесть экранов каталог не появился, а адаптация чужих форматов разошлась по `api`-сегментам слайсов:

- `entities/Connection/api/Connection.dto.ts` — формы ответов Clash API `/connections`;
- `entities/Proxy/api/Proxy.dto.ts` — `/proxies` и `/providers/proxies`;
- `entities/Daemon/api/Daemon.dto.ts` — `/version`, `/configs`, `/traffic`, `/memory` и состояние сервиса;
- `entities/*/model/*.mapper.ts` — перевод DTO в модель экрана (`toConnectionRow`, `toProxyGroups`, `toRuleRows`).

Владелец репозитория назвал это правилом по ходу работ: «адаптеры в апи слое должны лежать, а не отдельной папкой». Расхождение записано в [TechDebt](../TechDebt.md) и до сих пор не закрыто: правило действует, а гайд, PRD и пять конфигов говорят обратное.

В scope: где размещается код, переводящий чужой формат в модель приложения, и что делать с алиасом `@adapters`. Вне scope: сама трёхслойная модель из A.2 и способ получения схемы (ADR-0001) — они не меняются.

## Критерии выбора

1. **Требование A.2 выполняется**: экран не зависит от формы чужого API, изменение формата правится в одном месте.
2. **Границы проверяются линтером**, а не ревью: размещение кода — это правило, у которого должна быть машинная проверка.
3. **Высокая связность** (GRASP): код одной предметной области лежит рядом, а не разнесён по двум деревьям.
4. **Стоимость сопровождения**: сколько мест нужно править при добавлении слайса и при подъёме версии форка.
5. **Соответствие FSD**: методология описывает семь слоёв, каталог вне слоёв требует собственных правил обхода.

## Рассмотренные варианты

1. **Адаптер — часть своего слайса.** Форма чужого API и перевод в модель лежат в том слайсе, который с этим API работает: `entities/Connection/api/Connection.schema.ts`, `entities/Connection/model/Connection.adapter.ts`. Наружу уходит только модель — через `index.ts` слайса. Преимущества: критерий 1 выполняется тем же способом, что и раньше (наружу видна модель, не DTO), а границы проверяет существующий `fsd/boundaries` без единого нового правила (критерий 2); домен не разорван (критерий 3); новый слайс не требует правок в конфигах (критерий 4); слоёв ровно столько, сколько в методологии (критерий 5). Недостатки: адаптеры разных API больше не лежат в одном каталоге — «где вообще адаптеры» отвечает не структура, а сегмент слайса; при ломающем изменении схемы форка править придётся несколько слайсов, а не один каталог. **Принят.**

2. **Вернуть каталог `src/adapters/`.** Преимущества: буквальное соответствие прежнему тексту гайда; все адаптеры видны в одном месте. Недостатки: каталог вне слоёв нужно описать в линтере границ отдельным набором правил — кто его видит, кого видит он, применимо ли к нему Public API (критерий 2); DTO Clash API уезжает из слайса, который единственный им пользуется, — связность падает (критерий 3); на практике за шесть экранов каталог так и не понадобился, то есть решение вводит структуру под будущее, которого может не быть (критерий 4).

3. **Оставить как есть, правило — только в TechDebt.** Преимущества: нулевая стоимость сегодня. Недостатки: гайд, PRD и пять конфигов продолжают описывать несуществующий каталог, а правило не проверяется ничем — следующий исполнитель заведёт `src/adapters/`, потому что так написано в гайде. Это и есть текущее состояние, признанное долгом. **Отклонён.**

### Форма адаптера

Отдельно рассмотрено, чем именно переводить форму в модель.

1. **Чистая схема плюс рукописный адаптер.** Схема остаётся `ZodObject` и композируется через `.extend()` и `.omit()`; над одной схемой живёт сколько угодно адаптеров, в том числе обратный. **Принят.**
2. **`.transform()` внутри схемы.** Один артефакт вместо двух, но схема превращается в `ZodPipe`: пропадают `.extend()`, `.omit()`, `.pick()`, обратного направления нет, а одна схема начинает обслуживать ровно один экран. Отклонён.
3. **`z.codec()` с `decode`/`encode`.** Двусторонний механизм самой библиотеки, но кодек так же pipe-подобен и лишает композиции; `.catch()` в нём действует только на декодировании, поэтому деградация в обратную сторону теряется молча; у нормализации по ADR-0007 честного обратного направления нет вовсе — незнакомое происхождение схлопывается в `unknown`, и `encode` пришлось бы выдумывать. Отклонён.

## Принятое решение

Отдельного слоя `src/adapters/` в `apps/web` нет. Код, переводящий чужой формат в модель приложения, размещается так:

- **Форма чужого API описывается схемой** — файл `<Slice>.schema.ts` в сегменте `api` того слайса, который с этим API работает. Схема описывает то, что пришло по проводу, и ничего не переводит: `.transform()` внутри неё запрещён, иначе `ZodObject` становится `ZodPipe` и теряет `.extend()`, `.omit()`, `.pick()`, а `z.toJSONSchema()` на выходной стороне перестаёт быть представимым. Наружу схема не экспортируется: за пределы слайса уходит модель.
- **Исключения для «формата, который и есть модель экрана» больше нет.** Прежняя редакция разрешала слайсу `Daemon` отдавать форму ответа наружу как модель. Решение отзывается: форма и модель различаются не объёмом перевода, а тем, кто ими владеет, и совпадение полей сегодня не обязывает экран зависеть от чужого формата завтра.
- **Перевод и отказ** — файл `<Slice>.adapter.ts` в сегменте `model` того же слайса. Там же решается, чем становится непонятый ответ: отказом вида `Schema` (`shared/api/ApiError.ts`), когда без данных экран бессмыслен, или частичной моделью с видимым признаком деградации, когда показывать есть что. Молчаливый фолбэк запрещён: «данных нет» и «ответ не разобран» — разные вещи.
- **Разбор идёт до кэша**, в фабрике опций запроса, а не в `select`: `select` меняет то, что видит хук, но не то, что лежит в кэше, и чужая форма осталась бы доступна всякому, кто возьмёт данные по ключу. `fetch`-функция по-прежнему ничего не преобразует и отдаёт ответ как есть.
- **Схема конфига форка** остаётся сгенерированной в `shared/api/generated.ts` (ADR-0001), а её адаптация к экрану — в `entities/Config` и `entities/Rule`.
- **Алиас `@adapters` удаляется** из `vite.config.ts`, `tsconfig.json`, `tsconfig.app.json`, `tsconfig.mocks.json` и из списка слоёв `tools/fsdBoundaries.js`.

Требование A.2 продолжает выполняться: экран импортирует модель слайса, а не форму источника, и ломающее изменение чужого формата останавливается на границе слайса.

### Область действия и границы

Решение распространяется на `apps/web/src`. Демона, генератора схемы и контракта API не касается. Трёхслойная модель конфига (PRD, A.2) и способ генерации схемы (ADR-0001) не меняются.

## Последствия

### Положительные

- Правило совпадает с фактическим кодом, и его проверяет существующий линтер границ: DTO за пределы слайса не уедет, потому что его нет в Public API.
- Слайс остаётся единицей переноса: домен целиком лежит в одной папке вместе со своими тестами и моками.
- Пять конфигов перестают описывать каталог, которого нет.

### Отрицательные

- Ломающее изменение схемы форка правится в нескольких слайсах, а не в одном каталоге. Смягчается тем, что схема генерируется и её потребители известны из типов.
- Ответ на вопрос «где адаптеры» даёт соглашение об именах, а не структура каталогов. Соглашение записано в гайде и проверяется на ревью.

### Нейтральные или отложенные

- Фикстуры golden round-trip, которые гайд по тестированию помещал в `src/adapters/__tests__/fixtures/`, переезжают в `entities/Config/__tests__/`; сам корпус конфигов пока не собран — это отдельный пункт долга.

## Риски и меры снижения

| Риск                                                       | Вероятность и влияние    | Митигация                                                                                                                 |
| ---------------------------------------------------------- | ------------------------ | ------------------------------------------------------------------------------------------------------------------------- |
| Форма чужого API просочится в компонент экрана             | Средняя, среднее влияние | Схема не перечислена в `index.ts` слайса, а Public API собирается поимённо; импорт в обход барреля ловит `fsd/boundaries` |
| Адаптация одного формата расползётся по нескольким слайсам | Низкая, среднее влияние  | Формат принадлежит слайсу-владельцу; соседний слайс получает готовую модель через `@x`, а не разбирает DTO сам            |
| Подъём версии форка потребует обхода нескольких слайсов    | Средняя, низкое влияние  | Схема генерируется, ломающее изменение проявляется ошибкой типов в местах использования — обход даёт компилятор           |

## Совместимость, миграция и откат

Миграция не требуется: код уже размещён так, как фиксирует решение. Правятся только документы и конфиги — удаление алиаса `@adapters`, которым ничего не импортируется.

Откат: вернуть алиас в пять конфигов и завести каталог с собственными правилами границ. Стоимость отката — те же пять строк плюс правило в линтере.
