# ADR-0030. Состав сборки читать у бинаря, а какой тип закрыт тегом — из исходников форка

- Статус: Accepted
- Дата: 2026-09-23
- Ответственные: владелец репозитория

## Контекст и постановка проблемы

AC-47: тип узла, которого нет в сборке sing-box на устройстве, панель показывает с предупреждением. Собрать такой конфиг она не мешает, но называет последствие — бинарь откажется стартовать. Состав сборки берётся у самого бинаря, а не зашивается в панель списком.

Факты, проверенные по исходникам форка `v1.14.0-extended-2.7.1`:

- `sing-box version` печатает строку `Tags: with_quic,with_utls,...` с build-тегами бинаря. Для сборки без тегов этой строки нет (`cmd/sing-box/cmd_version.go`).
- Бинарь на BPI-R4 Pro собран без `with_ccm`, `with_ocm`, `with_cloudflared`, `with_naive_outbound`, `with_usbip`, `with_openvpn` и `with_openconnect` — замер `sing-box version` 2026-09-23. Набор тегов форка по умолчанию (`release/DEFAULT_BUILD_TAGS`) их включает, поэтому по нему судить о бинаре нельзя.
- Реестр типов отличить не помогает: при отсутствии тега файл `include/<x>_stub.go` регистрирует тот же тип с теми же опциями. Отличается он только ошибкой при запуске — «QUIC is not included in this build» (`docs/TechDebt.md`, «Схема шире возможностей бинаря»).
- Какой тег закрывает какой тип, видно только в исходниках `include/`. Файл под условием `//go:build with_x` или `!with_x` регистрирует типы прямо — `inbound.Register[...](registry, C.TypeHysteria, ...)` — или через функцию пакета протокола: `warp.RegisterEndpoint(registry)`.
- Генератор схемы уже читает исходники форка через `go/parser`: пакет `constant` и описания полей.

## Критерии выбора

1. Какие теги у бинаря — отвечает сам бинарь на устройстве.
2. Какой тег закрывает какой тип — выводится из форка, а не пишется руками, и обновляется вместе со схемой.
3. Неизвестный состав сборки не превращается в ложные предупреждения.
4. Без новых зависимостей в демоне и панели.

## Рассмотренные варианты

1. **Теги — у бинаря через `sing-box version`, таблица «тип → тег» — генератором схемы из `include/` форка.**
   - Демон один раз при старте читает теги вместе с версией.
   - Генератор печатает `BUILD_TAG_OF_TYPE` в `generated.ts`.
   - Отвечает всем критериям.
   - **Принят.**
2. **Проверять каждый тип вопросом к бинарю — пробный `sing-box check` на минимальном конфиге.** Точно по определению: заглушка отвечает ошибкой из конструктора, и `check` её ловит. Но это десятки запусков процесса на роутере при каждом старте демона ради того, что видно из одной строки `sing-box version`. **Отклонён.**
3. **Таблица «тип → тег» руками в панели.** Разъедется с форком на первой же пересборке — это прямо запрещает TechDebt. **Отклонён.**

## Принятое решение

- `singbox.Client.Build` читает версию и теги (`apps/metaboxd/internal/singbox/singbox.go`).
- `GET /api/status` отдаёт `singbox_build.tags`:
  - нет поля — бинарь не прочитан;
  - пустой список — сборка без тегов.
- `tools/schemagen/gates.go` строит таблицу «реестр → тип → тег»:
  - обходит `include/*.go` и берёт тег `with_*` из условия сборки;
  - учитывает прямые регистрации и один шаг в функцию пакета протокола — читается только вызванная функция, соседние регистрируют типы без тега;
  - типы, которых нет в схеме, в таблицу не попадают.
- Платформенная часть условия (`linux || windows` у usbip) не учитывается: панель управляет роутером на Linux.
- Панель: `findUnbuiltNodes` проходит секции `inbounds`, `outbounds`, `endpoints`, `providers`, `services`, `certificate_providers`, `dns.servers`. `ConfigBuildNotice` над содержимым раздела конфигурации называет узлы и последствие. При непрочитанном бинаре блока нет.

## Последствия

### Положительные

- Предупреждение следует за бинарём на устройстве: пересобранный с `with_ccm` форк снимет его без правки панели.
- Таблица меняется вместе со схемой и попадает в дифф `generated.ts`.

### Отрицательные

- Разбор `include/` опирается на соглашения форка: условие сборки с одним тегом `with_*`, регистрация прямым вызовом или через функцию пакета. Если форк сменит приём, таблица станет неполной. Ловит это `TestBuildGates`, а полноту списка — нет.
- Теги читаются один раз при старте демона: бинарь, заменённый под работающим демоном, попадёт в панель после его перезапуска.
- Предупреждение стоит только в разделе конфигурации. Бар применения его не повторяет, остановит применение `sing-box check`.

### Нейтральные или отложенные

- Помечать тип в выборе типа при создании узла — когда появятся формы создания узлов, сейчас их нет.

## Совместимость, миграция и откат

Поле `singbox_build` необязательное: панель без него предупреждения не показывает. Откат — убрать `emitGates` из генератора и `ConfigBuildNotice` из раскладки раздела.

## Проверка решения

- `go test ./internal/singbox ./internal/httpapi`:
  - теги разбираются;
  - сборка без тегов даёт пустой список, а не `null`;
  - непрочитанный бинарь не отдаёт поля.
- `make test-schemagen`, `TestBuildGates`:
  - прямая регистрация;
  - регистрация через пакет протокола (`warp`);
  - условие с платформенной частью;
  - тип, который соседняя функция пакета регистрирует без тега (входящий `naive`).
- `pnpm --filter web exec vitest run Config.build ConfigBuildNotice`.
