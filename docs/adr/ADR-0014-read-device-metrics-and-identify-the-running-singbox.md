# ADR-0014. Читать показания устройства из procfs и опознавать sing-box по слушателю Clash API

- Статус: Accepted
- Дата: 2026-09-13
- Ответственные: владелец репозитория

## Контекст и постановка проблемы

Панель показывала рантайм только тем, что отдаёт Clash API: скорость, память кучи sing-box, соединения. Всё, что рядом — загружен ли процессор роутера, греется ли плата, сколько памяти осталось, сколько канала вообще проходит мимо прокси, — оставалось за SSH.

Второй разрыв был виднее. На целевом BPI-R4 Pro маршрутизацией владеет пакет re:HomeProxy: он поднимает `/usr/bin/sing-box` своей службой против `/var/run/homeproxy/proxy.json`. Демон же спрашивает состояние у procd про `/etc/init.d/sing-box` — службу пакета sing-box, отключённую 2026-09-11. Результат на живом устройстве: экран показывал сотню активных соединений и идущий трафик и рядом надпись «sing-box остановлен» с кнопкой «Запустить», которая подняла бы вторую копию процесса поверх работающей.

Ограничения заданы раньше: `go.mod` демона без зависимостей ([Архитектура и стайлгайд](../../apps/metaboxd/docs/guides/Architecture&Style.md)), бюджет NFR-4 (RSS ≤ 64 МБ, CPU в простое ≤ 1% ядра), управление службой только через init-скрипт (PRD, Constraints).

В scope: откуда демон берёт показания устройства, как опознаёт работающий sing-box и что из этого попадает в контракт. Вне scope: хранение истории этих показаний и графики глубже минуты — они остаются в roadmap после v1.

## Критерии выбора

1. **Без новых зависимостей в демоне.** Каждая из них едет в единственный артефакт поставки.
2. **Честность показаний.** Панель не выдаёт остановленную службу за работающий рантайм и наоборот.
3. **Цена в простое.** Опрос идёт, только пока панель открыта, и укладывается в NFR-4.
4. **Проверяемость.** Чтение устройства должно тестироваться без живого роутера.
5. **Деградация по частям.** Плата без термозоны, устройство без маршрута по умолчанию и остановленный sing-box не должны гасить остальные показания.

## Рассмотренные варианты

### Источник показаний

1. **Внешний агент (collectd, netdata) и запрос к нему.** Преимущества: метрик много, считать их не нужно. Недостатки: пакет, которого на устройстве может не быть, и вторая точка отказа; цена по памяти сравнима с самим демоном (критерии 1, 3). **Отклонён.**

2. **`ubus` и вызовы `system info`.** Преимущества: родной для OpenWrt путь, уже используется для состояния службы. Недостатки: запуск внешнего процесса каждые несколько секунд там, где хватает чтения четырёх файлов (критерий 3); набор полей задан не нами и разнится между сборками. **Отклонён.**

3. **Чтение procfs и sysfs напрямую.** Преимущества: стандартная библиотека, корни файловых систем подменяются в тестах фейковым деревом (критерии 1, 4); чтение дешёвое. Недостатки: формат файлов ядра разбирается руками, и различия между платами ловятся только на устройстве. **Принят.**

### Опознание процесса sing-box

1. **Верить procd.** Преимущества: ничего не делать. Недостатки: ровно тот отказ, ради которого решение и принимается (критерий 2). **Отклонён.**

2. **Искать процесс по имени бинаря.** Преимущества: одно чтение `comm` на процесс. Недостатки: на устройстве может быть несколько sing-box — например, отключённая служба пакета и работающий homeproxy, — и выбор между ними был бы произвольным (критерий 2). **Отклонён.**

3. **Искать процесс, который слушает порт Clash API.** Преимущества: это ровно тот процесс, чьи данные показывает панель, — никакой другой ею и не рисуется (критерий 2). Недостатки: связь «сокет — процесс» в procfs выражена только ссылками в `fd`, поэтому поиск обходит дескрипторы всех процессов. **Принят**, обход выполняется один раз и кэшируется по pid.

## Принятое решение

Пакет `internal/device` читает `/proc/loadavg`, `/proc/meminfo`, `/proc/uptime`, `/proc/net/dev`, `/proc/net/route`, `/proc/<pid>/status` и `/sys/class/thermal/*`. Корни `proc` и `sys` — поля `Options`, поэтому тесты идут по дереву в `t.TempDir()`, а не по живой системе.

Показания уходят панели топиком `system` того же потока `GET /api/events` (ADR-0010) с шагом в две секунды. Поток поднимается только при наличии читателя, поэтому в простое опроса нет.

Процесс sing-box ищется по слушателю порта Clash API: порт берётся из применённого конфига, inode слушающего сокета — из `/proc/net/tcp` и `/proc/net/tcp6`, владелец inode — обходом `/proc/*/fd`. Найденный pid запоминается; перед каждым следующим чтением он сверяется по `comm`, потому что освободившийся pid система выдаёт заново.

Тот же поиск отвечает на вопрос «жив ли рантайм»: `contract.Service` получил поле `managed`. Статус `running` при `managed: false` означает, что sing-box работает, но поднят не службой демона. Панель в этом случае показывает службу работающей и убирает кнопки управления — они относятся к другому процессу.

Интерфейс наружу выбирается по маршруту по умолчанию с наименьшей метрикой, при этом туннели пропускаются: в режиме TUN маршрут по умолчанию принадлежит самому sing-box, и его трафик оказался бы одновременно делимым и делителем. Туннель отличается по файлу `tun_flags`, который ядро заводит только TUN/TAP-устройствам.

Доля канала через sing-box считается по приращениям за одно окно, а не по накопленным счётчикам: счётчик интерфейса идёт с подъёма линка, счётчик Clash API — с запуска процесса, и деление одного на другое дало бы число, не значащее ничего. Приращения копит демон: счётчик канала он читает сам, счётчик sing-box получает со снимком соединений. Клиентское накопление отвергнуто — окно наблюдения обнулялось бы перезагрузкой страницы, а секундное отношение прыгает от каждого всплеска (так же устроен и b4: он отдаёт готовое отношение `targeted_connections` к `total_connections`, а живые значения показывает отдельно).

## Последствия

**Хорошо:** показания устройства не требуют SSH; панель перестала называть работающий рантайм остановленным; опасная кнопка «Запустить» исчезла там, где процессом владеет чужая служба; чтение проверяется тестами без роутера.

**Плохо:** формат файлов ядра разбирается руками, и плата с другим составом `meminfo` или термозон обнаружится только на устройстве. Обход `/proc/*/fd` — самая дорогая часть опроса; он выполняется при первом поиске и после гибели процесса, но на устройстве с тысячами процессов это заметная разовая работа.

**Открытое:** возраст чужого процесса не показывается — его знает `/proc/<pid>/stat`, но поле контракта `uptime` описано как возраст службы, и смешивать два разных возраста в одном поле нельзя. Доля канала считается по интерфейсу целиком: трафик LAN-LAN в неё не попадает, а инкапсуляция прокси делает долю чуть выше честной.

## Проверка решения

На BPI-R4 Pro 2026-09-13, демон с ветки против `/etc/homeproxy/proxy.json`: `GET /api/service` вернул `{"status":"running","managed":false}` при отключённой службе пакета; топик `system` отдал загрузку 0.01 при четырёх ядрах, температуру 42.8 °C, 355 МБ занятой памяти из 7.8 ГБ, канал `pppoe-wan` 93.6 кБ/с, долю через sing-box 37%, RSS процесса 82.3 МБ при pid 5872 (Clash API в тот же момент отдавал 45.8 МБ: он считает только память рантайма Go, без резидентного кода бинаря), RSS демона 14.2 МБ и 23 горутины. Тесты `internal/device` проходят на фейковом дереве procfs, включая подмену pid чужим процессом и маршрут по умолчанию через туннель.
