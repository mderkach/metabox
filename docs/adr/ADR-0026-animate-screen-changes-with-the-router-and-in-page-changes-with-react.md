# ADR-0026. Анимировать смену экрана средствами роутера, а изменения внутри экрана — границей `ViewTransition` React

- Статус: Accepted
- Дата: 2026-09-19
- Ответственные: владелец репозитория

## Контекст и постановка проблемы

До этого решения панель меняла экраны и показывала панели мгновенно: строка правила открывала панель правки скачком, бар применения появлялся без перехода, экран сменялся другим за один кадр. Требований к анимации в PRD нет. Ближайшее к ним — UX-7: состояние системы всегда на виду. Бар применения и панели и есть это состояние в ответ на действие, а скачок разметки не показывает, что появилось и откуда, — глаз ищет изменение заново.

Браузерный API View Transitions (`document.startViewTransition`) в панели доступен двумя путями, и оба уже есть в зависимостях:

- React 19.3 даёт границу `<ViewTransition>`, которая анимирует появление, исчезновение и изменение поддерева, но только для обновлений, помеченных как Transition: `startTransition`, `useDeferredValue`, раскрытие `Suspense`. Рядом с ней `<Activity>` прячет поддерево, сохраняя его состояние.
- TanStack Router даёт `defaultViewTransition`: оборачивает коммит маршрута в `document.startViewTransition` и умеет передавать в CSS типы перехода.

Ограничение, заданное библиотеками: компоненты роутера подписаны на его состояние через `useSyncExternalStore`, а такие обновления React рендерит синхронно, вне Transition, даже когда сам роутер оборачивает их в `startTransition`. Проверено в браузере 2026-09-19 на подменённом `document.startViewTransition`: граница `<ViewTransition>` вокруг `Outlet` за две навигации не вызвала его ни разу. Граница вокруг панели правила при этом сработала на открытие и на закрытие.

Оба механизма зовут один и тот же `document.startViewTransition`, и новый вызов прерывает предыдущий. Решение должно назначить каждому виду изменения ровно один механизм.

В scope: смена экрана по адресу; появление и исчезновение панелей, бара применения, вкладок; что при переходе стоит на месте, а что движется; поведение при системной настройке «без анимации». Вне scope: анимации графиков и морфы общих элементов между экранами — пар таких элементов в панели пока нет.

## Критерии выбора

1. **Переход срабатывает.** Смена экрана и панели анимируются в Chromium и Safari; проверяется инструментом, а не глазами.
2. **Один вызов на изменение.** Механизмы не запускают `document.startViewTransition` одновременно для одного и того же изменения.
3. **Оболочка не мигает.** Сайдбар и бар применения при смене экрана не растворяются и остаются кликабельными.
4. **Состояние скрытого сохраняется.** Прокрутка, фильтры и фокус вкладки переживают переключение.
5. **Уважается настройка системы.** При `prefers-reduced-motion: reduce` движения нет.
6. **Без новых зависимостей** и с деградацией до мгновенной смены там, где браузер API не даёт.

## Рассмотренные варианты

1. **Смена экрана — роутером, изменения внутри экрана — границей React.** Роутер получает `defaultViewTransition` с функцией типов: по порядку пунктов меню она отдаёт `page-forward`, `page-backward` или `page-fade`, CSS читает их через `:active-view-transition-type()`. Экран, его шапка и полоса вкладок конфига именуются `view-transition-name`; корень остаётся живым. Панели, бар и вкладки оборачиваются `<ViewTransition>`, а их состояние меняется в `startTransition` или через `useDeferredValue`; вкладки с состоянием стоят под `<Activity>`. Преимущества: срабатывает на всех навигациях (критерий 1); механизмы разведены по видам изменений и не пересекаются (2); корень живой, оболочка не мигает (3); `Activity` держит состояние (4); одно правило CSS снимает движение (5); зависимостей нет (6). Недостатки: именованные элементы во время перехода не получают кликов — ограничение спецификации; направление перехода связывает роутер с порядком меню сайдбара; в браузерах без типов переходов экран сменяется мгновенно. **Принят.**

2. **Граница `<ViewTransition>` вокруг `Outlet`.** Одна строка в оболочке, одинаковый механизм для всего. Недостатки: не срабатывает на навигации из-за синхронного рендера подписки роутера (критерий 1) — проверено в браузере; сработала бы только на раскрытии `Suspense`, которого при предзагрузке чанка и словарей маршрута не бывает. **Отклонён.**

3. **Всё через роутер и ручной `document.startViewTransition`.** Панели и бар анимировать своим вызовом API вокруг `setState` с `flushSync`. Недостатки: React запрещает звать `startViewTransition` рядом со своими границами — вызовы перебивают друг друга (критерий 2); теряются семантика enter и exit по факту монтирования и связь с `Activity` (4); появляется свой планировщик анимаций рядом с двумя готовыми. **Отклонён.**

4. **CSS без View Transitions: `@starting-style`, keyframes на монтирование, классы `tw-animate-css`.** Преимущества: никакого JS. Недостатки: исчезновение элемента не анимируется, пока его не задержать в DOM руками; смена экрана не анимируется вовсе — старого экрана в DOM уже нет (критерий 1). **Отклонён.**

5. **Библиотека анимаций (`motion`).** Преимущества: готовые `AnimatePresence` и layout-анимации. Недостатки: новая зависимость на десятки килобайт ради того, что браузер и React уже умеют (критерий 6); смену экрана всё равно пришлось бы вязать к роутеру отдельно. **Отклонён.**

6. **Оставить без анимации.** Ноль кода и рисков. Недостатки: скачки разметки при открытии панелей и смене экрана остаются, связь действия с результатом читается хуже. **Отклонён.**

## Принятое решение

Смена экрана анимируется роутером, изменения внутри экрана — React. Правила:

- **Роутер.** `createRouter` получает `defaultViewTransition: { types: toPageTransitionTypes }` (`apps/web/src/app/router/Router.transition.ts`). Тип считается по порядку адресов меню `NAV_TARGETS` через `pickActiveNav`: движение вниз по меню — `page-forward`, вверх — `page-backward`, пути вне меню — `page-fade`. Переход внутри раздела — когда у адресов общий первый сегмент — получает `page-hold`: оболочку там держит раскладка, и она стоит, а сдвиг содержимого под неподвижной шапкой читался бы рывком; направление показывает сама полоса вкладок: текущая вкладка подчёркнута штатно, без анимации переезда. Два из трёх адресов раздела при этом стоят в меню соседними пунктами, и подсветка сайдбара между ними перескакивает — это цена решения, а не недосмотр. Первый заход и смена одних параметров адреса перехода не получают. Границу `<ViewTransition>` вокруг `Outlet` не ставить.
- **Именованные группы.** `view-transition-name` носят `<main>` оболочки (`page`), шапка экрана `PageHeader` (`page-header`), и полоса вкладок конфига (`config-tabs`). Корень живой: старый снимок корня скрыт, новый не анимируется. Вне перехода роутера — при анимациях React — именованные группы стоят живыми без снимка и растворения; анимируются они только под `:active-view-transition-type()` роутера. Новое имя добавляется в обе ветки правил `index.css`: в общую, где группа стоит живой, и под `:active-view-transition-type()`, где она анимируется.
- **Оболочка раздела.** Группа перехода собирается по имени, а не по тому, перемонтировался ли носитель. Шапка и полоса вкладок раздела конфигурации живут в маршруте-раскладке и переход между вкладками переживают, но снимков у них по-прежнему два. Отличает эти случаи тип перехода, а не `:only-child`: под `page-hold` оболочка стоит живой, меняется только содержимое. У шапки пара снимков есть при любой навигации — она стоит на каждом экране, — поэтому `:only-child` ей не подходит вовсе; за полосой вкладок ветка остаётся: с парой она стоит, без пары уходит вместе с содержимым.
- **React.** Появление и исчезновение внутри экрана — граница `<ViewTransition>` с классами `enter`/`exit`, а изменение состояния — в `startTransition` либо через `useDeferredValue`. Граница вокруг живо обновляемого содержимого получает `default='none'`, иначе каждое обновление строк анимируется. `document.startViewTransition` руками не вызывается.
- **Бар применения — CSS, а не граница.** Бар стоит над `<main>`, а `<main>` — именованная группа `page`: вне перехода роутера она стоит без анимации, и граница вокруг бара анимировала бы только его, пока экран под ним прыгает на высоту бара. Поэтому бар смонтирован всегда, а его высоту анимирует переход `grid-template-rows` от `0fr` к `1fr` на тех же переменных длительности; при «без анимации» переход снят.
- **Вкладки с состоянием.** Панель вкладки остаётся в DOM (`keepMounted`) под `<Activity>`, граница `<ViewTransition>` стоит сразу под `Activity`, до первого DOM-узла.
- **Движение.** Длительности и кривые заданы переменными `--view-transition-*` в `apps/web/src/app/styles/index.css`, keyframes лежат там же; отдельных `.css` файлов и inline-стилей анимации нет. Правило `prefers-reduced-motion: reduce` обнуляет длительность и задержку всех псевдоэлементов перехода. Слой перехода не ловит указатель.

Non-goals: морфы общих элементов между экранами, анимация раскрытия `Suspense` и перестановки строк списков — данные приходят через Query, а списки виртуализованы.

### Область действия и границы

`apps/web/src/app/router/`, `apps/web/src/app/ui/AppLayout.tsx`, `apps/web/src/app/ui/ConfigLayout.tsx`, `apps/web/src/app/styles/index.css`, `widgets/PageHeader`, `widgets/Config/ConfigTabs`, `widgets/AppSidebar` (порядок меню), экраны и фичи с границами `<ViewTransition>`.

## Последствия

### Положительные

- Смена экрана, открытие панелей, появление бара и переключение вкладок анимируются, и у каждого изменения один механизм.
- Направление перехода повторяет движение по меню: экран уходит туда же, куда сместился пункт.
- Оболочка не мигает и не блокируется на время перехода.
- Скрытая вкладка соединений сохраняет прокрутку, фильтры колонок и фокус.

### Отрицательные

- Именованные элементы — экран, шапка, полоса вкладок — не получают кликов, пока идёт переход: до 260 мс после смены экрана и до 140 мс после открытия панели. Ограничение спецификации, CSS его не снимает.
- Обе вкладки соединений смонтированы одновременно: поиск, срезы и подвал лежат в DOM дважды, а таблица закрытых соединений живёт в памяти, пока открыта активная.
- Роутер зависит от порядка пунктов меню: приложение импортирует `NAV_TARGETS` из виджета сайдбара.
- В браузерах без `:active-view-transition-type()` экран сменяется мгновенно: роутер передаёт переход без типов, и именованные группы остаются закреплёнными.
- Анимации проверяются инструментом — подменой `document.startViewTransition` и `document.getAnimations()`, — а не юнит-тестами: в jsdom API нет.

### Нейтральные или отложенные

- Общие элементы между экранами (морф строки в панель, узла соединения в узел конфига) появятся отдельным решением, когда для них будет пара.
- Растворение при раскрытии данных возможно только после перехода Query на `Suspense` — за рамками этого решения.

## Совместимость, миграция и откат

Данных и контрактов решение не касается. Откат — снять `defaultViewTransition` у роутера, классы `[view-transition-name:…]` у четырёх элементов и блок View Transitions в `index.css`; границы `<ViewTransition>` и `<Activity>` при этом продолжают работать независимо, их можно снимать по одной.

## Проверка решения

- `pnpm --filter web exec vitest run Router.transition` — направление по меню, растворение для адресов одного пункта и путей вне меню, отсутствие перехода на первом заходе и при смене параметров.
- Браузер с подменённым `document.startViewTransition`: одна навигация по сайдбару даёт ровно один вызов с типом `page-forward` или `page-backward`; `document.getAnimations()` после `ready` содержит `page-out` и `page-in` на `::view-transition-old(page)` и `::view-transition-new(page)`, `fade-out` и `fade-in` на шапке.
- Открытие панели правила на экране конфигурации и переключение вкладок соединений дают вызов без типов, в котором группы `page` и `page-header` имеют нулевую длительность.
- Эмуляция `prefers-reduced-motion: reduce`: длительности всех `::view-transition-*` равны нулю.
- `pnpm lint` — правила Tailwind принимают классы `[view-transition-name:…]`.
