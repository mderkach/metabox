# ADR-0039. Separate the interface from the fork schema with an adapter layer and do not lose what is unrecognized in the config

- Status: Accepted. The decision was made on 2026-08-30 in section A.2 of [`../PRD.md`](../PRD.md) and moved here without changes in substance
- Date: 2026-08-30
- Deciders: repository owner
- Supersedes: section A.2 of [`../PRD.md`](../PRD.md)

## Context and problem statement

The owner named full GUI coverage of the config a higher priority than speed to release (interview `metabox-di-001`, Round 4). The fork schema is large and changes with every release ([ADR-0038](./ADR-0038-target-the-sing-box-extended-fork-schema-only.md)): hand-written forms for the whole schema go stale on every release, and a form written against someone else's format breaks together with it.

The other side is who owns the config. The config on the router may be written by hand or by another tool, and the panel has to open it (Round 1: "the config may be generated by hand, the UI must parse it; adapters and highlighting of invalid rules are needed").

In scope: the layers between the fork schema and the screen, and the rule for handling a foreign config. Out of scope: the way the schema is obtained ([ADR-0001](./ADR-0001-generate-schema-from-fork-registries.md)), the apply protocol ([ADR-0002](./ADR-0002-apply-protocol-and-config-ownership.md)), the rules for manual JSON editing ([ADR-0043](./ADR-0043-treat-manual-json-as-a-feature-and-split-save-from-apply.md)).

## Decision drivers

- Full coverage of the schema by the interface (AC-5).
- A breaking change in the fork schema is fixed in one place and does not reach the screens.
- Proper UX where it matters, not only a generated form.
- A foreign config opens and does not lose what the model does not know (AC-1…AC-3).

## Considered options

The form source options come from Round 5 of the interview (option 1 is hand-written forms, option 2 is generation), the ownership options come from Round 1.

1. **Hand-written forms for the whole schema.** The best UX, but the forms go stale on every fork release, and the volume is several times larger than the product core (risk R-3). **Rejected.**
2. **Only forms generated from the schema.** Coverage by default, but without an adapter the screen depends on the shape of the schema, and in priority scenarios the UX is worse than hand-written. **Rejected.**
3. **Generation, hand-written forms on top of it, and an adapter layer between the schema and the UI**: the Round 5 answer, "in fact 1 + 2 + adapters". **Chosen.**

Config ownership:

1. **The config belongs entirely to metabox**: the panel generates it and does not accept a foreign one. This contradicts the scenario where a config already exists on the router. **Rejected.**
2. **The config belongs to the user, the panel only displays it.** This removes generation and apply from the panel. **Rejected.**
3. **Hybrid**: the Round 1 answer. **Chosen.**

## Decision outcome

The config model has three layers:

```text
┌─────────────────────────────────────────────────────────┐
│ UI Layer                                                │
│  hand-written forms (type checklist) + auto-generated   │
│  fallback renderer for uncovered schema nodes           │
└────────────────────────┬────────────────────────────────┘
                         │  metabox internal model
┌────────────────────────┴────────────────────────────────┐
│ Adapter Layer (versioned)                               │
│  mapping "fork schema ↔ metabox model"                  │
│  on a breaking API change ONLY this layer is edited     │
└────────────────────────┬────────────────────────────────┘
                         │  types + validators
┌────────────────────────┴────────────────────────────────┐
│ Schema Layer                                            │
│  generated from sing-box-extended, updated              │
│  mechanically on a fork release                         │
└─────────────────────────────────────────────────────────┘
```

The adapter layer isolates the UI from schema changes, generation gives coverage by default, and hand-written forms give proper UX where it matters.

**Config ownership is hybrid.** metabox owns the config and generates it, but has to parse an arbitrary `config.json`. Constructs the model did not recognize are not lost: they are preserved and highlighted in the UI as unrecognized or invalid.

### Scope and boundaries

Where the layers live in the code:

- **Schema Layer**: the `tools/schemagen` generator and its artifact `apps/web/src/shared/api/generated.ts` ([ADR-0001](./ADR-0001-generate-schema-from-fork-registries.md), strict schemas: [ADR-0018](./ADR-0018-generate-strict-schemas-and-mark-what-the-panel-does-not-know.md)).
- **Adapter Layer**: not a separate directory but the `api` and `model` segments of frontend slices; the config schema adaptation is in `entities/Config` and `entities/Rule` ([ADR-0005](./ADR-0005-keep-foreign-api-adapters-in-the-api-segment.md)).
- **UI Layer**: auto-forms from the schema and hand-written overrides on top of them ([ADR-0035](./ADR-0035-render-node-forms-from-the-generated-schema.md)).
- **Ownership**: the daemon holds the config as bytes ([ADR-0002](./ADR-0002-apply-protocol-and-config-ownership.md)), the panel edits the text in place ([ADR-0004](./ADR-0004-edit-config-text-in-place-on-the-client.md)), an unknown node is marked "not covered by the UI" (ADR-0018).

## Consequences

### Positive

- A fork version bump is mechanical: regenerate the schema, fix the adapter where the format broke.
- A foreign config passes a round-trip without losses (AC-1…AC-3 are confirmed by the corpus).

### Negative

- Three layers instead of one: every field a screen shows goes through the schema and the adapter.
- In the code the adapter is not versioned as the layer diagram promises: the panel is built on one schema version. A version mismatch is caught by a warning ([ADR-0044](./ADR-0044-catch-schema-drift-in-ci-and-at-runtime.md)), not by a second adapter.

### Neutral or deferred

- Completeness of parsing manually entered JSON back into forms is built up iteratively (section 8 of the PRD).

## Compatibility, migration and rollback

Not applicable: the decision has been in effect since the start of the project and is moved from the PRD without changes in substance.

## Validation

- The golden round-trip over the corpus `apps/web/src/entities/Config/__tests__/corpus/` in `make test` (AC-1…AC-3).
- The `ConfigNodeForm.coverage` walk test opens every inbound and outbound type with a form (AC-5).
- The boundary linter `apps/web/tools/fsdBoundaries.js` lets generated schemas only into the `api` and `model` segments of entities: screens read the model, not the shape of the schema.
