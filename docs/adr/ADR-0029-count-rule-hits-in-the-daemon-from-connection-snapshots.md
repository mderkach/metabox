# ADR-0029. Считать срабатывания правил в демоне по снапшотам соединений с его запуска

- Статус: Proposed
- Дата: 2026-09-23
- Ответственные: владелец репозитория

## Контекст и постановка проблемы

AC-46 требует показать у правила в списке, сколько раз оно сработало. Считать должен демон, по потоку соединений: ни sing-box, ни его Clash API такого числа не отдают. Счётчик живёт, пока живёт демон, и перезапуск его обнуляет — об этом панель говорит прямо, а не выдаёт ноль за «правило мёртвое».

Что уже есть в коде:

- Clash API отдаёт только живые соединения: `GET /connections` — снапшот, закрытых в нём нет. У каждого соединения есть строка сработавшего правила вида `rule_set=apple => route(proxy)`.
- Сопоставлять эту строку с узлом `route.rules` демон уже умеет: `matchRule` в `internal/route` сравнивает условия со списком `GET /rules` работающего процесса и отбрасывает правила, чьё действие перебор не прерывает ([ADR-0007](./ADR-0007-explain-route-without-own-rule-evaluator.md)).
- Хаб потока рантайма опрашивает `/connections` только пока есть читатель, то есть открыта панель.
- Гайд демона запрещает фоновые опросы без потребителя. Единственное исключение — учёт трафика `events.Accounting`, с разбором цены (`apps/metaboxd/docs/guides/DeviceIO.md`, «Ресурсы»).

Вне scope: точный счёт каждого соединения и хранение счёта между перезапусками демона.

## Критерии выбора

1. Счёт идёт всё время работы демона, а не только пока открыта панель.
2. Номер правила не выдумывается: сопоставление только тем способом, что уже есть в ADR-0007.
3. Переставленное при применении правило сохраняет свой счёт.
4. Цена в простое названа и ограничена.
5. Без новых зависимостей.

## Рассмотренные варианты

1. **Отдельный постоянный опрос `/connections` в демоне, ключ счёта — условия и действие правила.**
   - Соединение засчитывается, когда его идентификатор впервые появился в снапшоте.
   - Список правил перечитывается, когда встретилось правило, которого нет в запомненном.
   - Номер правила определяется при чтении счёта по текущему списку процесса.
   - Отвечает всем критериям. Минус — второе исключение из правила фоновых опросов.
   - **Принят.**
2. **Считать внутри хаба потока, пока есть читатель.** Дёшево, но счёт шёл бы только при открытой панели, и «за 3 часа» значило бы «за те минуты, что панель была открыта». Противоречит AC-46. **Отклонён.**
3. **Ключ счёта — номер правила.** Проще, но после применения, которое переставило правила, счёт переехал бы к чужому правилу. **Отклонён.**
4. **Считать в браузере по кадрам потока.** Счёт обнулялся бы с каждой вкладкой и был бы у каждого зрителя свой. **Отклонён.**

## Принятое решение

- `route.Counter` (`apps/metaboxd/internal/route/hits.go`) поднимается в `main.go` вместе с учётом трафика и работает до остановки демона.
- Интервал опроса тот же, что у топика соединений: `connectionsInterval`, одна секунда.
- Соединение засчитывается один раз — по первому появлению идентификатора. Соединения `final` считаются отдельно, соединения с правилом, которого нет в списке процесса, не засчитываются.
- Ключ счёта — пара «условия, действие» правила процесса. Дубль правила ниже по списку получает ноль: роутер останавливается на первом совпадении.
- `GET /api/rules/hits` отдаёт `route.Hits`:
  - `seconds` — сколько идёт счёт;
  - `rules` — по записи на правило процесса в его порядке;
  - `final`.

  Отказ рантайма — 502 `runtime_unavailable`, как у объяснения маршрута.

- Панель сверяет длину списка процесса с `route.rules` применённого файла и при расхождении счёт не показывает.
- Строка черновика получает счёт через своё правило в применённом файле: узел сравнивается целиком (`toAppliedIndices`). Правило, изменённое в черновике, счёта не получает.
- В подвале списка — окно счёта «за N с запуска metaboxd, перезапуск его обнуляет».

## Последствия

### Положительные

- Счёт виден без открытой панели и переживает применение, которое переставило правила.
- Ноль читается как «не срабатывало за это окно», а не как «правило мёртвое».

### Отрицательные

- Счёт наблюдаемый, а не точный: соединение, которое открылось и закрылось между двумя снапшотами, в него не попадает. Короткие DNS- и QUIC-соединения недосчитываются.
- Постоянная цена в простое: один снапшот `/connections` в секунду. На 5000 соединений — это разбор мегабайта JSON в секунду независимо от того, смотрит ли кто-нибудь на панель. Замера на устройстве нет.
- При открытой панели `/connections` опрашивают двое — хаб и счётчик: запросы в секунду удваиваются.
- Правила с одинаковыми условиями и действием, различающиеся только полями, которые Clash API не показывает, сливаются в один счёт.

### Нейтральные или отложенные

- Хранение счёта на диске не делается: AC-46 прямо требует обнуления при перезапуске.
- Объединить опрос хаба и счётчика в один — после замера цены на устройстве.

## Совместимость, миграция и откат

Новая ручка, контракт существующих не меняется. Откат — убрать `route.NewCounter` из `main.go`: ручки не станет, а панель покажет список без колонки и подпись «счёт не получен».

## Проверка решения

- `go test -race ./internal/route ./internal/httpapi`:
  - соединение засчитывается один раз;
  - счёт следует за переставленным правилом;
  - список перечитывается на незнакомое правило;
  - дубль получает ноль;
  - окно счёта считается на фиктивных часах `synctest`;
  - ручка отдаёт 502 при лежащем рантайме.
- `pnpm --filter web exec vitest run EditorPage Rule.applied`:
  - колонка и окно счёта видны;
  - процесс на другом конфиге счёт не раздаёт;
  - изменённое правило помечено и счёта не получает.
- На устройстве — замерить RSS и CPU демона в простое с 5000 соединениями.
