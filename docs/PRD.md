## 1. Обзор продукта и постановка проблемы

### 1.1. Проблема

Единственный способ управлять sing-box на OpenWrt — SSH: правка `config.json` в редакторе, `sing-box check`, рестарт сервиса, ручной откат, если связь отвалилась.

Две задачи возникают чаще всего, и цикл обслуживает их плохо:

1. **Правка правил маршрутизации** — «этот домен мимо прокси», «это устройство через выход X». Изменение на одну строку требует полного цикла SSH → редактор → check → restart.
2. **Диагностика «почему не работает»** — чтобы понять, какое правило сработало, нужно сопоставлять живые соединения с конфигом и логами вручную.

Цена ошибки асимметрична: неудачная правка маршрутизации отрезает доступ и к интернету, и к самому роутеру.

### 1.2. Продукт

**metabox** — веб-панель для OpenWrt, объединяющая две вещи, которые сегодня разнесены по разным инструментам:

1. **графическое создание и редактирование конфигурации sing-box-extended** — так, чтобы работа с JSON была выбором, а не необходимостью;
2. **рантайм-мониторинг и управление** прокси в духе MetaCubeXD (переписанный самостоятельно, не форк).

Поставляется как единый Go-демон со встроенным веб-интерфейсом, устанавливаемый на роутер.

Формула продукта: **единое место, где видно, что роутер делает с трафиком, и это можно изменить**. Новичку — прямой ответ на вопрос «почему не работает»; тому, кто знает схему, — полный нативный конфиг без SSH. Оба входа ведут к одним и тем же данным: экран соединений объясняет маршрут и открывает сработавшее правило, редактор и raw-режим дают полный контроль над документом.

### 1.3. Отличие от аналогов

| Проект                   | Что делает                                                                                                       | Чего не делает                                 |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| MetaCubeXD               | дашборд Clash API для mihomo                                                                                     | не редактирует конфиг, не про sing-box         |
| b4 (daniellavrushin)     | GUI обхода DPI, свои sets, geodat                                                                                | своя модель, не sing-box                       |
| LuCI-пакеты для sing-box | базовая настройка через uci                                                                                      | нет полноценного редактора схемы, нет дашборда |
| **metabox**              | **полное GUI-покрытие схемы sing-box-extended + дашборд + rule-sets + объяснение маршрута по живому соединению** | —                                              |

Редактор форм воспроизводим и сам по себе преимуществом не является. Отличие держится на том, чего нет ни у редакторов, ни у дашбордов: связка «живое соединение → сработавшее правило → узел конфига» и безопасное применение правки. Как это строится на наблюдаемых данных core — [ADR-0007](./adr/ADR-0007-explain-route-without-own-rule-evaluator.md).

## 2. Персоны и пользовательские сценарии

### 2.1. Персоны

**P1. Владелец роутера — основная персона v1.** Автор проекта, BPI-R4 Pro. Знает схему sing-box и правит конфиг руками. Работа с JSON допустима, но не обязательна. Проблема — цикл обслуживания, а не сложность sing-box.

**P2. Продвинутый пользователь OpenWrt — вторичная персона, появляется при выходе в опенсорс.** Ставит пакеты и читает документацию, схему sing-box не знает. GUI для него — условие использования. На приёмку v1 не влияет, но решения не должны закрывать его сценарий.

**Сцена работы.** Панель открывают с десктопа, чаще рядом с ssh-сессией на роутер: там правят правила, редактируют конфиг и применяют его. С телефона смотрят обзор и соединения и переключают ноду — это диагностический вход. Правка конфига и Apply с телефона целевым сценарием не считаются, но каркас панели обязан оставаться пригодным от 400 px (AC-42).

## 3. Цель и метрики успеха

### 3.1. Цель

Дать владельцу OpenWrt-роутера возможность полностью управлять sing-box-extended из браузера: собрать конфигурацию любой поддерживаемой форком сложности в графическом интерфейсе, безопасно применить её на устройство с гарантией отката, подключить нужные наборы правил маршрутизации и наблюдать за результатом в реальном времени — не подключаясь по SSH.

При этом metabox обязан корректно принимать конфигурации, написанные вручную или сгенерированные другими инструментами: распарсить, показать в UI, дать отредактировать и сохранить.

### 3.2. Метрики успеха

Метрики измеряют продукт, критерии приёмки раздела 5 — готовность релиза.

| ID   | Метрика                                  | Целевое значение                                                                                             | Как измеряется               |
| ---- | ---------------------------------------- | ------------------------------------------------------------------------------------------------------------ | ---------------------------- |
| SM-1 | Время типовой правки маршрутизации       | ≤ 1 минуты от открытия UI до применённого конфига                                                            | Замер на живом сценарии US-1 |
| SM-2 | Время диагностики «трафик пошёл не туда» | ≤ 2 минут, без чтения конфига и логов через SSH                                                              | Замер на живом сценарии US-2 |
| SM-3 | Подключения по SSH ради конфига          | 0 за месяц эксплуатации                                                                                      | Журнал владельца             |
| SM-4 | Надёжность применения                    | 0 случаев потери доступа, потребовавших SSH или физического сброса                                           | Журнал эксплуатации          |
| SM-5 | Целостность round-trip                   | 100% конфигов из тестового корпуса загружаются и сохраняются без потери данных и без ложных ошибок валидации | Автотест на корпусе конфигов |

SM-1 и SM-2 закрывают две задачи из §1.1, SM-3…SM-5 — сохранность доступа и данных.

## 5. Функциональные требования (критерии приёмки)

### Config Editor

- [x] **AC-1.** Рукописный `config.json` с реального роутера загружается, парсится и отображается в UI без ошибок.
- [x] **AC-2.** После загрузки чужого конфига, изменения одного поля и сохранения диф с исходным файлом содержит только это изменение — ничего не потеряно и не переупорядочено произвольно. Единственное допустимое отличие сверх правок пользователя — секция `experimental.clash_api`, добавляемая по AC-31 и показываемая явно. Секция `service` типа `api` под это исключение не подпадает: по AC-33 она появляется только по явному действию пользователя.
- [x] **AC-3.** Конструкции, не распознанные моделью, сохраняются при round-trip и отмечаются в UI как нераспознанные.
- [ ] **AC-4.** Невалидные значения подсвечиваются в UI до попытки применения, с указанием узла и причины.
- [ ] **AC-5.** Каждый тип inbound/outbound из чеклиста форка имеет либо ручную форму, либо автогенерируемый рендерер — узлов без рендерера нет.
- [ ] **AC-6.** Конфиг, собранный в UI с нуля для сценария «VLESS/Reality + маршрутизация по правилам», проходит `sing-box check` без правок руками.

### Rule-set Manager

- [ ] **AC-7.** В UI есть каталог готовых наборов правил с выбором поставщика и поиском по категориям: Runet Freedom, `geosite` и `geoip` v2fly, antifilter и прочие источники, которые владелец сочтёт нужными. Выбранная категория попадает в конфиг как `remote` rule-set с корректным URL, а поставщик виден в UI — по нему понятно, чьему списку доверяет маршрут. Каталог открывается без доступа к сети: снимок перечня категорий встроен в демон. Когда сеть есть, демон сам сверяет перечень с поставщиками раз в сутки, а панель показывает, когда перечень сверен. Он не единственный путь — адрес, которого в каталоге нет, вписывается руками, и у поставщика можно выбрать зеркало, потому что до основного адреса из России дотягиваются не всегда.
- [ ] **AC-8.** Пользователь может собрать кастомный список доменов и адресов в UI, в том числе взяв за основу список поставщика из AC-7. Список хранится в конфиге sing-box, а не в состоянии демона: небольшой — узлом `inline` в `route.rule_set`, большой — файлом в подкаталоге каталога конфига под узлом `local`, который пишется, проверяется и откатывается протоколом Apply вместе с конфигом.
- [ ] **AC-9.** Правило маршрутизации может ссылаться на любой подключённый rule-set, и это отражается в применённом конфиге.
- [ ] **AC-44.** Подключая `remote` rule-set, панель проверяет, есть ли в конфиге `experimental.cache_file`, и, если его нет, объясняет цену: без кэша перезагрузка роутера в момент, когда поставщик недоступен, не даёт sing-box запуститься вовсе — один недобранный набор обрывает старт целиком. Включение секции предлагается явным действием и уходит тем же применением, что и сам набор; сама панель её не добавляет — исключение из AC-2 остаётся ровно одно, и это `experimental.clash_api` из AC-31.
- [x] **AC-45.** Режим маршрутизации sing-box (`Rule`, `Global`, `Direct`) переключается из панели, а не только показывается. Режим — состояние рантайма, а не конфига: переключение уходит в Clash API и не трогает файл, поэтому бара применения и окна подтверждения у него нет. Текущий режим виден без перехода на отдельный экран, а отказ рантайма показывается так же, как у прочих действий над ним.
- [x] **AC-46.** У правила в списке видно, сколько раз оно сработало. Счётчик ведёт демон по потоку соединений: ни sing-box, ни его Clash API такого числа не отдают. Счётчик живёт, пока живёт демон, и его перезапуск обнуляет счёт — панель показывает это прямо, а не выдаёт ноль за «правило мёртвое».
- [x] **AC-47.** Тип узла, которого нет в сборке sing-box на устройстве, панель показывает с предупреждением: собрать такой конфиг она не мешает, но называет последствие — бинарь откажется стартовать. Состав сборки берётся у самого бинаря, а не зашивается в панель списком.

### Runtime Dashboard

- [x] **AC-10.** Overview показывает трафик up/down в реальном времени, счётчики, память и состояние сервиса. Там же — сводку живого снапшота соединений: действие правила, тип сети, топ узлов прокси и устройств локальной сети, число открытых соединений за минуту и задержка выбранных группами узлов. Сводку считает панель по снапшоту и метит как вычисленное (UX-8); собственной истории у сводки нет — она описывает снапшот, а не период. История трафика и показаний платы — AC-37.
- [x] **AC-35.** Overview показывает показания устройства: загрузку и число ядер, температуру платы, занятую память из общей, скорость интерфейса наружу, долю трафика, прошедшую через sing-box за время наблюдения, резидентную память и pid процесса sing-box, память и горутины демона, аптайм роутера. Читает их демон из procfs и sysfs и отдаёт топиком единого потока; отсутствие отдельного источника — термозон, маршрута по умолчанию, процесса — гасит своё поле, а не весь топик.
- [x] **AC-36.** Панель различает «процессом sing-box владеет служба, которой управляет демон» и «sing-box работает, но поднят чужой службой». Во втором случае состояние показывается работающим, а команды службы не предлагаются: они относятся к другому процессу.
- [x] **AC-37.** Демон копит историю рантайма — трафик, загрузку, температуру и память платы — и отдаёт её `GET /api/history`. Окно равно времени работы демона: заполненное кольцо не выбрасывает старое, а укрупняет шаг вдвое, начиная с десяти секунд. История и накопленные объёмы переживают перезагрузку страницы и закрытие вкладки; перезапуск демона их обнуляет. Абсолютного времени точка не несёт — подписи оси считает панель.
- [x] **AC-11.** Экран Proxies отображает группы и ноды, позволяет переключить активную ноду и запустить проверку задержки.
- [x] **AC-12.** Экран Connections показывает живой список соединений (хост, сработавшее правило, цепочка прокси, трафик, скорость за интервал снапшотов и возраст соединения) и позволяет закрыть соединение.

### Device Integration

- [x] **AC-13.** Apply выполняет полную последовательность из [ADR-0002](./adr/ADR-0002-apply-protocol-and-config-ownership.md); при провале `sing-box check` запись не происходит и пользователь видит ошибку от бинаря.
- [ ] **AC-14.** Заведомо ломающий связь конфиг приводит к автоматическому возврату предыдущего и восстановлению доступа без вмешательства по SSH.
- [x] **AC-15.** История версий конфига доступна в UI; откат на любую предыдущую версию работает.
- [x] **AC-16.** Рестарт сервиса выполняется через procd и корректно отрабатывает при уже остановленном сервисе.

### Backend / API

- [x] **AC-17.** Демон стартует одной командой, раздаёт встроенный UI и отвечает на REST API.
- [x] **AC-18.** Демон доступен со всех интерфейсов локальной сети — проводных, беспроводных и гостевых, — и недоступен снаружи: запрос с WAN не проходит. Набор локальных интерфейсов задаётся на устройстве и меняется без пересборки демона.
- [x] **AC-19.** Мутирующие запросы с несоответствующим `Origin`/`Host` отклоняются.

### Dev Environment

- [x] **AC-20.** `.devcontainer` одной командой поднимает фронт с HMR, Go-демон и целевое окружение с sing-box-extended.
- [x] **AC-21.** Внутри окружения выполняется полный цикл Apply, включая `sing-box check`, рестарт и healthcheck — без физического роутера.

### Устойчивость и схема

- [x] **AC-27.** При остановленном или упавшем sing-box панель открывается, показывает состояние сервиса и ошибку, позволяет отредактировать конфиг и запустить сервис.
- [x] **AC-28.** При расхождении версии установленного бинаря со схемой, на которой собран демон, в UI отображается предупреждение об этом.
- [ ] **AC-29.** Запись конфига атомарна: прерывание процесса или питания в момент записи не оставляет повреждённый или полузаписанный файл.
- [ ] **AC-30.** Экран Connections остаётся отзывчивым на конфиге с сотнями правил и тысячах активных соединений.

### Источник данных дашборда

- [x] **AC-31.** Демон гарантирует, что применяемый конфиг содержит работоспособный `experimental.clash_api`. Если секции нет, демон добавляет её целиком: `external_controller` со значением `127.0.0.1:<порт>` и сгенерированный `secret`. Если секция есть, а `external_controller` отсутствует или пуст, дописывается только адрес. Остальные пользовательские значения не изменяются, и `secret` к заведённой пользователем секции не дописывается: пустой секрет отключает авторизацию Clash API, а дописанный токен отрезал бы уже настроенных клиентов.
- [x] **AC-32.** Добавление секции проходит обычный протокол Apply и явно показывается пользователю как изменение, инициированное metabox, с указанием причины и того, что потребуется рестарт sing-box.
- [x] **AC-33.** Секцию `service` типа `api` демон сам не добавляет: она появляется только по явному действию пользователя и проходит обычный протокол Apply. Наличие или отсутствие этой секции не отключает ни один экран: пока источника событий нет, соединения читаются снапшотами Clash API. `GET /api/status` сообщает, какие источники доступны и какой используется для соединений, а контракт с фронтом не зависит от того, какой сработал. Решение — [ADR-0006](./adr/ADR-0006-read-runtime-from-clash-api-and-optional-grpc.md).

### Работа со списками и оформление панели

- [x] **AC-38.** Списки правил и соединений отбираются поиском по подстроке и фасетами — действие правила и устройство локальной сети. Отбор действует только на показ: конфиг он не меняет, а строка, которую схема не приняла, из списка не исчезает (AC-3).
- [x] **AC-39.** Снимок соединений выгружается в CSV и JSON тем же составом колонок и тем же отбором, что виден на экране. Выгрузка идёт из того, что уже пришло в панель, и отдельного запроса к устройству не делает.
- [x] **AC-40.** Экран правки всего конфига текстом (AC-24) показывает нумерацию строк, подсветку JSON и поиск с переходом по совпадениям. Подсветка и поиск текст не меняют: в Apply уходят те же байты, что видит пользователь.
- [x] **AC-41.** Панель работает в тёмной и светлой теме, тема переключается из интерфейса, и выбор переживает перезагрузку страницы.
- [x] **AC-42.** Каркас панели остаётся пригодным на ширине от 400 px: на узком экране навигация уходит в нижнюю панель с подписями, а корень панели открывает обзор, таблицы с фиксированными колонками прокручиваются по горизонтали вместе с шапкой, горизонтального переполнения самой страницы нет.
- [x] **AC-43.** Панель говорит на русском и английском. При первом заходе язык берётся у браузера, дальше — сохранённый выбор; переключается он из интерфейса и переживает перезагрузку. Язык документа объявлен атрибутом `lang` и следует за выбором. Текст экрана приезжает вместе с самим экраном: ключей вместо слов пользователь не видит. Устройство текстов — [ADR-0019](./adr/ADR-0019-keep-interface-texts-in-the-slice-and-load-them-over-the-network.md).

### Объяснение маршрута

- [x] **AC-34.** Каждое утверждение в объяснении маршрута несёт происхождение — `observed`, `computed` или `unknown`, — и API не отдаёт утверждений без него. Сработавшее правило связывается с узлом `route.rules` применённого конфига по его индексу; условие, причину непопадания которого вычислить нечем, помечается `unknown`, а не заменяется догадкой. Решение — [ADR-0007](./adr/ADR-0007-explain-route-without-own-rule-evaluator.md).

## 8. Non-Goals (v1)

- Аутентификация и многопользовательский доступ.
- Доступ к панели из интернета, HTTPS, защита от брутфорса.
- LuCI-интеграция.
- Экран логов.
- Скачивание и парсинг `geosite.dat`/`geoip.dat` на устройстве.
- Сборки под mips/mipsel и оптимизация под 8–16 МБ флеша.
- Поддержка upstream sing-box как отдельной цели совместимости.
- Управление несколькими роутерами из одной панели.
- **Формы для секции `services`.** Service-типы форка (`manager`, `manager-api`, `node`, `node-manager-api`, `admin-panel`, `ssm-api`, `ccm`, `ocm`, `derp`, `resolved`, `oom-killer`, `profiler`, `usbip-client`, `usbip-server`) относятся к серверным, мультиарендным или не-VPN сценариям. Они парсятся и сохраняются при round-trip по общему правилу AC-3/AC-25 и показываются сырыми блоками; рукописных форм для них не будет. Чеклист типов в AC-5 покрывает только inbound/outbound. Исключение — появившийся в 1.14 тип `api`: он относится к сценарию самой панели, форма для него нужна ([ADR-0006](./adr/ADR-0006-read-runtime-from-clash-api-and-optional-grpc.md)), а сама секция добавляется только по явному действию пользователя (AC-33).
- **Режим работы дашборда без Clash API.** Источник данных гарантируется демоном (AC-31); экрана-заглушки «включите clash_api» и тумблера в настройках нет. Единственное вырожденное состояние — остановленный sing-box (AC-27).
- **Полнота обратного разбора вручную отредактированного JSON в формы.** Ручное редактирование JSON — заявленная функция (US-8, AC-23…AC-24), но требование «любой введённый вручную конфиг полностью раскладывается в формы» набирается итерациями: в v1 распознанное показывается формами, остальное — сырыми блоками.

## 9. Constraints

- Схема — только sing-box-extended (форк shtorm-7); upstream-конфиги валидны как подмножество.
- Контракты демона и фронта не предполагают, что управляемый рантайм всегда sing-box-extended: тип, вариант и версия core приходят данными, а не зашиты в типы и имена ручек. Это ограничение на форму контрактов, а не разрешение добавлять второй core в v1 — он остаётся за границей раздела 8.
- Целевая ОС — OpenWrt; управление сервисом только через procd/init.d.
- Целевая архитектура сборки v1 — aarch64.
- Единый артефакт поставки — Go-бинарь со встроенной статикой; пакет apk. Целевое устройство работает на OpenWrt SNAPSHOT с apk 3.0.5 и ipk не принимает; формат ipk в v1 не собирается.
- Веб-стек: React, TypeScript, Vite, oxlint, oxfmt; TanStack Router / Query / Table / Virtual; Zustand; React Hook Form; Zod (генерируется, версия пинится точно); shadcn/ui + Tailwind. Подробности и обоснование — A.10.
- Порядок сборки задаётся Makefile, `go:embed` берёт `apps/web/dist`. Воркспейс pnpm нужен для общих devDependencies и единых версий инструментов.
- Демон слушает только LAN-интерфейс.
- Разработка ведётся в `.devcontainer`, поднимающем фронт, бэк и целевое окружение.
- Работа с JSON — выбор пользователя, а не условие выполнения задачи.

### Roadmap после v1

1. **Аутентификация** — логин/пароль, сессии, защита API. Закрывает R-1.
2. **Второй core** — сначала upstream sing-box как отдельная цель совместимости, затем Xray. Каждый core получает собственные схему, validator, адаптер сервиса и публичную таблицу возможностей; общая «усреднённая» схема конфига не заводится. Начинается с ADR о границе адаптера, а не с кода.
3. Экран Logs.
4. **Разрезы истории по источнику.** История трафика глубже минуты появилась в демоне (AC-37, [ADR-0015](./adr/ADR-0015-keep-traffic-history-in-the-daemon.md)). Официальный дашборд и metacubexd режут её ещё и по устройству, хосту, прокси и процессу — это требует писать в историю снапшот соединений, а в нём до 5000 записей в секунду (NFR-2).
5. **Сетевая диагностика** — проверка качества канала и STUN-тест, как отдельный экран. Взято из инструментов встроенного дашборда sing-box.
6. LuCI-интеграция.
7. Локальный dat-пайплайн как опция (скачивание geosite/geoip, дерево категорий).
8. Поддержка слабого железа и mips — при наличии запроса сообщества.
9. HTTPS и безопасный внешний доступ.

## Приложение A. Архитектурные решения

Решения, принятые до введения ADR. Приложение закрыто для новых записей: новое решение оформляется ADR в [`adr/`](./adr/README.md), а раздел A.* переезжает туда, когда соответствующую часть системы начинают реализовывать.

### A.1. Целевая схема — только sing-box-extended

Совместимость целится в форк [shtorm-7/sing-box-extended](https://github.com/shtorm-7/sing-box-extended) (WARP, MASQUE, MTProxy, Mieru, TrustTunnel, SSH сверх upstream-протоколов; OpenVPN и Snell в 1.14 переехали в upstream, и форк перешёл на его реализации). Поскольку форк является надмножеством upstream, обычные конфиги sing-box остаются валидными автоматически.

Установка sing-box-extended на OpenWrt в целевом сценарии — через [EikeiDev/OpenWRT-sing-box-extended](https://github.com/EikeiDev/OpenWRT-sing-box-extended).

### A.2. Трёхслойная модель конфига

```text
┌─────────────────────────────────────────────────────────┐
│ UI Layer                                                 │
│  ручные формы (чеклист типов) + автогенерируемый         │
│  fallback-рендерер для непокрытых узлов схемы            │
└────────────────────────┬────────────────────────────────┘
                         │  внутренняя модель metabox
┌────────────────────────┴────────────────────────────────┐
│ Adapter Layer (версионированный)                         │
│  маппинг «схема форка ↔ модель metabox»                 │
│  при ломающем изменении API правится ТОЛЬКО этот слой   │
└────────────────────────┬────────────────────────────────┘
                         │  типы + валидаторы
┌────────────────────────┴────────────────────────────────┐
│ Schema Layer                                             │
│  генерируется из sing-box-extended, обновляется          │
│  механически при релизе форка                            │
└─────────────────────────────────────────────────────────┘
```

**Обоснование (Round 5):** полное GUI-покрытие названо приоритетом, а ручные формы под всю схему протухают на каждом релизе форка. Адаптерный слой изолирует UI от изменений схемы; генерация даёт покрытие по умолчанию; ручные формы дают нормальный UX там, где он важен.

**Владение конфигом (Round 1):** гибрид. metabox владеет конфигом и генерирует его, но обязан распарсить произвольный `config.json`. Конструкции, которые модель не распознала, не теряются — сохраняются и подсвечиваются в UI как нераспознанные/невалидные.

### A.2.1. Получение схемы из форка — решение по OQ-2 (2026-08-30)

Раздел переехал в [ADR-0001](./adr/ADR-0001-generate-schema-from-fork-registries.md): описанный здесь алгоритм расходится с фактическим устройством форка, и ADR задаёт его заново.

Из решения остаётся в силе требование к форме результата: генерируемые схемы держатся представимыми для `z.toJSONSchema()`, без `.transform()`, — на этой конвертации стоит авторендерер непокрытых узлов (AC-5).

### A.3. Рантайм — Go-демон со встроенным UI

Один бинарь на устройстве:

- раздаёт собранную SPA (embed);
- REST API для конфига, рулсетов, применения;
- владеет `config.json`, историей версий и бэкапами;
- вызывает `sing-box check`, `sing-box rule-set compile`;
- управляет сервисом через procd (`/etc/init.d/sing-box`);
- проксирует Clash API sing-box для дашборда.

**Цена решения:** проект двухъязычный (Go + TypeScript), нужна кросс-компиляция под aarch64 и CI, собирающий фронт перед embed.

### A.4. Протокол Apply (Round 7)

Раздел переехал в [ADR-0002](./adr/ADR-0002-apply-protocol-and-config-ownership.md): последовательность применения задана там вместе с решениями, которых здесь не было, — представлением конфига, предметом валидации и хранением состояния транзакции.

### A.5. Rule-sets (Round 6)

Раздел переехал в ADR: каталог готовых категорий и его сверка с поставщиками — в [ADR-0034](./adr/ADR-0034-keep-the-rule-set-catalog-in-the-daemon-and-refresh-it-daily.md), хранение кастомных списков — в [ADR-0033](./adr/ADR-0033-keep-custom-rule-lists-in-the-singbox-config.md). Компиляция кастомного списка в `.srs` на устройстве отменена: `local` rule-set форка читает исходник в JSON напрямую.

### A.6. Модель доступа (Round 8) — осознанный риск

**Аутентификации в v1 нет.**

Риск зафиксирован явно: любое устройство в LAN (гостевой Wi-Fi, IoT, скомпрометированный клиент) получает полный контроль над маршрутизацией всей сети и может незаметно завернуть трафик через свой outbound. Отдельно — CSRF: злонамеренная веб-страница в браузере владельца способна слать запросы на адрес панели без всякого пароля.

Обязательные митигации в v1:

- bind строго на LAN-интерфейс, **не** на `0.0.0.0`;
- проверка заголовков `Origin`/`Host` на всех мутирующих запросах;
- явное предупреждение в README;
- аутентификация — первый пункт roadmap после v1.

### A.7. Целевое железо (Round 11)

**Banana Pi BPI-R4 Pro** (MediaTek MT7988A, aarch64, 8 ГБ RAM, NVMe/eMMC). Ресурсных ограничений уровня «влезет ли во флеш» нет. Единственная целевая архитектура сборки v1 — **aarch64**.

### A.8. Ручное редактирование JSON и модель Save/Apply (интервью 2, Round 4–6)

Ручное редактирование JSON — заявленная функция, а не аварийный люк: raw-режим доступен на любом узле, плюс есть режим правки всего конфига текстом. Три правила разрешают конфликт двух источников истины:

1. **Данные не теряются.** Нераспознанный узел сохраняется как есть и показывается сырым блоком с пометкой «UI не покрывает».
2. **Валидность определяет `sing-box check`,** а не схема metabox. Схема обслуживает формы и подсказки, но не запрещает то, что принимает бинарь.
3. **Save ≠ Apply.** Save сохраняет черновик всегда, с предупреждениями; Apply требует успешного `check`. Обойти вердикт бинаря нельзя — force-apply отсутствует намеренно.

Требование «вручную введённый JSON полностью раскладывается в формы» — итеративное: v1 раскладывает распознанное, полнота набирается со временем.

### A.9. Отслеживание дрейфа схемы (интервью 2, Round 7)

Два независимых механизма:

- **CI** отслеживает релизы sing-box-extended, прогоняет генератор схемы и открывает PR с диффом — изменение не может пройти незамеченным.
- **Рантайм** сравнивает версию установленного на устройстве бинаря с версией схемы, на которой собран демон, и при расхождении показывает предупреждение в UI (AC-28). Работает: демон читает `sing-box version` и отдаёт её в `/api/status`, схема несёт версию форка константой.

### A.10. Стек фронтенда и структура репозитория — решение по OQ-1 (2026-08-30)

Определяющий факт: в приложении **два состояния с разными требованиями**, и их нельзя накрывать одним инструментом.

- **Документ конфига** — один большой вложенный JSON. Клиентский, живёт между экранами, требует dirty-tracking, черновика отдельно от применённого (UX-2), дифа перед Apply (UX-6), истории, адресации по строковому пути (авторендерер строит поля из схемы в рантайме) и сырых блоков внутри дерева (UX-3).
- **Рантайм-данные дашборда** — server state: эфемерный, высокочастотный, до 5000 соединений (NFR-2).

| Слой                | Решение                                 | Обоснование                                                                                                                                                                                        |
| ------------------- | --------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Состояние документа | Zustand                                 | Документ — не форма; черновик, история и диф пишутся явно, без submit-семантики. Черновик immer снят: дерева в сторе нет ([ADR-0024](./adr/ADR-0024-drop-the-immer-draft-from-frontend-stores.md)) |
| Server state        | TanStack Query, только запрос-ответ     | Поток рантайма (трафик, соединения) идёт мимо Query в отдельный стор; Query поверх потока даёт кэш, который врёт                                                                                   |
| Роутинг             | TanStack Router, code-based             | Экранов шесть, file-based плагин избыточен ; типизированные search params держат фильтры Connections в URL                                                                                         |
| Таблицы и списки    | TanStack Table + TanStack Virtual       | Требование виртуализации из NFR-2                                                                                                                                                                  |
| Формы               | React Hook Form + `@hookform/resolvers` | Неконтролируемый — меньше ререндеров на конфиге в 500 правил                                                                                                                                       |
| Валидация           | Zod (генерируется, см. A.2.1)           | Единый источник со схемой                                                                                                                                                                          |
| UI                  | shadcn/ui + Tailwind                    | Авторендерер собирает поля программно, ему нужны примитивы без чужой темизации сверху                                                                                                              |

**Ограничения RHF, влияющие на реализацию.** Имена полей — только точечная нотация (`outbounds.2.uuid`), скобки не поддерживаются; авторендерер печатает пути точками. Формы типизируются против типа **узла** (`VLESSOutboundOptions`), а не против типа всего конфига: `Path<T>` по union на 57 веток разложит компилятор. Именно решение держать документ в Zustand и открывать форму на узле снимает этот риск. Для авторендерера типобезопасности путей нет ни в одной библиотеке — там строка и приведение типа.

**Структура репозитория** — папка на проект: `apps/metaboxd`, `apps/web`, `tools/schemagen`, каждый со своим манифестом, `AGENTS.md` и гайдами. Актуальное дерево — в [`../README.md`](../README.md) и [`../AGENTS.md`](../AGENTS.md), чтобы описание не разъезжалось с репозиторием.

Сборку связывает Makefile: фронт собирается до `go build`, потому что попадает в бинарь через `go:embed`. Воркспейс pnpm держит общие devDependencies и каталог версий, сборкой не управляет.

## Приложение B. Технический контекст

**Стек, зафиксированный пользователем:** React, TypeScript, TanStack, Vite, oxlint, oxfmt. Остальное (стейт-менеджмент, UI-кит, роутинг, форма, тесты, структура проекта) — предмет отдельного согласования после утверждения PRD.

**Дополнительно следует из решений интервью:**

- Go — язык демона (кросс-компиляция под aarch64, embed статики).
- Схема и адаптеры требуют генератора: извлечение структуры из sing-box-extended → типы TS + валидаторы.
- Clash API sing-box (`experimental.clash_api`) — источник данных для дашборда; трафик и память форк отдаёт построчным chunked-ответом, соединения — снапшотом.
- Multi-container devcontainer: dev-контейнер со стеком сборки + target-контейнер на OpenWrt rootfs.

**Референсы, изученные в ходе интервью:**

- [shtorm-7/sing-box-extended](https://github.com/shtorm-7/sing-box-extended) — целевой форк.
- [EikeiDev/OpenWRT-sing-box-extended](https://github.com/EikeiDev/OpenWRT-sing-box-extended) — установщик под OpenWrt.
- [daniellavrushin/b4](https://github.com/daniellavrushin/b4) — Go-демон со встроенным UI, единый JSON-конфиг, каталог geodat-источников в UI, выбор категорий в Sets → Targets. Архитектурный образец для A.3, каталог источников — для A.5, но своей модели конфига (не sing-box) и без `.srs`.
- MetaCubeXD — образец набора экранов дашборда Clash API.
