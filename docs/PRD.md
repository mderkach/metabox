## 1. Product overview and problem statement

### 1.1. Problem

Without a dedicated panel, sing-box on OpenWrt is managed over SSH: editing `config.json` in an editor, `sing-box check`, restarting the service, manual rollback if the connection drops.

Two tasks come up most often, and the cycle serves them poorly:

1. **Editing routing rules** — "this domain bypasses the proxy", "this device goes through outbound X". A one-line change requires the full SSH → editor → check → restart cycle.
2. **Diagnosing "why it doesn't work"** — to see which rule matched, live connections must be matched against the config and logs by hand.

The cost of a mistake is asymmetric: a bad routing edit cuts off access both to the internet and to the router itself.

### 1.2. Product

**metabox** is a web panel for OpenWrt that combines two things that today live in separate tools:

1. **graphical creation and editing of the sing-box-extended configuration** — so that working with JSON is a choice, not a necessity;
2. **runtime monitoring and control** of the proxy in the spirit of MetaCubeXD (rewritten independently, not a fork).

It ships as a single Go daemon with an embedded web interface, installed on the router.

Product formula: **one place where you can see what the router does with traffic, and change it**. For a newcomer — a direct answer to "why it doesn't work"; for someone who knows the schema — the full native config without SSH. Both entries lead to the same data: the connections screen explains the route and opens the matched rule, the editor and raw mode give full control over the document.

### 1.3. Difference from analogs

Checked against the projects' READMEs as of 2026-10-13, not verified on a device.

| Project                                | What is claimed                                                                                                                                             | How it differs from metabox                                |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| MetaCubeXD                             | Clash API dashboard, profile editor with a check before activation                                                                                          | mihomo core, not sing-box                                  |
| b4 (daniellavrushin)                   | DPI bypass GUI, own sets, geodat                                                                                                                            | own model, not sing-box                                    |
| luci-app-singbox-ui, luci-app-sing-box | LuCI apps: JSON editing, templates, forms for part of the settings, dashboard; one of them checks and rolls back on profile activation                      | the "connection → rule → config node" chain is not claimed |
| **metabox**                            | **forms built from the sing-box-extended schema for supported nodes, raw JSON on any node, dashboard, rule sets, route explanation from a live connection** | —                                                          |

A form editor is reproducible and is not an advantage by itself. The difference rests on what none of the projects above claims: the "live connection → matched rule → config node" chain and safe application of an edit. How this is built on observable core data — [ADR-0007](./adr/ADR-0007-explain-route-without-own-rule-evaluator.md).

## 2. Personas and user scenarios

### 2.1. Personas

**P1. Router owner — the main v1 persona.** The project author, BPI-R4 Pro. Knows the sing-box schema and edits the config by hand. Working with JSON is acceptable but not required. The problem is the maintenance cycle, not the complexity of sing-box.

**P2. Advanced OpenWrt user — a secondary persona that appears with the open-source release.** Installs packages and reads documentation, does not know the sing-box schema. A GUI is a condition of use for them. Does not affect v1 acceptance, but decisions must not close off their scenario.

**Working setting.** The panel is opened from a desktop, usually next to an ssh session to the router: rules are edited, the config is edited and applied there. From a phone, people look at the overview and connections and switch the node — this is the diagnostic entry. Editing the config and Apply from a phone are not a target scenario, but the panel frame must stay usable from 400 px (AC-42).

## 3. Goal and success metrics

### 3.1. Goal

Let the owner of an OpenWrt router fully manage sing-box-extended from a browser: build a configuration of any complexity the fork supports in a graphical interface, apply it safely to the device with a rollback guarantee, connect the needed routing rule sets and watch the result in real time — without connecting over SSH.

metabox must also correctly accept configurations written by hand or generated by other tools: parse them, show them in the UI, allow editing and save them.

### 3.2. Success metrics

Metrics measure the product, the acceptance criteria in section 5 measure release readiness.

| ID   | Metric                                        | Target value                                                                                             | How it is measured                  |
| ---- | --------------------------------------------- | -------------------------------------------------------------------------------------------------------- | ----------------------------------- |
| SM-1 | Time of a typical routing edit                | ≤ 1 minute from opening the UI to an applied config                                                      | Measured on a live US-1 scenario    |
| SM-2 | Time to diagnose "traffic went the wrong way" | ≤ 2 minutes, without reading the config and logs over SSH                                                | Measured on a live US-2 scenario    |
| SM-3 | SSH connections for the sake of the config    | 0 per month of operation                                                                                 | Owner's log                         |
| SM-4 | Apply reliability                             | 0 cases of lost access that required SSH or a physical reset                                             | Operations log                      |
| SM-5 | Round-trip integrity                          | 100% of configs from the test corpus load and save without data loss and without false validation errors | Automated test on the config corpus |

SM-1 and SM-2 cover the two tasks from §1.1, SM-3…SM-5 cover preservation of access and data.

## 5. Functional requirements (acceptance criteria)

### Config Editor

- [x] **AC-1.** A handwritten `config.json` from a real router loads, parses and is shown in the UI without errors.
- [x] **AC-2.** After loading a foreign config, changing one field and saving, the diff against the original file contains only that change — nothing is lost or arbitrarily reordered. The only allowed difference beyond the user's edits is the `experimental.clash_api` section, added under AC-31 and shown explicitly. A `service` section of type `api` does not fall under this exception: under AC-33 it appears only on an explicit user action.
- [x] **AC-3.** Constructs not recognized by the model are preserved on round-trip and marked in the UI as unrecognized.
- [x] **AC-4.** Invalid values are highlighted in the UI before an apply attempt, with the node and the reason.
- [x] **AC-5.** Each inbound/outbound type from the fork checklist has either a manual form or an auto-generated renderer — there are no nodes without a renderer.
- [ ] **AC-6.** A config built from scratch in the UI for the "VLESS/Reality + rule-based routing" scenario passes `sing-box check` without manual edits.

### Rule-set Manager

- [ ] **AC-7.** The UI has a catalog of ready-made rule sets with a choice of provider and search by category: Runet Freedom, v2fly `geosite` and `geoip`, and other sources the owner considers necessary; antifilter was removed from the list on 2026-10-09 (OQ-20), its lists are available as Runet Freedom categories. The selected category goes into the config as a `remote` rule set with a correct URL, and the provider is visible in the UI — it shows whose list the route trusts. The catalog opens without network access: a snapshot of the category list is built into the daemon. When there is network, the daemon itself checks the list against providers once a day, and the panel shows when the list was checked. It is not the only path — an address that is not in the catalog is entered by hand, and a provider can have a mirror selected, because the main address is not always reachable from Russia.
- [x] **AC-8.** The user can build a custom list of domains and addresses in the UI, including one based on a provider list from AC-7. The list is stored in the sing-box config, not in the daemon state: a small one as an `inline` node in `route.rule_set`, a large one as a file in a subdirectory of the config directory under a `local` node, which is written, checked and rolled back by the Apply protocol together with the config. When the device had no config before the apply, the rollback returns the list files alone and leaves the written config in place.
- [x] **AC-9.** A routing rule can reference any connected rule set, and this is reflected in the applied config.
- [x] **AC-44.** When connecting a `remote` rule set, the panel checks whether the config has `experimental.cache_file` and, if not, explains the cost: without the cache, rebooting the router while the provider is unreachable prevents sing-box from starting at all — one missing set aborts the whole start. Enabling the section is offered as an explicit action and goes out with the same apply as the set itself; the panel does not add it on its own — the AC-2 exception stays exactly one, and it is `experimental.clash_api` from AC-31.
- [x] **AC-45.** The sing-box routing mode (`Rule`, `Global`, `Direct`) is switched from the panel, not only shown. The mode is runtime state, not config: switching goes to the Clash API and does not touch the file, so it has no apply bar and no confirmation window. The current mode is shown and switched on the overview screen, and a runtime failure is shown the same way as for other runtime actions.
- [x] **AC-46.** A rule in the list shows how many times it matched. The counter is kept by the daemon from the connection stream: neither sing-box nor its Clash API returns such a number. The counter lives as long as the daemon lives, and its restart resets the count — the panel says so directly rather than presenting zero as "the rule is dead".
- [x] **AC-47.** A node type missing from the sing-box build on the device is shown by the panel with a warning: it does not prevent building such a config, but names the consequence — the binary will refuse to start. The build composition is taken from the binary itself, not hardcoded in the panel as a list.

### Runtime Dashboard

- [x] **AC-10.** Overview shows up/down traffic in real time, counters, memory and service state. It also shows a summary of the live connection snapshot: rule action, network type, top proxy nodes and LAN devices, number of opened connections per minute and latency of the nodes selected by groups. The summary is computed by the panel from the snapshot and marked as computed (UX-8); the summary has no history of its own — it describes the snapshot, not a period. Traffic and board readings history — AC-37.
- [x] **AC-35.** Overview shows device readings: load and number of cores, board temperature, used memory out of total, outward interface speed, the share of traffic that went through sing-box during observation, resident memory and pid of the sing-box process, daemon memory and goroutines, router uptime. The daemon reads them from procfs and sysfs and returns them as a topic of the single stream; a missing individual source — thermal zone, default route, process — blanks its own field, not the whole topic.
- [x] **AC-36.** The panel tells apart "the sing-box process is owned by the service the daemon manages" and "sing-box is running, but brought up by a foreign service". In the second case the state is shown as running, and service commands are not offered: they refer to another process.
- [x] **AC-37.** The daemon accumulates runtime history — traffic, load, temperature and board memory — and returns it via `GET /api/history`. The window equals the daemon uptime: a full ring does not drop old data but doubles the step, starting from ten seconds. History and accumulated volumes survive a page reload and closing the tab; a daemon restart resets them. A point carries no absolute time — axis labels are computed by the panel.
- [x] **AC-11.** The Proxies screen shows groups and nodes, allows switching the active node and running a latency check.
- [x] **AC-12.** The Connections screen shows a live list of connections (host, matched rule, proxy chain, traffic, speed over the snapshot interval and connection age) and allows closing a connection.

### Device Integration

- [x] **AC-13.** Apply runs the full sequence from [ADR-0002](./adr/ADR-0002-apply-protocol-and-config-ownership.md); if `sing-box check` fails, nothing is written and the user sees the error from the binary.
- [ ] **AC-14.** A config that is known to break connectivity leads to an automatic return of the previous one and restored access without SSH intervention.
- [x] **AC-15.** Config version history is available in the UI; rollback to any previous version works.
- [x] **AC-16.** Service restart is done via procd and works correctly when the service is already stopped.

### Backend / API

- [x] **AC-17.** The daemon starts with one command, serves the embedded UI and answers the REST API.
- [x] **AC-18.** The daemon is reachable from all LAN interfaces — wired, wireless and guest — and unreachable from outside: a request from WAN does not pass. The set of local interfaces is configured on the device and changes without rebuilding the daemon.
- [x] **AC-19.** Mutating requests with a mismatched `Origin`/`Host` are rejected.

### Dev Environment

### Resilience and schema

- [x] **AC-27.** With sing-box stopped or crashed, the panel opens, shows the service state and the error, allows editing the config and starting the service.
- [x] **AC-28.** If the installed binary version differs from the schema the daemon was built with, the UI shows a warning about it.
- [ ] **AC-29.** Config writes are atomic: interrupting the process or power during a write does not leave a corrupted or half-written file.
- [ ] **AC-30.** The Connections screen stays responsive on a config with hundreds of rules and thousands of active connections.

### Dashboard data source

- [x] **AC-31.** The daemon guarantees that the applied config contains a working `experimental.clash_api`. If the section is missing, the daemon adds it whole: `external_controller` with the value `127.0.0.1:<port>` and a generated `secret`. If the section exists but `external_controller` is missing or empty, only the address is added. Other user values are not changed, and `secret` is not added to a section the user created: an empty secret disables Clash API authorization, and an added token would cut off already configured clients.
- [x] **AC-32.** Adding the section goes through the normal Apply protocol and is shown to the user explicitly as a change initiated by metabox, with the reason and the fact that a sing-box restart will be required.
- [x] **AC-33.** The daemon does not add a `service` section of type `api` on its own: it appears only on an explicit user action and goes through the normal Apply protocol. The presence or absence of this section does not disable any screen: while there is no event source, connections are read as Clash API snapshots. `GET /api/status` reports which sources are available and which one is used for connections, and the contract with the frontend does not depend on which one worked. Decision — [ADR-0006](./adr/ADR-0006-read-runtime-from-clash-api-and-optional-grpc.md).

### Working with lists and panel appearance

- [x] **AC-38.** Rule and connection lists are filtered by substring search and facets: for rules — action and LAN device, for connections — device, action, rule, chain and network, with multi-select and a row count for each value. Filtering affects only the display: it does not change the config, and a row the schema did not accept does not disappear from the list (AC-3).
- [x] **AC-39.** The connection snapshot is exported to CSV and JSON with the same set of columns and the same filtering as on screen. The export uses what has already arrived in the panel and makes no separate request to the device.
- [x] **AC-40.** The screen for editing the whole config as text (AC-24) shows line numbers, JSON highlighting and search with navigation between matches. Highlighting and search do not change the text: Apply sends the same bytes the user sees.
- [x] **AC-41.** The panel works in dark and light themes, the theme is switched from the interface, and the choice survives a page reload.
- [x] **AC-42.** The panel frame stays usable at widths from 400 px: on a narrow screen navigation moves to a bottom bar with labels, and the panel root opens the overview, tables with fixed columns scroll horizontally together with the header, there is no horizontal overflow of the page itself.
- [x] **AC-43.** The panel speaks Russian and English. On the first visit the language is taken from the browser, then from the saved choice; it is switched from the interface and survives a reload. The document language is declared by the `lang` attribute and follows the choice. A screen's text arrives together with the screen itself: the user does not see keys instead of words. How texts are organized — [ADR-0019](./adr/ADR-0019-keep-interface-texts-in-the-slice-and-load-them-over-the-network.md). A daemon failure reaches the screen in the chosen language too: every error the daemon API returns carries a stable code, the panel takes the text by the code, and the daemon's own English text is only a fallback for an unknown code and a detail under the translated cause ([ADR-0022](./adr/ADR-0022-report-the-apply-failure-step-as-a-code.md)).

### Route explanation

- [x] **AC-34.** Each statement in the route explanation carries its origin — `observed`, `computed` or `unknown` — and the API returns no statements without it. The matched rule is linked to the `route.rules` node of the applied config by its index; a condition whose reason for not matching cannot be computed is marked `unknown`, not replaced with a guess. ### Dataplane

- [x] **AC-48.** sing-box is started by a service from the metabox package: a procd instance with `-c` and `-D` pointing to the config directory, an open files limit and `respawn` as in homeproxy. The daemon manages it without the `-init-script` flag; start order is dnsmasq, fw4, the sing-box service, metaboxd, so that the replay of the transaction on start does not touch the service before the network is up. Verified on the test bench; on the router — after the switch (AC-67).
- [x] **AC-49.** LAN traffic interception repeats the homeproxy `redirect_tproxy` mode: TCP via redirect, UDP via tproxy to the ports of the dataplane model. ACL mode is `all` or `listed`; in `listed` only the listed sources go through sing-box, the rest go direct. A source is set by an IP address or subnet, as in homeproxy, or by a MAC address: a MAC does not depend on DHCP lease changes, while sing-box route rules still need an IP (AC-62). The router's own traffic is intercepted by the same chains, traffic with the bypass mark goes around, private and service destinations are not intercepted.
- [x] **AC-50.** DNS: udp/53 from LAN is intercepted to dnsmasq, dnsmasq forwards queries to sing-box `dns-in`. The upstream is set by a fragment in the dnsmasq conf-dir, which the service puts in place on start and removes on stop; UCI `dhcp` is not edited (OQ-19). Applying the JSON config does not restart dnsmasq and does not reload fw4; dnsmasq is restarted only when the dataplane DNS settings change, and exactly once.
- [x] **AC-51.** nft rules, `ip rule`/`ip route` and the dnsmasq upstream are set up and removed by the init script of the sing-box service, not by the daemon: the dataplane survives a router reboot without metaboxd, `stop` removes it when the daemon is dead, after `stop` there are no traces of metabox in `nft list ruleset` and `ip rule`. The daemon is the editor of the dataplane model in UCI and the initiator of the service `reload`. Decision — [ADR-0047](./adr/ADR-0047-set-up-lan-interception-in-the-singbox-init-script.md).
- [x] **AC-52.** Fail-closed, as in homeproxy: when sing-box crashes, interception and the dnsmasq upstream stay in place, traffic of listed devices and network DNS do not bypass the proxy. The same on restart and config reload: interception and upstream are not removed while sing-box comes up, so there is no window in which traffic or DNS would go direct; only an explicit service stop removes them. The process is brought up by procd `respawn`; while it is down, the panel shows the crash and its reason (AC-27, AC-55). Fail-open rejected by the owner on 2026-10-09 (OQ-16).
- [x] **AC-53.** Changing ACL and dataplane DNS settings goes through the same protocol as Apply of the config: model check, UCI write, service `reload`, confirmation window, automatic rollback to the previous model. An unconfirmed ACL change does not cut off the administrator's device for longer than the window.
- [x] **AC-54.** The healthcheck after a restart is not limited to polling the Clash API: it checks a DNS probe through `dns-in`, that interception is present and that the process pid is new. A config with a broken `dns` section is rolled back. The DNS probe also runs before the restart against the running config: when it already fails there, the apply did not break DNS and a rollback would not repair it, so the check after the restart is skipped with a warning and the apply relies on the confirmation window ([ADR-0061](./adr/ADR-0061-skip-the-dns-check-when-dns-already-failed-before-the-restart.md)).
- [x] **AC-55.** The sing-box crash reason is read also when `log.output` points to a file, not only from `logread`.
- [x] **AC-56.** The state of a service with several procd instances is determined by the sing-box instance, not by the first live one; a state read error carries a code per [ADR-0022](./adr/ADR-0022-report-the-apply-failure-step-as-a-code.md), and the panel translates it.
- [x] **AC-57.** The dataplane coexists with b4: both nft tables are in place, a flow marked by b4 does not go into tproxy. Checked on the test bench with fw4 and repeated on the router in the first day after the switch.

### Logs and operation without SSH

- [x] **AC-63.** The log screen shows the tail of the sing-box log as a stream, filters by level and clears the log; rotation is done by the service, not by a separate script.
- [x] **AC-64.** The `providers` subscription is updated from the panel manually via the Clash API. For a `remote` rule set the fork's Clash API has no endpoint: in `v1.14.1-extended-2.7.2` `PUT /providers/rules/{name}` is a stub returning 404 (`experimental/clashapi/ruleprovider.go`), so rule sets are updated by sing-box's own `update_interval` or by a service restart.
- [x] **AC-65.** Deleting a rule or a rule set requires confirmation or is cancelled.
- [x] **AC-66.** Secrets in forms — subscription URLs and the Clash API `secret` — are shown masked and revealed by a button; the full value goes into the diff. Done for node forms on 2026-10-09 (`secret`, `password`, `private_key`, `pre_shared_key`, `psk`, `token`, `auth_str`, `access_key_secret`; for `url` and `download_url` everything after the host is hidden). On 2026-10-19: the `experimental` section opens as a form, so `experimental.clash_api.secret` is masked too; a field that the form shows as JSON text and that holds a secret key at any depth is shown masked and read-only until revealed. Not masked by design: the JSON tab of a node and the whole-config text screen show values as they are — text there is edited in place, and a mask would not be a value. On 2026-10-20 the list grew by `uuid` (for vless and vmess it is the credential itself), `key` (every such key in the fork schema is key material: TLS, ECH, OpenVPN, VPN users), `auth_key`, `api_token`, `api_key`, `mac_key` and the `Authorization` and `Proxy-Authorization` headers; a key matches in any case, and a secret given as a list or an object is masked in every string inside it. The daemon masks MCP results by the same list (AC-73).
- [x] **AC-67.** Migration from homeproxy is described by a switch and rollback runbook and run on the test bench; steps that touch homeproxy cannot be run on the test bench, they are repeated on the router during the switch. The package installs while homeproxy is running, without touching its dataplane and ports, while the metabox sing-box service is disabled. If the "Devices" screen (AC-61) is not ready by the switch, the ACL source list is moved from homeproxy by editing UCI over SSH — acceptable temporarily (OQ-17).
- [x] **AC-68.** Dataplane diagnostics: port listeners, a DNS probe through `dns-in`, presence of nft chains, internet access through the selected node. With interception removed, diagnostics names the missing chain, with sing-box stopped — the closed port. The owner uses LuCI diagnostics, so the screen is needed before the switch (OQ-23, 2026-10-09).
- [ ] **AC-69.** The panel can be protected by a password. The password is optional and not set by default: without it the panel is open as before. It is set, changed and removed in the panel and reset over SSH. With a password set, a request without a session gets 401, except the daemon health check, the login endpoints and the panel static files; five wrong passwords from one address within 15 minutes lock that address for 5 minutes. A mutating request from a foreign origin gets 403 with or without a password (AC-19). Done after the router switches to metabox (OQ-14, 2026-10-09); decision in [ADR-0052](./adr/ADR-0052-protect-the-panel-with-an-optional-password-and-a-cookie-session.md).
- [ ] **AC-74.** With `option https '1'` in UCI `metabox` the panel and the MCP endpoint are served over HTTPS on the same address and port as plain http. By default HTTPS is off: a root of the daemon's own has to be installed on every device before the browser trusts the panel, which a new user does not do. The daemon issues a root certificate once and keeps it in its state directory; the server certificate is issued under that root for the listen addresses, `localhost` and the host from `-allowed-origin`, and is reissued before expiry and when the addresses change, without a new root. The root is served at `/metabox-ca.crt` for installing on the owner's devices; its name constraints admit only the panel addresses and private networks. A plain http request to the panel port gets a redirect to `https://` on the same address, except the health check and the root certificate file; the session cookie of AC-69 carries `Secure`. With `option https '0'`, the default, the daemon serves plain http; `https_cert` and `https_key` make it serve a certificate pair the owner already has instead of its own root, and the root file is then not served. Decision in [ADR-0056](./adr/ADR-0056-serve-the-panel-over-https-with-a-root-the-daemon-issues.md).

### MCP server

- [x] **AC-71.** The daemon serves an MCP endpoint for agents (Claude Code and other MCP clients) on the same address as the panel. It is off by default: while it is off, the endpoint answers as an unknown path. It is enabled and disabled in the panel; enabling generates an access token that is shown once and can be regenerated, which invalidates the old one. A request without the token or with a wrong one gets 401, a request with a foreign `Origin` gets 403, the `Host` check of AC-19 applies; a request without `Origin` is accepted, because the token cannot be sent by a foreign page. The token does not depend on the panel password (AC-69): it works with or without one, the panel session does not open the endpoint and the token does not open the panel API. MCP is disabled over SSH without reinstalling the package; turning it on or off and changing the token restart neither sing-box nor the daemon.
- [x] **AC-72.** Phase 1 is read-only. The agent gets tools for: sing-box service and daemon state with versions and the routing mode; the route explanation of AC-34 for a domain, from live connections to it, and an explicit "no connection" answer instead of a guess; connections with a filter by host, device, rule, chain and network; proxy groups, nodes and their last known latency, without running a latency check; config version history; the tail of the sing-box log with a level filter; the dataplane diagnostics of AC-68. Every tool is marked read-only for the client. A tool that writes is not offered at all to a token without a write permission, and the status tool names the permissions the agent has.
- [x] **AC-73.** Secrets in tool results are masked by the rules of AC-66, with no way to reveal them through MCP. Each tool call leaves one line in the daemon log with the tool, the client address, the duration and the error reason, without the arguments; a failure inside a tool returns an error to the agent and does not stop the daemon. Decision in [ADR-0055](./adr/ADR-0055-embed-a-read-only-mcp-server-in-the-daemon-with-the-official-go-sdk.md).

## 7. Interface principles

| ID   | Principle                                                         | Consequence                                                                                                                                                    |
| ---- | ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |

## 8. Non-Goals (v1)

- Multi-user access and roles.
- Access to the panel from the internet.
- LuCI integration.
- Downloading and parsing `geosite.dat`/`geoip.dat` on the device.
- Builds for mips/mipsel and optimization for 8–16 MB of flash.
- Support for upstream sing-box as a separate compatibility target.
- Managing several routers from one panel.
- **Forms for the `services` section.** The fork's service types (`manager`, `manager-api`, `node`, `node-manager-api`, `admin-panel`, `ssm-api`, `ccm`, `ocm`, `derp`, `resolved`, `oom-killer`, `profiler`, `usbip-client`, `usbip-server`) belong to server, multi-tenant or non-VPN scenarios. They are parsed and preserved on round-trip by the general AC-3/AC-25 rule and shown as raw blocks; there will be no handwritten forms for them. The type checklist in AC-5 covers only inbound/outbound. The exception is the `api` type that appeared in 1.14: it belongs to the panel's own scenario, a form for it is needed ([ADR-0006](./adr/ADR-0006-read-runtime-from-clash-api-and-optional-grpc.md)), and the section itself is added only on an explicit user action (AC-33).
- **A dashboard mode without Clash API.** The data source is guaranteed by the daemon (AC-31); there is no "enable clash_api" placeholder screen and no toggle in settings. The only degenerate state is a stopped sing-box (AC-27).
- **Complete reverse parsing of manually edited JSON into forms.** Manual JSON editing is a declared feature (US-8, AC-23…AC-24), but the requirement "any manually entered config is fully laid out into forms" is reached iteratively: in v1 what is recognized is shown as forms, the rest as raw blocks.

## 9. Constraints

- Schema — only sing-box-extended (the shtorm-7 fork); upstream configs are valid as a subset.
- Daemon and frontend contracts do not assume that the managed runtime is always sing-box-extended: the core type, variant and version arrive as data, not hardcoded into types and endpoint names. This is a constraint on the shape of contracts, not permission to add a second core in v1 — it stays outside section 8.
- Target OS — OpenWrt; service management only via procd/init.d.
- Target build architecture for v1 — aarch64.
- A single delivery artifact — a Go binary with embedded static assets; an apk package. The target device runs OpenWrt SNAPSHOT with apk 3.0.5 and does not accept ipk; the ipk format is not built in v1.
- Web stack: React, TypeScript, Vite, oxlint, oxfmt; TanStack Router / Query / Table / Virtual; Zustand; React Hook Form; Zod (generated, version pinned exactly); shadcn/ui + Tailwind. Details and rationale — [ADR-0045](./adr/ADR-0045-split-document-and-server-state-and-keep-a-folder-per-project.md).
- Build order is set by the Makefile, `go:embed` takes `apps/web/dist`. The pnpm workspace is needed for shared devDependencies and uniform tool versions.
- The daemon listens only on the LAN interface.
- Development happens in a `.devcontainer` that brings up the frontend, backend and target environment.
- Working with JSON is the user's choice, not a condition for completing a task.

### Roadmap after v1

1. **Second core** — first upstream sing-box as a separate compatibility target, then Xray. Each core gets its own schema, validator, service adapter and a public capability table; a common "averaged" config schema is not introduced. It starts with an ADR on the adapter boundary, not with code.
2. **History breakdowns by source.** Traffic history deeper than a minute is in the daemon (AC-37, [ADR-0015](./adr/ADR-0015-keep-traffic-history-in-the-daemon.md)). The official dashboard and metacubexd also break it down by device, host, proxy and process — this requires writing the connection snapshot into history, and it has up to 5000 records per second (NFR-2).
3. **Network diagnostics** — channel quality check and a STUN test, as a separate screen. Taken from the tools of the built-in sing-box dashboard.
4. LuCI integration.
5. Local dat pipeline as an option (downloading geosite/geoip, category tree).
6. Support for weak hardware and mips — if the community asks for it.
7. Secure external access.
8. **Interception mode during a sing-box restart.** Only fail-closed exists (AC-52). The option "let traffic go direct while the core comes up" means removing and restoring the fw4 include and the dnsmasq fragment on every restart, with two dnsmasq restarts; deferred on 2026-10-09 as a second path in the init script that does not break the dataplane model.
9. **Write through MCP** (phase 2 after AC-71…AC-73). An edit goes to the draft by an allow-list of config paths, so a new field is closed to the agent until opened explicitly; closed are the dataplane and the ACL, the panel address and port, `experimental.clash_api`, the MCP settings and secrets. The agent gets the diff and the value read back, applying goes through Apply with the confirmation window, undo is a rollback to a version from history. A write is refused if the draft or the applied version changed since the agent read it. Write tools exist only for a token with a write permission. It starts with an ADR and a security review.
