## 1. Product overview and problem statement

### 1.1. Problem

Without a dedicated panel, sing-box on OpenWrt is managed over SSH: editing `config.json` in an editor, `sing-box check`, restarting the service, manual rollback if the connection drops.

Two tasks come up most often, and the cycle serves them poorly:

1. **Editing routing rules** — "this domain bypasses the proxy", "this device goes through outbound X". A one-line change requires the full SSH → editor → check → restart cycle.
2. **Diagnosing "why it doesn't work"** — to see which rule matched, live connections must be matched against the config and logs by hand.

The cost of a mistake is asymmetric: a bad routing edit cuts off access both to the internet and to the router itself.

### 1.2. Product

**metabox** is a web panel for a router that combines two things that today live in separate tools:

1. **graphical creation and editing of the sing-box-extended configuration** — so that working with JSON is a choice, not a necessity;
2. **runtime monitoring and control** of the proxy in the spirit of Clash API dashboards (written independently, not a fork).

It ships as a single Go daemon with an embedded web interface, installed on the router. Today it works with OpenWrt and the sing-box-extended core; other cores and platforms are roadmap items 1 and 10.

Product formula: **one place where you can see what the router does with traffic, and change it**. For a newcomer — a direct answer to "why it doesn't work"; for someone who knows the schema — the full native config without SSH. Both entries lead to the same data: the connections screen explains the route and opens the matched rule, the editor and raw mode give full control over the document.

### 1.3. Difference from analogs

Checked against the projects' READMEs as of 2026-10-13, not verified on a device.

| Project                | What is claimed                                                                                                                                             | How it differs from metabox                                |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| Clash API dashboards   | Clash API dashboard, profile editor with a check before activation                                                                                          | mihomo core, not sing-box                                  |
| LuCI apps for sing-box | LuCI apps: JSON editing, templates, forms for part of the settings, dashboard; one of them checks and rolls back on profile activation                      | the "connection → rule → config node" chain is not claimed |
| **metabox**            | **forms built from the sing-box-extended schema for supported nodes, raw JSON on any node, dashboard, rule sets, route explanation from a live connection** | —                                                          |

A form editor is reproducible and is not an advantage by itself. The difference rests on what none of the projects above claims: the "live connection → matched rule → config node" chain and safe application of an edit. How this is built on observable core data — [ADR-0007](./adr/ADR-0007-explain-route-without-own-rule-evaluator.md).

## 2. Personas and user scenarios

### 2.1. Personas

**P1. Router owner — the main v1 persona.** The project author, BPI-R4 Pro. Knows the sing-box schema and edits the config by hand. Working with JSON is acceptable but not required. The problem is the maintenance cycle, not the complexity of sing-box.

**P2. Advanced OpenWrt user — a secondary persona that appears with the open-source release.** Installs packages and reads documentation, does not know the sing-box schema. A GUI is a condition of use for them. Does not affect v1 acceptance, but decisions must not close off their scenario.

**Working setting.** The panel is opened from a desktop, usually next to an ssh session to the router: rules are edited, the config is edited and applied there. From a phone, people look at the overview and connections and switch the node — this is the diagnostic entry. Editing the config and Apply from a phone are not a target scenario, but the panel frame must stay usable from 400 px (AC-42).

## 3. Goal and success metrics

### 3.1. Goal

Let the owner of an OpenWrt router fully manage sing-box-extended from a browser: build a configuration of any complexity the fork supports in a graphical interface, apply it safely to the device with a rollback guarantee, connect the needed routing rule sets and watch the result in real time — without connecting over SSH.

metabox must also correctly accept configurations written by hand or generated by other tools: parse them, show them in the UI, allow editing and save them.

### 3.2. Success metrics

Metrics measure the product, the acceptance criteria in section 5 measure release readiness.

| ID   | Metric                                        | Target value                                                                                             | How it is measured                  |
| ---- | --------------------------------------------- | -------------------------------------------------------------------------------------------------------- | ----------------------------------- |
| SM-1 | Time of a typical routing edit                | ≤ 1 minute from opening the UI to an applied config                                                      | Measured on a live US-1 scenario    |
| SM-2 | Time to diagnose "traffic went the wrong way" | ≤ 2 minutes, without reading the config and logs over SSH                                                | Measured on a live US-2 scenario    |
| SM-3 | SSH connections for the sake of the config    | 0 per month of operation                                                                                 | Owner's log                         |
| SM-4 | Apply reliability                             | 0 cases of lost access that required SSH or a physical reset                                             | Operations log                      |
| SM-5 | Round-trip integrity                          | 100% of configs from the test corpus load and save without data loss and without false validation errors | Automated test on the config corpus |

SM-1 and SM-2 cover the two tasks from §1.1, SM-3…SM-5 cover preservation of access and data.

## 7. Interface principles

| ID   | Principle                                                         | Consequence                                                                                                                                                    |
| ---- | ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| UX-1 | GUI is the main path, JSON is an equal alternative                | Forms cover the schema by the type checklist; raw mode is available on any node; there is a separate mode for editing the whole config as text                 |
| UX-2 | Saving and applying are different actions                         | An edit goes into the draft as it is made, an incomplete state included; Apply sends the config to the device and requires a successful `sing-box check`       |
| UX-3 | User data is never lost                                           | An unrecognized node is preserved as is and shown as a raw block with a mark, not thrown away and not silently "fixed"                                         |
| UX-4 | The judge of validity is `sing-box check`, not the metabox schema | The schema serves forms and hints, but has no right to forbid what the binary accepts; otherwise metabox becomes a brake on every fork release                 |
| UX-5 | An error is specific                                              | A message about an invalid value points to the specific node and reason, not "the config is invalid"                                                           |
| UX-6 | Before applying, it is visible what exactly is applied            | Apply shows the diff between the active config and the one that will be written                                                                                |
| UX-7 | System state is always in view                                    | Service status, binary version, presence of an unsaved draft and a schema mismatch warning are visible without going to a separate screen                      |
| UX-8 | Observation and computation are distinguishable                   | Data from the core, what metabox computed itself and what cannot be computed are marked differently (AC-34); a prediction is not presented as a confirmed fact |

## 8. Non-Goals (v1)

- Multi-user access and roles.
- Access to the panel from the internet. The single exception is the port of an entry server opened by the AC-85 toggle; the panel itself is never exposed.
- LuCI integration.
- Downloading and parsing `geosite.dat`/`geoip.dat` on the device.
- Builds for mips/mipsel and optimization for 8–16 MB of flash.
- Support for upstream sing-box as a separate compatibility target in v1; after v1 it follows roadmap item 1.
- Editing DHCP pools, dnsmasq options and IPv6 (`odhcpd`) from the panel: only the `host` sections of AC-80 are written, the rest stays in LuCI or UCI.
- Managing several routers from one panel.
- **Forms for the `services` section.** The fork's service types (`manager`, `manager-api`, `node`, `node-manager-api`, `admin-panel`, `ssm-api`, `ccm`, `ocm`, `derp`, `resolved`, `oom-killer`, `profiler`, `usbip-client`, `usbip-server`) belong to server, multi-tenant or non-VPN scenarios. They are parsed and preserved on round-trip by the general AC-3/AC-25 rule and shown as raw blocks; there will be no handwritten forms for them. The type checklist in AC-5 covers only inbound/outbound. The exception is the `api` type that appeared in 1.14: it belongs to the panel's own scenario, a form for it is needed ([ADR-0006](./adr/ADR-0006-read-runtime-from-clash-api-and-optional-grpc.md)), and the section itself is added only on an explicit user action (AC-33).
- **A dashboard mode without Clash API.** The data source is guaranteed by the daemon (AC-31); there is no "enable clash_api" placeholder screen and no toggle in settings. The only degenerate state is a stopped sing-box (AC-27).
- **Complete reverse parsing of manually edited JSON into forms.** Manual JSON editing is a declared feature (US-8, AC-23…AC-24), but the requirement "any manually entered config is fully laid out into forms" is reached iteratively: in v1 what is recognized is shown as forms, the rest as raw blocks.

## 9. Constraints

- Schema — only sing-box-extended (the shtorm-7 fork); upstream configs are valid as a subset.
- Daemon and frontend contracts do not assume that the managed runtime is always sing-box-extended: the core type, variant and version arrive as data, not hardcoded into types and endpoint names. This is a constraint on the shape of contracts, not permission to add a second core in v1 — it stays outside section 8.
- Target OS for v1 — OpenWrt; service management only via procd/init.d. Other platforms come after the platform layer of roadmap item 10, Docker without a dataplane first.
- Target build architecture for v1 — aarch64.
- A single delivery artifact — a Go binary with embedded static assets; an apk package. The target device runs OpenWrt SNAPSHOT with apk 3.0.5 and does not accept ipk; the ipk format is not built in v1.
- Web stack: React, TypeScript, Vite, oxlint, oxfmt; TanStack Router / Query / Table / Virtual; Zustand; React Hook Form; Zod (generated, version pinned exactly); shadcn/ui + Tailwind. Details and rationale — [ADR-0045](./adr/ADR-0045-split-document-and-server-state-and-keep-a-folder-per-project.md).
- Build order is set by the Makefile, `go:embed` takes `apps/web/dist`. The pnpm workspace is needed for shared devDependencies and uniform tool versions.
- The daemon listens only on the LAN interface. On a platform without a dataplane (Docker, a server) the password of AC-69 is mandatory and cannot be removed from the panel.
- Development happens in a `.devcontainer` that brings up the frontend, backend and target environment.
- Working with JSON is the user's choice, not a condition for completing a task.

### Roadmap after v1

1. **Second core** — in this order: the adapter boundary (service, check, runtime source, version and installation source of a core) and a public capability table in the contract; then upstream sing-box as a separate compatibility target; then Xray, which has no Clash API and needs its own schema generator and runtime source. Each core gets its own schema, validator and service adapter; a common "averaged" config schema is not introduced. The boundary is designed together with item 10: the core adapter and the platform adapter share the daemon's `apply` and `diag` interfaces. The ADR is written with the implementation, not before it. Until then the wizard's core step (AC-78) offers one core.
2. **History breakdowns by source.** Traffic history deeper than a minute is in the daemon (AC-37, [ADR-0015](./adr/ADR-0015-keep-traffic-history-in-the-daemon.md)). Clash API dashboards commonly break it down by device, host, proxy and process — this requires writing the connection snapshot into history, and it has up to 5000 records per second (NFR-2).
3. **Network diagnostics** — channel quality check and a STUN test, as a separate screen. Taken from the tools of the built-in sing-box dashboard. The screen also shows the external address and country seen through each outbound and directly: split routing exposes both addresses to any site that asks for them. A DNS check states what it proves: the router resolver, test queries seen on WAN and an independent DoH request, each with the interface and path tested; it also looks for the dataplane gaps — the DoH canary domain `use-application-dns.net`, the iCloud Private Relay domain `mask.icloud.com`, device DNS to foreign servers on 53 and 853, IPv6 around interception while the model has `ipv6` off. An incomplete observation is `unknown`, not "no leaks".
4. LuCI integration.
5. Local dat pipeline as an option (downloading geosite/geoip, category tree).
6. Support for weak hardware and mips — if the community asks for it.
7. Secure external access.
8. **Interception mode during a sing-box restart.** Only fail-closed exists (AC-52). The option "let traffic go direct while the core comes up" means removing and restoring the fw4 include and the dnsmasq fragment on every restart, with two dnsmasq restarts; deferred on 2026-10-09 as a second path in the init script that does not break the dataplane model.
9. **Write through MCP** (phase 2 after AC-71…AC-73). An edit goes to the draft by an allow-list of config paths, so a new field is closed to the agent until opened explicitly; closed are the dataplane and the ACL, the panel address and port, `experimental.clash_api`, the MCP settings and secrets. The agent gets the diff and the value read back, applying goes through Apply with the confirmation window, undo is a rollback to a version from history. A write is refused if the draft or the applied version changed since the agent read it. Write tools exist only for a token with a write permission. It starts with an ADR and a security review.
10. **Platforms other than OpenWrt.** A platform layer in the daemon: service control, firewall, DNS, DHCP, paths, package manager; the OpenWrt implementation is what exists today. The first non-router target is Docker without a dataplane — the panel and the core in one container, no interception, the password mandatory; this is also the server mode for a VPS and the upstream side of a cascade built from an entry server (AC-83). Generic Linux with interception (systemd, nftables) comes after it and needs its own test bench in CI. Decided 2026-10-24 together with item 1.
11. **Routing warnings in the editor**, next to the config like the build warning of AC-47, without blocking Apply: a rule that never matches because a rule above covers it, computed for domain, domain suffix, address and device conditions and `unknown` for the contents of a remote rule set (AC-34); a rule whose outbound group contains `direct`, so its traffic goes direct when the nodes fail; a DNS rule with an `ip_cidr` rule set, which sends every name to that server; QUIC without `reject` before a proxy rule; no direct rule for NTP.
12. **A rule from observation.** From a connection: put its host into a rule or a custom list (AC-8) in the draft and offer the other hosts of the same device in the same minute as candidates, since a site that opens halfway usually needs its API, CDN or sign-in domains too. From repeated reachability checks: when a target fails directly and opens through a chosen proxy, offer a domain rule in the draft with the evidence; a DNS or certificate error is not taken as a routing problem. Nothing is added silently and nothing overwrites a changed draft; the edit goes through the summary and Apply.
13. **Watchdog in steady state**, opt-in. Probes do not depend on DNS: the provider through WAN, the tunnel through a proxy with an exit country other than the router's, the interception chains, the nodes through Clash API; a probe to a site that also opens directly does not count. The inferred cause is shown apart from the observations — WAN down, proxy path down, target down only directly — and a missing probe is `unknown`. Actions go in steps after repeated failures, with a cooldown and a rate limit, under the Apply lock: move a group off a dead node, refresh the subscription, restart the core. A version that worked is marked in history, and the watchdog rolls back to it. An availability strip shows a day or a week of tunnel and provider state. Fail-closed (AC-52) stays, and a WAN outage does not restart the core. Starts with an ADR.
14. **Notifications outside the panel.** A Telegram bot sends through the tunnel, then through WAN, then queues; commands come from one chat only, a restart only by a confirmation button, the token and permissions follow the MCP model. An external heartbeat: a request to a configured address every few minutes around the tunnel, so that the receiving service notices a dead router.
15. **Diagnostic bundle**, downloaded on request: panel, core and schema versions, service state, diagnostics results, routes, nftables state and a bounded log tail. Secrets in the config and logs are masked, and the user sees the contents before the download.
16. **Entries by task** for persona P2. The overview and empty states offer tasks instead of config sections: add a VPN from a share link (creates an outbound and offers a rule), a device through VPN, a site around the proxy, a site directly, "why does it not open". Each task leads to a ready form; the config sections stay for those who know the schema. The first-config step of the wizard (AC-78) offers a starter routing layout built from catalog categories (AC-7), not from lists of our own. A user scenario and criteria next to US-13 are written when the item is taken.
17. **Network topology.** A screen with the tree "client → rule → node → outside" built from the connection snapshot and the route explanation: the connection count on a node, edge width by it, collapsed clients, a pause. It needs a graph layout dependency, chosen together with the item.
