## 1. Обзор продукта и постановка проблемы

### 1.1. Проблема

Единственный способ управлять sing-box на OpenWrt — SSH: правка `config.json` в редакторе, `sing-box check`, рестарт сервиса, ручной откат, если связь отвалилась.

Две задачи возникают чаще всего, и цикл обслуживает их плохо:

1. **Правка правил маршрутизации** — «этот домен мимо прокси», «это устройство через выход X». Изменение на одну строку требует полного цикла SSH → редактор → check → restart.
2. **Диагностика «почему не работает»** — чтобы понять, какое правило сработало, нужно сопоставлять живые соединения с конфигом и логами вручную.

Цена ошибки асимметрична: неудачная правка маршрутизации отрезает доступ и к интернету, и к самому роутеру.

### 1.2. Продукт

**metabox** — веб-панель для OpenWrt, объединяющая две вещи, которые сегодня разнесены по разным инструментам:

1. **графическое создание и редактирование конфигурации sing-box-extended** — так, чтобы работа с JSON была выбором, а не необходимостью;
2. **рантайм-мониторинг и управление** прокси в духе MetaCubeXD (переписанный самостоятельно, не форк).

Поставляется как единый Go-демон со встроенным веб-интерфейсом, устанавливаемый на роутер.

### 1.3. Отличие от аналогов

| Проект                   | Что делает                                                            | Чего не делает                                 |
| ------------------------ | --------------------------------------------------------------------- | ---------------------------------------------- |
| MetaCubeXD               | дашборд Clash API для mihomo                                          | не редактирует конфиг, не про sing-box         |
| b4 (daniellavrushin)     | GUI обхода DPI, свои sets, geodat                                     | своя модель, не sing-box                       |
| LuCI-пакеты для sing-box | базовая настройка через uci                                           | нет полноценного редактора схемы, нет дашборда |
| **metabox**              | **полное GUI-покрытие схемы sing-box-extended + дашборд + rule-sets** | —                                              |

## 2. Персоны и пользовательские сценарии

### 2.1. Персоны

**P1. Владелец роутера — основная персона v1.** Автор проекта, BPI-R4 Pro. Знает схему sing-box и правит конфиг руками. Работа с JSON допустима, но не обязательна. Проблема — цикл обслуживания, а не сложность sing-box.

**P2. Продвинутый пользователь OpenWrt — вторичная персона, появляется при выходе в опенсорс.** Ставит пакеты и читает документацию, схему sing-box не знает. GUI для него — условие использования. На приёмку v1 не влияет, но решения не должны закрывать его сценарий.

## 3. Цель и метрики успеха

### 3.1. Цель

Дать владельцу OpenWrt-роутера возможность полностью управлять sing-box-extended из браузера: собрать конфигурацию любой поддерживаемой форком сложности в графическом интерфейсе, безопасно применить её на устройство с гарантией отката, подключить нужные наборы правил маршрутизации и наблюдать за результатом в реальном времени — не подключаясь по SSH.

При этом metabox обязан корректно принимать конфигурации, написанные вручную или сгенерированные другими инструментами: распарсить, показать в UI, дать отредактировать и сохранить.

### 3.2. Метрики успеха

Метрики измеряют продукт, критерии приёмки раздела 5 — готовность релиза.

| ID   | Метрика                                  | Целевое значение                                                                                             | Как измеряется               |
| ---- | ---------------------------------------- | ------------------------------------------------------------------------------------------------------------ | ---------------------------- |
| SM-1 | Время типовой правки маршрутизации       | ≤ 1 минуты от открытия UI до применённого конфига                                                            | Замер на живом сценарии US-1 |
| SM-2 | Время диагностики «трафик пошёл не туда» | ≤ 2 минут, без чтения конфига и логов через SSH                                                              | Замер на живом сценарии US-2 |
| SM-3 | Подключения по SSH ради конфига          | 0 за месяц эксплуатации                                                                                      | Журнал владельца             |
| SM-4 | Надёжность применения                    | 0 случаев потери доступа, потребовавших SSH или физического сброса                                           | Журнал эксплуатации          |
| SM-5 | Целостность round-trip                   | 100% конфигов из тестового корпуса загружаются и сохраняются без потери данных и без ложных ошибок валидации | Автотест на корпусе конфигов |

SM-1 и SM-2 закрывают две задачи из §1.1, SM-3…SM-5 — сохранность доступа и данных.

## 5. Функциональные требования (критерии приёмки)

### Config Editor

- [ ] **AC-1.** Рукописный `config.json` с реального роутера загружается, парсится и отображается в UI без ошибок.
- [ ] **AC-2.** После загрузки чужого конфига, изменения одного поля и сохранения диф с исходным файлом содержит только это изменение — ничего не потеряно и не переупорядочено произвольно. Единственное допустимое отличие сверх правок пользователя — секция `experimental.clash_api`, добавляемая по AC-31 и показываемая явно.
- [ ] **AC-3.** Конструкции, не распознанные моделью, сохраняются при round-trip и отмечаются в UI как нераспознанные.
- [ ] **AC-4.** Невалидные значения подсвечиваются в UI до попытки применения, с указанием узла и причины.
- [ ] **AC-5.** Каждый тип inbound/outbound из чеклиста форка имеет либо ручную форму, либо автогенерируемый рендерер — узлов без рендерера нет.
- [ ] **AC-6.** Конфиг, собранный в UI с нуля для сценария «VLESS/Reality + маршрутизация по правилам», проходит `sing-box check` без правок руками.

### Rule-set Manager

- [ ] **AC-7.** В UI есть каталог источников remote rule-set с поиском по категориям; выбранная категория попадает в конфиг как `remote` rule-set с корректным URL.
- [ ] **AC-8.** Пользователь может собрать кастомный список доменов/IP в UI; демон компилирует его в `.srs` и подключает как `local` rule-set.
- [ ] **AC-9.** Правило маршрутизации может ссылаться на любой подключённый rule-set, и это отражается в применённом конфиге.

### Runtime Dashboard

- [ ] **AC-10.** Overview показывает трафик up/down в реальном времени, счётчики, память и состояние сервиса.
- [ ] **AC-11.** Экран Proxies отображает группы и ноды, позволяет переключить активную ноду и запустить проверку задержки.
- [ ] **AC-12.** Экран Connections показывает живой список соединений (хост, сработавшее правило, цепочка прокси, трафик) и позволяет закрыть соединение.

### Device Integration

- [ ] **AC-13.** Apply выполняет полную последовательность из [ADR-0002](./adr/ADR-0002-apply-protocol-and-config-ownership.md); при провале `sing-box check` запись не происходит и пользователь видит ошибку от бинаря.
- [ ] **AC-14.** Заведомо ломающий связь конфиг приводит к автоматическому возврату предыдущего и восстановлению доступа без вмешательства по SSH.
- [ ] **AC-15.** История версий конфига доступна в UI; откат на любую предыдущую версию работает.
- [ ] **AC-16.** Рестарт сервиса выполняется через procd и корректно отрабатывает при уже остановленном сервисе.

### Backend / API

- [ ] **AC-17.** Демон стартует одной командой, раздаёт встроенный UI и отвечает на REST API.
- [ ] **AC-18.** Демон слушает только LAN-интерфейс; запрос с внешнего интерфейса не проходит.
- [ ] **AC-19.** Мутирующие запросы с несоответствующим `Origin`/`Host` отклоняются.

### Dev Environment

- [x] **AC-20.** `.devcontainer` одной командой поднимает фронт с HMR, Go-демон и целевое окружение с sing-box-extended.
- [x] **AC-21.** Внутри окружения выполняется полный цикл Apply, включая `sing-box check`, рестарт и healthcheck — без физического роутера.
- [ ] **AC-22.** Тот же образ целевого окружения используется в CI для интеграционных прогонов.

---

### Ручное редактирование JSON и черновики

- [ ] **AC-23.** Любой узел конфига можно открыть в raw-режиме и отредактировать как JSON; изменения возвращаются в модель без потери остальных данных.
- [ ] **AC-24.** Есть режим редактирования JSON всего конфига целиком в вебе.
- [ ] **AC-25.** Узел, который модель не распознала, отображается как сырой блок с пометкой «UI не покрывает» и сохраняется без искажений; форма по этому узлу недоступна, остальной конфиг редактируется нормально.
- [ ] **AC-26.** Save сохраняет черновик даже при наличии предупреждений; Apply отклоняется, если `sing-box check` не прошёл, и показывает вывод бинаря.

### Устойчивость и схема

- [ ] **AC-27.** При остановленном или упавшем sing-box панель открывается, показывает состояние сервиса и ошибку, позволяет отредактировать конфиг и запустить сервис.
- [ ] **AC-28.** При расхождении версии установленного бинаря со схемой, на которой собран демон, в UI отображается предупреждение об этом.
- [ ] **AC-29.** Запись конфига атомарна: прерывание процесса или питания в момент записи не оставляет повреждённый или полузаписанный файл.
- [ ] **AC-30.** Экран Connections остаётся отзывчивым на конфиге с сотнями правил и тысячах активных соединений.

### Источник данных дашборда

- [ ] **AC-31.** Демон гарантирует, что применяемый конфиг содержит работоспособный `experimental.clash_api`. Если секция отсутствует или `external_controller` пуст, демон добавляет её со значениями `127.0.0.1:<порт>` и сгенерированным `secret`. Существующие пользовательские значения не изменяются.
- [ ] **AC-32.** Добавление секции проходит обычный протокол Apply и явно показывается пользователю как изменение, инициированное metabox, с указанием причины и того, что потребуется рестарт sing-box.

## 6. Нефункциональные требования

| ID    | Требование                                      | Значение                                                                                                                                                                                                           |
| ----- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| NFR-1 | Панель не зависит от работоспособности sing-box | Демон стартует и обслуживает UI при остановленном, упавшем или неверно сконфигурированном sing-box. UI различает «сервис лежит» и «панель недоступна»                                                              |
| NFR-2 | Отзывчивость под нагрузкой                      | Конфиг до 500 правил и до 5000 активных соединений не блокируют интерфейс; поток Connections агрегируется на стороне демона, длинные списки виртуализируются; отсутствуют блокировки главного потока дольше 100 мс |
| NFR-3 | Атомарность записи                              | Конфиг пишется через временный файл с `fsync` и атомарным `rename`; повреждение файла при сбое питания исключено                                                                                                   |
| NFR-4 | Бюджет ресурсов демона                          | RSS в установившемся режиме ≤ 64 МБ, потребление CPU в простое ≤ 1% одного ядра                                                                                                                                    |
| NFR-5 | Длительность применения                         | Полный цикл Apply укладывается в 15 секунд на целевом железе; окно подтверждения до автоотката — 60 секунд                                                                                                         |

Пороги NFR-2, NFR-4 и NFR-5 — ориентиры, подлежат подтверждению замером. На BPI-R4 Pro достижимы с запасом; заданы, чтобы архитектуру не пришлось переписывать под слабое железо.

## 8. Non-Goals (v1)

- Аутентификация и многопользовательский доступ.
- Доступ к панели из интернета, HTTPS, защита от брутфорса.
- LuCI-интеграция.
- Экран логов.
- Скачивание и парсинг `geosite.dat`/`geoip.dat` на устройстве.
- Сборки под mips/mipsel и оптимизация под 8–16 МБ флеша.
- Поддержка upstream sing-box как отдельной цели совместимости.
- Управление несколькими роутерами из одной панели.
- **Формы для секции `services`.** Двенадцать service-типов форка (`manager`, `manager-api`, `node`, `node-manager-api`, `admin-panel`, `ssm-api`, `ccm`, `ocm`, `derp`, `resolved`, `oom-killer`, `profiler`) относятся к серверным, мультиарендным или не-VPN сценариям. Они парсятся и сохраняются при round-trip по общему правилу AC-3/AC-25 и показываются сырыми блоками; рукописных форм для них не будет. Чеклист типов в AC-5 покрывает только inbound/outbound.
- **Режим работы дашборда без Clash API.** Источник данных гарантируется демоном (AC-31); экрана-заглушки «включите clash_api» и тумблера в настройках нет. Единственное вырожденное состояние — остановленный sing-box (AC-27).
- **Полнота обратного разбора вручную отредактированного JSON в формы.** Ручное редактирование JSON — заявленная функция (US-8, AC-23…AC-24), но требование «любой введённый вручную конфиг полностью раскладывается в формы» набирается итерациями: в v1 распознанное показывается формами, остальное — сырыми блоками.

## 9. Constraints

- Схема — только sing-box-extended (форк shtorm-7); upstream-конфиги валидны как подмножество.
- Целевая ОС — OpenWrt; управление сервисом только через procd/init.d.

- Разработка ведётся в `.devcontainer`, поднимающем фронт, бэк и целевое окружение.
- Работа с JSON — выбор пользователя, а не условие выполнения задачи.

## Приложение A. Архитектурные решения

Решения, принятые до введения ADR. Приложение закрыто для новых записей: новое решение оформляется ADR в [`adr/`](./adr/README.md), а раздел A.* переезжает туда, когда соответствующую часть системы начинают реализовывать.

### A.1. Целевая схема — только sing-box-extended

Совместимость целится в форк [shtorm-7/sing-box-extended](https://github.com/shtorm-7/sing-box-extended) (WARP, MASQUE, MTProxy, Mieru, OpenVPN, TrustTunnel, Snell, SSH сверх upstream-протоколов). Поскольку форк является надмножеством upstream, обычные конфиги sing-box остаются валидными автоматически.

Установка sing-box-extended на OpenWrt в целевом сценарии — через [EikeiDev/OpenWRT-sing-box-extended](https://github.com/EikeiDev/OpenWRT-sing-box-extended).

### A.2. Трёхслойная модель конфига

```text
┌─────────────────────────────────────────────────────────┐
│ UI Layer                                                 │
│  ручные формы (чеклист типов) + автогенерируемый         │
│  fallback-рендерер для непокрытых узлов схемы            │
└────────────────────────┬────────────────────────────────┘
                         │  внутренняя модель metabox
┌────────────────────────┴────────────────────────────────┐
│ Adapter Layer (версионированный)                         │
│  маппинг «схема форка ↔ модель metabox»                 │
│  при ломающем изменении API правится ТОЛЬКО этот слой   │
└────────────────────────┬────────────────────────────────┘
                         │  типы + валидаторы
┌────────────────────────┴────────────────────────────────┐
│ Schema Layer                                             │
│  генерируется из sing-box-extended, обновляется          │
│  механически при релизе форка                            │
└─────────────────────────────────────────────────────────┘
```

**Обоснование (Round 5):** полное GUI-покрытие названо приоритетом, а ручные формы под всю схему протухают на каждом релизе форка. Адаптерный слой изолирует UI от изменений схемы; генерация даёт покрытие по умолчанию; ручные формы дают нормальный UX там, где он важен.

**Владение конфигом (Round 1):** гибрид. metabox владеет конфигом и генерирует его, но обязан распарсить произвольный `config.json`. Конструкции, которые модель не распознала, не теряются — сохраняются и подсвечиваются в UI как нераспознанные/невалидные.

### A.2.1. Получение схемы из форка — решение по OQ-2 (2026-08-30)

Раздел переехал в [ADR-0001](./adr/ADR-0001-generate-schema-from-fork-registries.md): описанный здесь алгоритм расходится с фактическим устройством форка, и ADR задаёт его заново.

Из решения остаётся в силе требование к форме результата: генерируемые схемы держатся представимыми для `z.toJSONSchema()`, без `.transform()`, — на этой конвертации стоит авторендерер непокрытых узлов (AC-5).

### A.3. Рантайм — Go-демон со встроенным UI

Один бинарь на устройстве:

- раздаёт собранную SPA (embed);
- REST API для конфига, рулсетов, применения;
- владеет `config.json`, историей версий и бэкапами;
- вызывает `sing-box check`, `sing-box rule-set compile`;
- управляет сервисом через procd (`/etc/init.d/sing-box`);
- проксирует Clash API sing-box для дашборда.

**Цена решения:** проект двухъязычный (Go + TypeScript), нужна кросс-компиляция под aarch64 и CI, собирающий фронт перед embed.

### A.4. Протокол Apply (Round 7)

Раздел переехал в [ADR-0002](./adr/ADR-0002-apply-protocol-and-config-ownership.md): последовательность применения задана там вместе с решениями, которых здесь не было, — представлением конфига, предметом валидации и хранением состояния транзакции.

### A.5. Rule-sets (Round 6)

- **Готовые категории** — через `remote` rule-set: в UI каталог источников и поиск по категориям, URL прописывается в конфиг, скачиванием и обновлением `.srs` занимается сам sing-box.
- **Кастомные списки** — пользователь собирает свой набор доменов/IP в UI, демон компилирует его в `.srs` локально (`sing-box rule-set compile`) и подключает как `local` rule-set.
- Скачивание и парсинг `geosite.dat`/`geoip.dat` на устройстве в v1 **не делается**.

### A.6. Модель доступа (Round 8) — осознанный риск

**Аутентификации в v1 нет.**

Риск зафиксирован явно: любое устройство в LAN (гостевой Wi-Fi, IoT, скомпрометированный клиент) получает полный контроль над маршрутизацией всей сети и может незаметно завернуть трафик через свой outbound. Отдельно — CSRF: злонамеренная веб-страница в браузере владельца способна слать запросы на адрес панели без всякого пароля.

Обязательные митигации в v1:

- bind строго на LAN-интерфейс, **не** на `0.0.0.0`;
- проверка заголовков `Origin`/`Host` на всех мутирующих запросах;
- явное предупреждение в README;
- аутентификация — первый пункт roadmap после v1.

### A.7. Целевое железо (Round 11)

**Banana Pi BPI-R4 Pro** (MediaTek MT7988A, aarch64, 8 ГБ RAM, NVMe/eMMC). Ресурсных ограничений уровня «влезет ли во флеш» нет. Единственная целевая архитектура сборки v1 — **aarch64**.

### A.8. Ручное редактирование JSON и модель Save/Apply (интервью 2, Round 4–6)

Ручное редактирование JSON — заявленная функция, а не аварийный люк: raw-режим доступен на любом узле, плюс есть режим правки всего конфига текстом. Три правила разрешают конфликт двух источников истины:

1. **Данные не теряются.** Нераспознанный узел сохраняется как есть и показывается сырым блоком с пометкой «UI не покрывает».
2. **Валидность определяет `sing-box check`,** а не схема metabox. Схема обслуживает формы и подсказки, но не запрещает то, что принимает бинарь.
3. **Save ≠ Apply.** Save сохраняет черновик всегда, с предупреждениями; Apply требует успешного `check`. Обойти вердикт бинаря нельзя — force-apply отсутствует намеренно.

Требование «вручную введённый JSON полностью раскладывается в формы» — итеративное: v1 раскладывает распознанное, полнота набирается со временем.

### A.9. Отслеживание дрейфа схемы (интервью 2, Round 7)

Два независимых механизма:

- **CI** отслеживает релизы sing-box-extended, прогоняет генератор схемы и открывает PR с диффом — изменение не может пройти незамеченным.
- **Рантайм** сравнивает версию установленного на устройстве бинаря с версией схемы, на которой собран демон, и при расхождении показывает предупреждение в UI (AC-28).

### A.10. Стек фронтенда и структура репозитория — решение по OQ-1 (2026-08-30)

Определяющий факт: в приложении **два состояния с разными требованиями**, и их нельзя накрывать одним инструментом.

- **Документ конфига** — один большой вложенный JSON. Клиентский, живёт между экранами, требует dirty-tracking, черновика отдельно от применённого (UX-2), дифа перед Apply (UX-6), истории, адресации по строковому пути (авторендерер строит поля из схемы в рантайме) и сырых блоков внутри дерева (UX-3).
- **Рантайм-данные дашборда** — server state: эфемерный, высокочастотный, до 5000 соединений (NFR-2).

| Слой                | Решение                                 | Обоснование                                                                                                        |
| ------------------- | --------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Состояние документа | Zustand + immer                         | Документ — не форма; черновик, история и диф пишутся явно, без submit-семантики                                    |
| Server state        | TanStack Query, только запрос-ответ     | WebSocket-потоки (трафик, соединения) идут мимо Query в отдельный стор; Query поверх потока даёт кэш, который врёт |
| Роутинг             | TanStack Router, code-based             | Экранов шесть, file-based плагин избыточен; типизированные search params держат фильтры Connections в URL          |
| Таблицы и списки    | TanStack Table + TanStack Virtual       | Требование виртуализации из NFR-2                                                                                  |
| Формы               | React Hook Form + `@hookform/resolvers` | Неконтролируемый — меньше ререндеров на конфиге в 500 правил                                                       |
| Валидация           | Zod (генерируется, см. A.2.1)           | Единый источник со схемой                                                                                          |
| UI                  | shadcn/ui + Tailwind                    | Авторендерер собирает поля программно, ему нужны примитивы без чужой темизации сверху                              |

**Ограничения RHF, влияющие на реализацию.** Имена полей — только точечная нотация (`outbounds.2.uuid`), скобки не поддерживаются; авторендерер печатает пути точками. Формы типизируются против типа **узла** (`VLESSOutboundOptions`), а не против типа всего конфига: `Path<T>` по union на 57 веток разложит компилятор. Именно решение держать документ в Zustand и открывать форму на узле снимает этот риск. Для авторендерера типобезопасности путей нет ни в одной библиотеке — там строка и приведение типа.

**Монорепо-тулинг не берём.** Артефакта два (SPA и Go-бинарь), связь одна: `web/dist` собирается до `go build`. У Go и Vite свои кэши, третий слой поверх них избыточен. Отдельно проверено: `@nx-go/nx-go` (4.1.1) объявляет peer `@nx/devkit >= 20 < 23` при текущем Nx 23.x, то есть отстаёт на мажор. Порядок сборки выражается Makefile'ом. Пересмотреть — если из роадмапа приедет второй фронт под LuCI плюс общая UI-библиотека. Сам воркспейс pnpm уже заведён, но сборкой не управляет: корневой пакет держит общие devDependencies (линтеры, хуки, commitlint) и каталог версий, `web` — единственный пакет в нём.

## Приложение B. Технический контекст

**Стек, зафиксированный пользователем:** React, TypeScript, TanStack, Vite, oxlint, oxfmt. Остальное (стейт-менеджмент, UI-кит, роутинг, форма, тесты, структура проекта) — предмет отдельного согласования после утверждения PRD.

**Дополнительно следует из решений интервью:**

- Go — язык демона (кросс-компиляция под aarch64, embed статики).
- Схема и адаптеры требуют генератора: извлечение структуры из sing-box-extended → типы TS + валидаторы.
- Clash API sing-box (`experimental.clash_api`) — источник данных для дашборда; трафик и соединения идут по WebSocket.
- Multi-container devcontainer: dev-контейнер со стеком сборки + target-контейнер на OpenWrt rootfs.

**Референсы, изученные в ходе интервью:**

- [shtorm-7/sing-box-extended](https://github.com/shtorm-7/sing-box-extended) — целевой форк.
- [EikeiDev/OpenWRT-sing-box-extended](https://github.com/EikeiDev/OpenWRT-sing-box-extended) — установщик под OpenWrt.
- [daniellavrushin/b4](https://github.com/daniellavrushin/b4) — Go-демон со встроенным UI, единый JSON-конфиг, каталог geodat-источников в UI, выбор категорий в Sets → Targets. Архитектурный образец для A.3, каталог источников — для A.5, но своей модели конфига (не sing-box) и без `.srs`.
- MetaCubeXD — образец набора экранов дашборда Clash API.
