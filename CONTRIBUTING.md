# Как вносить изменения

Правила разработки — [`AGENTS.md`](./AGENTS.md), требования — [`docs/PRD.md`](./docs/PRD.md), гайды Go-части — [`apps/metaboxd/docs/guides/`](./apps/metaboxd/docs/guides/README.md), гайды фронтенда — [`apps/web/docs/`](./apps/web/docs/README.md). Здесь только процесс: ветка, проверки, коммит, PR.

## Цикл работы

1. Ветка от `main`.
2. Изменения по правилам затронутой части репозитория.
3. Локальные проверки — таблица ниже. Красные проверки не коммитим.
4. Атомарные коммиты в формате Conventional Commits.
5. PR в `main`, CI зелёный.

## Формат коммита

```text
<тип>(<скоуп>): <что сделано>

<тело: зачем и что важно знать, по-русски>

<футеры>
```

Заголовок — на английском, в повелительном наклонении, без точки, до 72 символов. Тело — на русском.

**Типы:**

| Тип        | Когда                                     |
| ---------- | ----------------------------------------- |
| `feat`     | новое поведение, видимое пользователю     |
| `fix`      | исправление дефекта                       |
| `refactor` | поведение то же, меняется устройство кода |
| `perf`     | оптимизация без смены поведения           |
| `test`     | только тесты и фикстуры                   |
| `docs`     | только документация                       |
| `build`    | сборка, зависимости, тулчейн              |
| `ci`       | пайплайны и их конфиги                    |
| `chore`    | всё остальное, что не попало в типы выше  |

**Скоупы:**

| Скоуп    | Что затрагивает                                           |
| -------- | --------------------------------------------------------- |
| `daemon` | `apps/metaboxd/`                                          |
| `schema` | `tools/schemagen`, `apps/web/src/shared/api/generated.ts` |
| `fe`     | `apps/web/` кроме генерируемой схемы                      |
| `docs`   | `docs/`, гайды проектов, `AGENTS.md`, `README.md`         |
| `ci`     | `.github/`                                                |
| `infra`  | `.devcontainer/`, `Makefile`                              |
| `deps`   | обновление зависимостей и версий тулчейна                 |
| `ai`     | `.claude/`, инструкции и скиллы агентов                   |

Скоуп опускается, только если изменение реально задевает весь репозиторий. Этот же список задан в `scope-enum` — `commitlint.config.mjs`.

**Ломающее изменение** — `!` после скоупа и футер `BREAKING CHANGE:` с описанием миграции. Для API демона и формата конфига это обязательно.

Примеры:

```text
feat(daemon): add config rollback on failed healthcheck
fix(fe): keep draft when websocket reconnects
build(deps): bump oxlint to 1.80.0
refactor(schema)!: rename generated Outbound fields
```

Плохо: `update code`, `fix bug`, `wip`, `правки после ревью`, `chore: разное`.

## Атомарность

Один коммит — одна тема. Признак нарушения: в теле приходится перечислять несвязанные пункты. Перенос файлов, переименование и содержательная правка — разные коммиты, иначе diff не читается.

## Что не коммитим

- `apps/web/src/shared/api/generated.ts` руками — правится генератор, файл пересобирается `make schema`.
- `*.local.*` (`AGENTS.local.md`, `.claude/settings.local.json`) — они в `.gitignore`.
- `.omc/**` — рабочие заметки агентов; ссылаться на них в коммитах, коде и документации нельзя.
- Секреты, ключи, дампы конфигов с реальных устройств.
- `dist/`, `apps/web/dist/`, `node_modules/`.

## Проверки перед коммитом

| Что                  | Команда                             |
| -------------------- | ----------------------------------- |
| Go: тесты демона     | `cd apps/metaboxd && go test ./...` |
| Go: тесты генератора | `make test-schemagen`               |
| Go: линт             | `make lint`                         |
| Линт: корень         | `pnpm lint`                         |
| Линт: фронт          | `pnpm --filter web lint`            |
| Формат (весь репо)   | `pnpm format:check`                 |
| Типы и сборка фронта | `pnpm --filter web build`           |
| Всё вместе           | `make test`                         |

Команды запускаются из корня, кроме тестов демона: модуля в корне нет, `go test ./...` работает только из каталога модуля. Генератор тестируется через `make test-schemagen` — без build-тегов форка он не собирается. Фронт — пакет воркспейса, поэтому `pnpm --filter web <скрипт>`. Формат общий на репозиторий: конфиг `.oxfmtrc.json` в корне, для `apps/web/**` в нём лежит override. Линтер каскадный — `apps/web/.oxlintrc.json` расширяет корневой.

Результат проверок приводится как есть; красный не коммитим.

## Хуки

Проверки выше запускает lefthook, ставится один раз: `make hooks` (в devcontainer это делает `postCreateCommand`).

| Хук          | Что делает                                                                                        |
| ------------ | ------------------------------------------------------------------------------------------------- |
| `pre-commit` | gofmt и go vet, линт и формат фронта, запрет ручной правки `apps/web/src/shared/api/generated.ts` |
| `commit-msg` | commitlint по конвенции из этого документа, правила — `commitlint.config.mjs`                     |
| `pre-push`   | `make test` и сборка фронта с проверкой типов                                                     |

Джобы отбираются по staged-файлам: правка только в Go не запускает проверки фронта и наоборот. Конфиг — `lefthook.yml` в корне. lefthook и commitlint — devDependencies корневого пакета, ставить отдельно нечего: `pnpm install` подтягивает их и через скрипт `prepare` сам прописывает хуки.

`git commit --no-verify` — только когда изменение объективно не может пройти проверку, и это объяснено в PR. CI гоняет то же самое плюс commitlint по всем коммитам PR.

## Документация в коммите

PRD — первоисточник требований и решений. Документы правятся тем же коммитом, что и изменение, а не потом:

| Что меняется в коммите                               | Что правится                                                     |
| ---------------------------------------------------- | ---------------------------------------------------------------- |
| выполнен критерий приёмки                            | отмечается чекбокс AC в разделе 5                                |
| часть проекта перешла из каркаса в рабочее состояние | строка в [`docs/Status.md`](./docs/Status.md)                    |
| принято новое техническое решение                    | ADR в `docs/adr/`; PRD правится, только если меняется требование |
| переехал файл или каталог, упомянутый в документах   | пути в документах                                                |

Чекбокс AC отмечается только тогда, когда критерий подтверждён прогоном — тестом, CI или замером. «Написано, вероятно работает» — не основание.

Новые технические решения оформляются ADR в [`docs/adr/`](./docs/adr/README.md). Приложение A PRD закрыто для новых записей: его разделы переезжают в ADR, когда соответствующую часть начинают реализовывать. Транскрипты интервью — в [`docs/Interviews.md`](./docs/Interviews.md), они не редактируются.

## Ветки и PR

- Имя ветки: `<тип>/<кратко-через-дефис>`, например `feat/apply-rollback`.
- PR описывает, что и зачем; ссылка на PRD или ADR, если решение туда попадает.
- CI обязателен: `make lint`, тесты Go обоих модулей, линт и формат фронта, сборка фронта и интеграционный прогон на образе целевого окружения.
- Прямой push в `main` — только для владельца репозитория.

## Специфика частей

**Демон (`apps/metaboxd/`).** Владеет файлами конфига и циклом Apply. Изменения в API или формате хранения — ломающие, требуют футера и правки PRD. Перед правкой кода читается документ из таблицы в [`apps/metaboxd/AGENTS.md`](./apps/metaboxd/AGENTS.md); перед сдачей — [чеклист ревью](./apps/metaboxd/docs/guides/ReviewChecklist.md).

**Схема (`tools/schemagen`).** Генератор — источник, `apps/web/src/shared/api/generated.ts` — артефакт. Коммит должен содержать и правку генератора, и перегенерированный файл, иначе фронт разъедется со схемой.

**Фронт (`apps/web/`).** Перед правкой кода читается документ из таблицы в [`apps/web/AGENTS.md`](./apps/web/AGENTS.md); перед сдачей — [чеклист ревью](./apps/web/docs/guides/ReviewChecklist.md). Часть правил проверяет `pnpm lint`, дублировать их в PR-описании не нужно.
