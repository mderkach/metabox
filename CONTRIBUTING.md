# Как вносить изменения

Правила разработки — [`AGENTS.md`](./AGENTS.md), требования — [`docs/PRD.md`](./docs/PRD.md), гайды фронтенда — [`web/docs/`](./web/docs/README.md). Здесь только процесс: ветка, проверки, коммит, PR.

## Цикл работы

1. Ветка от `main`.
2. Изменения по правилам затронутой части репозитория.
3. Локальные проверки — таблица ниже. Красные проверки не коммитим.
4. Атомарные коммиты в формате Conventional Commits.
5. PR в `main`, CI зелёный.

## Формат коммита

```
<тип>(<скоуп>): <что сделано>

<тело: зачем и что важно знать, по-русски>

<футеры>
```

Заголовок — на английском, в повелительном наклонении, без точки, до 72 символов: так его читают инструменты и так написана текущая история. Тело — на русском, как остальная документация; нужно, когда из заголовка не видно причины или последствий.

**Типы:**

| Тип        | Когда                                     |
| ---------- | ----------------------------------------- |
| `feat`     | новое поведение, видимое пользователю     |
| `fix`      | исправление дефекта                       |
| `refactor` | поведение то же, меняется устройство кода |
| `perf`     | оптимизация без смены поведения           |
| `test`     | только тесты и фикстуры                   |
| `docs`     | только документация                       |
| `build`    | сборка, зависимости, тулчейн              |
| `ci`       | пайплайны и их конфиги                    |
| `chore`    | всё остальное, что не попало в типы выше  |

**Скоупы:**

| Скоуп    | Что затрагивает                                  |
| -------- | ------------------------------------------------ |
| `daemon` | `cmd/metaboxd`, `internal/`                      |
| `schema` | `tools/schemagen`, `web/src/schema.generated.ts` |
| `fe`     | `web/` кроме генерируемой схемы                  |
| `docs`   | `docs/`, `web/docs/`, `AGENTS.md`, `README.md`   |
| `ci`     | `.github/`                                       |
| `infra`  | `.devcontainer/`, `Makefile`                     |
| `deps`   | обновление зависимостей и версий тулчейна        |
| `ai`     | `.claude/`, инструкции и скиллы агентов          |

Скоуп опускается, только если изменение реально задевает весь репозиторий. Этот же список уходит в `scope-enum`, когда подключим линтер коммитов.

**Ломающее изменение** — `!` после скоупа и футер `BREAKING CHANGE:` с описанием миграции. Для API демона и формата конфига это обязательно.

Примеры:

```
feat(daemon): add config rollback on failed healthcheck
fix(fe): keep draft when websocket reconnects
build(deps): bump oxlint to 1.80.0
refactor(schema)!: rename generated Outbound fields
```

Плохо: `update code`, `fix bug`, `wip`, `правки после ревью`, `chore: разное`.

## Атомарность

Один коммит — одна тема. Признак нарушения: в теле приходится перечислять несвязанные пункты. Перенос файлов, переименование и содержательная правка — разные коммиты, иначе diff не читается.

## Что не коммитим

- `web/src/schema.generated.ts` руками — правится генератор, файл пересобирается `make schema`.
- `*.local.*` (`AGENTS.local.md`, `.claude/settings.local.json`) — они в `.gitignore`.
- `.omc/**` — рабочие заметки агентов; ссылаться на них в коммитах, коде и документации нельзя.
- Секреты, ключи, дампы конфигов с реальных устройств.
- `dist/`, `web/dist/`, `node_modules/`.

## Проверки перед коммитом

| Что                  | Команда                   |
| -------------------- | ------------------------- |
| Go: тесты            | `go test ./...`           |
| Go: статика          | `go vet ./...`            |
| Линт: корень         | `pnpm lint`               |
| Линт: фронт          | `pnpm --filter web lint`  |
| Формат (весь репо)   | `pnpm format:check`       |
| Типы и сборка фронта | `pnpm --filter web build` |
| Версии зависимостей  | `pnpm lint:deps`          |
| Всё вместе           | `make test`               |

Команды запускаются из корня: фронт — пакет воркспейса, поэтому `pnpm --filter web <скрипт>`. Формат общий на репозиторий: конфиг `.oxfmtrc.json` в корне, для `web/**` в нём лежит override. Линтер каскадный — `web/.oxlintrc.json` расширяет корневой.

Результат проверок приводится как есть. Красный линт не «поправим потом» — либо чиним, либо не коммитим.

## Хуки

Проверки выше запускает lefthook, ставится один раз: `make hooks` (в devcontainer это делает `postCreateCommand`).

| Хук          | Что делает                                                                                    |
| ------------ | --------------------------------------------------------------------------------------------- |
| `pre-commit` | gofmt и go vet, линт/формат/версии фронта, запрет ручной правки `web/src/schema.generated.ts` |
| `commit-msg` | commitlint по конвенции из этого документа, правила — `commitlint.config.mjs`                 |
| `pre-push`   | `make test` и сборка фронта с проверкой типов                                                 |

Джобы отбираются по staged-файлам: правка только в Go не запускает проверки фронта и наоборот. Конфиг — `lefthook.yml` в корне. lefthook и commitlint — devDependencies корневого пакета, ставить отдельно нечего: `pnpm install` подтягивает их и через скрипт `prepare` сам прописывает хуки.

`git commit --no-verify` — только когда изменение объективно не может пройти проверку, и это объяснено в PR. CI гоняет то же самое плюс commitlint по всем коммитам PR, так что обход всплывёт.

## Ветки и PR

- Имя ветки: `<тип>/<кратко-через-дефис>`, например `feat/apply-rollback`.
- PR описывает, что и зачем; ссылка на PRD или ADR, если решение туда попадает.
- CI обязателен: `go vet`, `go test`, линт, формат, версии зависимостей, сборка фронта и интеграционный прогон на образе целевого окружения.
- Прямой push в `main` — только для владельца репозитория.

## Специфика частей

**Демон (`cmd/metaboxd`, `internal/`).** Владеет файлами конфига и циклом Apply. Изменения в API или формате хранения — ломающие, требуют футера и правки PRD.

**Схема (`tools/schemagen`).** Генератор — источник, `web/src/schema.generated.ts` — артефакт. Коммит должен содержать и правку генератора, и перегенерированный файл, иначе фронт разъедется со схемой.

**Фронт (`web/`).** Перед правкой кода читается документ из таблицы в [`AGENTS.md`](./AGENTS.md); перед сдачей — [чеклист ревью](./web/docs/guides/ReviewChecklist.md). Часть правил проверяет `pnpm lint`, дублировать их в PR-описании не нужно.
