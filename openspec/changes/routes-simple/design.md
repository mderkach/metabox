# Simple Routes

## Context

The panel edits a config document while the daemon owns validation, Apply, confirmation, and rollback. Simple adds a guided view of the current document. Editor and JSON remain the complete paths for imported or unsupported constructs.

## Design brief

**Question:** What should I set up first, where will this traffic go, and what will change if I apply this draft?

- Present Interception, DNS, Outbounds, and Rules in that order. Keep each routine operation at its point of use, including the empty editable configuration.
- Use nearby help for terms, an expandable explanation for rule order, compact contextual forms for edits, and the existing draft bar and version history. Preserve the user's place when a form closes.
- Show the real configuration and distinguish it from runtime observations, predictions, and unavailable data. Limit catalog service details to source and known usage. Offer controls supported by the active core.
- Cover imported and empty configs, unavailable runtime data, invalid input, unsupported and ambiguous operations, and a failed validation or Apply. Use the shared responsive and accessible components in both languages and themes. Preserve keyboard operation, focus, and reduced-motion behavior.

The first delivery uses one dialog from Outbounds and the empty configuration. The dialog stages supported server links and links to manual subscription entry in Editor. The header adds the existing import action beside the view tabs and version history. The configuration path remains available in Editor and JSON. The subscription slice expands the same dialog after an eligible HTTPS address is entered. Keep the address masked and the notice beside it. Show the name, optional group, refresh interval, and request header in that order. Reveal custom controls in place and keep the original trigger and final focus.

## Goals / Non-Goals

- Let users complete common tasks in Simple and use other views when an edit needs advanced fields.
- Reuse the configuration document and runtime boundaries. Keep detection from #392, first-run setup, and full-schema editing in their existing scopes.
- Avoid a separate rule evaluator, parallel draft, or inferred core behavior.

## Decisions

1. **Projection and focused edits.** Use the shared configuration draft from all three views and reuse existing leaf edits, validation, editing controls, and Apply flow. Derive the numbered view from the actual draft rather than assigning its own rule positions. Editing a list view only changes the relevant document items. Separate draft ownership would make view switching and rollback inconsistent. See [ADR-0002](../../../docs/adr/ADR-0002-apply-protocol-and-config-ownership.md), [ADR-0004](../../../docs/adr/ADR-0004-edit-config-text-in-place-on-the-client.md), and [ADR-0053](../../../docs/adr/ADR-0053-write-form-and-json-edits-to-the-draft-as-they-are-typed.md).
2. **Proven data in context.** Reuse the catalog and rule set metadata for the service disclosure. Link supported rule and device identities to the existing inventories. Reordering can prove positions and simple overlaps. A full evaluation of imported rules would diverge from what the core actually does, so unsupported or unknown overlap is explained rather than represented as a prediction. See [ADR-0007](../../../docs/adr/ADR-0007-explain-route-without-own-rule-evaluator.md).
3. **Catalog route and DNS pair.** Prepare one candidate against the current shared draft. Preview the effective route and DNS rule, then show only the actual edits in the diff. The [catalog mapping](#catalog-route-and-dns-mapping) defines when that candidate is safe.
4. **Capability-gated DNS and interception.** Treat resolver inventory, per-path assignments, and fallback ordering as different operations. Validate edits against the existing schema and what the active core can use. Preserve imported representations unless a lossless edit is supported. Device selection uses the managed dataplane contract. Application proxy and advanced inbound settings are distinct and get only verified, supported actions. See [ADR-0047](../../../docs/adr/ADR-0047-set-up-lan-interception-in-the-singbox-init-script.md).
5. **One import flow with explicit review.** Reuse the server parser and subscription validation and check the draft before offering group choices. A recognized type opens its fields in the same form. An eligible HTTPS URL with unknown contents opens the subscription fields with an unverified-link notice. It remains in the form until the user explicitly stages or cancels it. Other ambiguous links and duplicates stay in that context. Allow the regular add action for a matching subscription URL when the provider tag is unique across the configuration and draft. Each subscription retains independent settings, and the User-Agent may match. An optional same-address notice can link to the existing entry without changing the primary action. Reject a conflicting tag in the form and retain the entered values. Reuse the shared cache-tag validation tracked in [#379](https://github.com/mderkach/metabox/issues/379) for collisions with rule sets and endpoints. Credentials must stay out of warnings and previews beyond the protected editable field. The existing Apply flow owns validation and network effects. This avoids hidden changes triggered by pasting a link.
6. **Shared presentation patterns.** Use existing help popovers, disclosures, dialogs or sheets, the draft bar, and the current focus and transition contracts. Use the same pointer and keyboard behavior for sequential fallback and rule ordering. See [ADR-0026](../../../docs/adr/ADR-0026-animate-screen-changes-with-the-router-and-in-page-changes-with-react.md), [ADR-0049](../../../docs/adr/ADR-0049-slide-side-panels-and-float-the-apply-bar-with-css-transitions.md), and [ADR-0078](../../../docs/adr/ADR-0078-gate-panel-design-with-the-impeccable-detector-a-brief-and-an-independent-critique.md).

The supported fork accepts explicit provider lists in selector and URL test groups. Simple can append to one eligible group or create a manual-choice group. A group configured to use all subscriptions includes the new one automatically. Simple accepts refresh intervals from one minute up to the duration format limit, and editable User-Agent values without ASCII control characters.

## Catalog route and DNS mapping

In v11 the user picks a catalog source, service, exit and device scope. A suggestion on the empty screen opens the same form with the service filled in. The example inserts a route before “Everything else” and shows it in the draft. For production the preview must also name the resolver, indicate any reused rule, and give the positions in the actual draft. A failed preview identifies the specific exit, resolver, set or rule that prevents staging.

The form uses the effective service-specific DNS rule when one already provides a verified assignment. Otherwise the user chooses an eligible inventory entry, even when there is only one. The choice applies to this service. A missing eligible resolver blocks staging and the form keeps the selection. Creating resolvers and managing shared assignments belong to the DNS workflow. The preview explains that the paired rules cover all devices whose traffic passes through the core. It recognizes domain-bearing SOCKS or mixed listeners alongside dedicated DNS inbounds covered by the leading inbound-scoped DNS hijack. Transparent or unfamiliar ingress stays unavailable for automatic pairing. Suggested services from the empty screen open the same catalog search.

### Which resolver can serve this exit?

The verified configuration uses sing-box-extended `1.14.3-extended-2.7.3`, a domain rule set with tag `S`, and a typed TCP DNS server with a literal IPv4 upstream address. The route matches traffic for which the core has the destination domain. The DNS rule matches a query for that domain that reaches the core's DNS router. Both use `rule_set: [S]` and terminal `action: "route"`. On the traffic side the destination field is `outbound`. On the DNS side it is `server`, the tag of an entry in `dns.servers`. That entry's dial settings determine how the query leaves the core.

| Selected exit     | Eligible configuration                                                                                                                                                               | What the path establishes                                                                                                                                          |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Direct            | Route to a plain `type: "direct"` outbound. Select a TCP server with `detour` naming that outbound, or a TCP server with no detour when both use the same ordinary dial settings.    | The data and upstream DNS connection both leave directly, even with a proxy as `route.final`. A custom direct outbound needs separate proof of equivalent dialing. |
| Proxy group       | Route to the selected `type: "selector"` tag. The server's `detour` names **that same group**. The tested members are explicitly configured SOCKS5 outbounds with literal addresses. | Data and DNS use the group's selected member. The common policy is the group. Its selection can change between connections.                                        |
| Specific outbound | Route to the chosen SOCKS5 outbound tag. The server's `detour` names **that exact outbound**, including when it also belongs to a group.                                             | Both use the named relay independently of the group's selection. A detour to a different tag requires its own proof.                                               |

Use an unambiguous configured assignment or an explicitly chosen, eligible server. A tag such as `proxy-dns`, inventory order, `dns.final`, `route.final` or `route.default_domain_resolver` does not establish that choice. Other DNS transports, bootstrap through hostnames, custom dial settings, dynamic subscription members, an unknown core or a chain of resolvers fall outside the verified matrix.

### Which entries change?

First resolve the service to its exact catalog source and rule-set definition. Reuse the matching definition and tag. A new definition, if needed, is an actual addition in the same preview and diff under the [catalog contract](../../specs/rule-sets/spec.md). Before adding or reusing the definition, check its tag against other sets, subscriptions, WARP endpoints and MASQUE outbounds in the current draft. The core can store their data under the same cache key. Same display names from different providers do not identify the same set. The tested scope is a domain set for all devices. Address-only or unclassified sets, device-specific exceptions, and ingress where the core cannot identify the destination domain have no verified pair.

Check the route and DNS lists **independently** at their real positions, including existing draft edits. Preserve DNS ingress handling. For simple terminal rules the first applicable action in each list wins. An earlier overlapping route can redirect data while DNS takes the requested path, or an earlier DNS rule can do the reverse. Never move an imported rule to make a candidate win. If an earlier match or modifier, or the effect of inserting ahead of another rule, cannot be resolved from the supported conditions, identify the rule and refuse the pair. Different catalog tags alone do not prove disjointness.

A plain terminal exact-domain rule can stay ahead of a new catalog rule when it already selects the same outbound or resolver tag. It keeps its position and handles any intersection with the service. A match on exact names alone does not establish coverage of the full catalog set or select a resolver for it.

An explicitly configured compatible entry makes the pair eligible for a new preview, subject to the same order checks. A newly requested server appears in the diff if it is part of the user's pending edits. No implicit resolver, reassignment or fallback is created.                                       |

The receiver measurements follow [ADR-0095](../../../docs/adr/ADR-0095-verify-catalog-dns-paths-at-the-receiver.md). The [verification cases](../../../docs/Verification.md#catalog-route-and-dns-mapping) record schema acceptance, core validation, rule matches and observations at the upstream. The stand uses synthetic sets with known contents to test the shared-rule split. For independent downloaded catalog sets the panel has no membership or disjointness evidence under the [rule-set detail contract](../../specs/rule-sets/spec.md). It must keep such a split unavailable.

## DNS assignments for exact-domain routes

For an explicit path assignment, Simple can pair terminal traffic and DNS rules for the same exact domain. The selected outbound determines which traffic rules are in scope. The DNS server tag identifies the resolver, and the resolver's dial settings determine its path. The control must identify the affected domains before editing. Domains on other exits and queries outside the displayed scope keep their existing treatment.

A later plain terminal rule with a resolved set reference leaves earlier exact route matches in scope. Names from later routes may be shadowed by the set. An opaque DNS rule still blocks reassignment if an affected name has yet to reach a proven terminal DNS rule.

A separate receiver check on sing-box-extended `1.14.3-extended-2.7.3` verified direct, selector and named SOCKS assignments for disjoint exact domains. It covered a combined DNS rule and separate imported rules, reassignment on the same path, and an unmatched query with either an explicit or implicit default server. The [frontend checks](../../../docs/Verification.md#resolver-inventory-and-path-assignments-in-simple) cover the corresponding draft edits and refusal cases.

Appending to a nonempty inventory preserves its first entry. In an empty inventory the first configured server would become the default. Simple must explain when an inventory-only addition cannot preserve the default. Adding a second resolver also requires preserving bootstrap for hostname dialers that can implicitly use a sole resolver. Opaque rule order, overlapping matches or mixed conditions require separate evidence. Catalog sets stay in the service-specific workflow: their tags alone cannot establish disjoint membership across exits. A finding about DNS and traffic taking different paths depends on the revision-scoped diagnostic in [#392](https://github.com/mderkach/metabox/issues/392).

## DNS options in the shared draft

On the [pinned core](https://github.com/shtorm-7/sing-box-extended/tree/d9442d14b19ddd02605bf3ee893a171947038e19), each `type: "fallback"` transport has its own ordered `servers` array. The first member is the primary. An omitted, empty or `sequential` strategy uses the remaining members in order. Each attempt receives the remaining deadline divided by the number of members left. A transport error, timeout or response code other than NOERROR or NXDOMAIN advances to the next member. A successful empty response and a nonexistent domain both stop the search. The core resolves member tags when constructing the chain, so only earlier inventory entries are available. The panel displays the tag of each actual chain and keeps its primary fixed. A parallel, unfamiliar or ambiguous chain can be inspected. A configuration without a fallback transport has no backup order to edit.

The address-family field edits the global `dns.strategy`. An absent, empty or `as_is` value uses the default. The two preference strategies allow both families and order lookup results. The two single-family strategies suppress the other family. Rules or individual lookups can supply a more specific strategy. Opening the control or choosing the same effective value preserves the imported representation.

Static entries belong to the selected `type: "hosts"` transport. Its `predefined` map accepts a single IP address or an ordered list, including both families. For a matching A or AAAA question reaching that transport, predefined entries take precedence over its hosts files. The core canonicalizes names, so a case or trailing-dot variant of an existing name cannot be added twice. Simple edits the selected mapping, including renaming its domain. Creating a hosts transport or sending queries to it requires an explicit configuration edit. Editing these options does not expand the [catalog pairing matrix](#which-resolver-can-serve-this-exit).

## Server import comparison

Simple compares the protocol and every resulting server field in the configuration and draft, excluding the tag. The comparison includes the address, port, credentials, TLS and transport, and any protocol-specific settings such as the Shadowsocks method, VMess security settings or Hysteria 2 obfuscation. JSON object key order has no effect. An exact match is a duplicate regardless of the name in the link. A match with extra settings on the configured server needs an explicit choice to add it separately. Differing mapped values do not establish a duplicate. The comparison uses manually configured outbounds and makes no claim about servers inside subscriptions.

Simple can append the server to an existing selector or latency-test group with an editable member list, create a manual-choice group, or leave the server ungrouped. Adding the server and updating its chosen group use one draft write.

## Risks / Trade-offs

- A simple control may hide a more complex imported configuration. Keep unsupported items visible as such and verify that edits to supported fields preserve the rest of the document.
- A draft outbound obtained from a subscription may not yet exist at runtime. Show its staged status and let the existing Apply verification establish the result.
- Pairing a catalog route with DNS could alter traffic outside the new rule if mapped incorrectly. Stage the pair only after proving the mapping, preserve existing unrelated rules, and verify that the diff and Apply cover both parts.
- A manual proxy address can be misread as already reachable. Distinguish configured state and observed evidence and leave unsupported editing unavailable.

## Migration Plan

No data migration. Existing drafts and imported configs remain valid in Editor and JSON. Enable Simple writes only for each verified supported capability and retain the existing draft validation, Apply, and rollback flow.
