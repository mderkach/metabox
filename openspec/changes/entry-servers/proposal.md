## Why

An owner who wants to reach the home network or share a proxy has to build an inbound, a route rule and a firewall rule by hand.

Issue: none yet.

## What Changes

An inbound of a server type can be created today only through the generic schema form. To build:

- AC-83, panel: an "entry server" form per server type: port, users or secrets generated by the panel, the fake-TLS domain where the type has one, the outbound; on save the inbound and a `route.rules` entry by inbound tag are written to the draft together, and removed together.
- AC-83: the port check against the dataplane ports (`redirect_port`, `tproxy_port`, `dns_port`), the panel listen port and other inbounds of the draft.
- AC-84, panel: a client link by type (`tg://proxy?…`, `ss://`, `vless://`, …) and a QR code, for the LAN address or for a WAN address or DDNS name the user enters; a statement when the WAN link cannot work.
- AC-84, daemon: the facts the statement needs: the LAN address, the WAN address and whether it is behind CGNAT.
- AC-85, daemon: the "reachable from the internet" toggle: a named `firewall` rule for the port through UCI, `fw4 reload`, removal when the toggle or the server goes off, restore of the previous rules on a failed write; a platform answer "no fw4".
- AC-85, panel: the toggle, its state, and the text for a platform without fw4 with the offer to bind the server to the LAN address.

## Capabilities

### New Capabilities

- `entry-servers`: AC-83, AC-84 and AC-85.

## Impact

- `apps/web`: a new feature for the entry server form and the link, `features/Config/ConfigNodeAdd` (entry point from the "Inbound proxy server" group), `entities/Config`, `entities/Dataplane`; a QR code needs either a new dependency or own code.
- `apps/metaboxd`: a new package for the firewall rule (UCI `firewall`, `fw4`), `internal/httpapi`, `internal/contract`, `internal/locale`, `internal/device` or `internal/diag` for the WAN facts; `shared/api/daemon.generated.ts` through `make schema-daemon`.
- `.devcontainer`: a bench check that the port opens and closes on WAN.
- `docs/Verification.md`, `docs/PRD.md` section 8 already names the AC-85 exception; user documentation.

## Already built

Nothing of the three criteria as stated. Pieces the change stands on:

- The inbound types of the fork are grouped, and the server types (`mtproxy`, `shadowsocks`, `vless`, `trojan`, `hysteria2`, `socks`, …) are offered as "Inbound proxy server" when a node is added: `INBOUND_TYPE_GROUP` in `apps/web/src/features/Config/ConfigNodeAdd/model/ConfigNodeAdd.model.ts`; tests "describes every inbound type of the fork", "groups inbound types into router, proxy server and other, in this order" in `ConfigNodeAdd.model.test.ts`. The node is then filled in the generic schema form: no generated users, no route rule, no port check.
- Share links are parsed into outbounds (`apps/web/src/features/Config/ConfigNodeAdd/model/ConfigNodeAdd.link.ts`); nothing builds a link from an inbound.
- A random secret is generated in one place, for the Clash API (`crypto.getRandomValues` in `apps/web/src/features/Config/ConfigNodeForm/model/ConfigNodeForm.overrides.ts`).
- The dataplane ports are in the model (`apps/metaboxd/internal/dataplane/dataplane.go`) and reach the panel through `entities/Dataplane`.
- The UCI write pattern with snapshot, read-back and restore exists for `metabox.dataplane` (`apps/metaboxd/internal/dataplane/write.go`). The daemon writes nothing to UCI `firewall` and never reloads fw4; the dataplane chains are put into the fw4 table by the init script of `metabox-singbox`.

Not found in the code: QR code, WAN address or CGNAT detection, any `firewall` rule.

## Out of scope

- Access to the panel itself from the internet: stays a non-goal (PRD section 8, Non-Goals); the AC-85 port is the only exception.
- Hand-made forms for client node types: issue #266.
- Platforms other than OpenWrt (roadmap item 10); AC-85 only states what the toggle says without fw4.
- DDNS setup and port forwarding on an upstream router: the user enters the name, the panel does not configure it.
- Per-user traffic accounting and limits of a server.

## Open questions

- No issue names this work; open one when it is scheduled.
- The owner has not approved this proposal: it carries a criterion that was not marked as done when the criteria moved out of the product document.
- The spec sits in the `entry-servers` domain; an entry server is an inbound of the config. Which screen holds entry servers, and should the domain be `config` or its own?
- "Any server type in the schema": the server group of the fork holds far more types than the six the requirement names. Does every one get a hand-made form in the first delivery, or a named first set (`mtproxy`, `shadowsocks`, `vless`, …) with the rest on the generic form? This overlaps issue #266.
- The client link exists only for some types; `socks`, `ssh`, `snell` and others have no agreed link format. What does AC-84 show for them?
- Where is the "reachable from the internet" toggle stored? The inbound lives in the sing-box config and goes through Apply; the firewall rule lives in UCI. Does the rule change with Apply of the config (then the "server is turned off" clause is checked at Apply), or at once, outside the confirmation window?
- AC-50 says applying the config does not reload fw4. A toggle that reloads fw4 during Apply contradicts it unless AC-50 is amended.
- How is CGNAT detected: the WAN address in 100.64.0.0/10 or a private range only, or a comparison with the external address seen from outside (a request to a third party)?
- QR code: a new dependency in `apps/web` or own code? The repository rule is no new dependency without need.
- UDP types (`hysteria2`, `tuic`): the firewall rule protocol follows the type; confirm the rule is tcp, udp or both by type.
