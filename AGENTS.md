# Правила проекта metabox

## Что это

GUI-редактор конфигов sing-box для OpenWrt: Go-демон (`cmd/metaboxd`) раздаёт встроенный SPA (`web/`) и владеет файлами конфига. Схема конфига генерируется из форка sing-box рефлексией (`tools/schemagen`).

Требования — [`docs/PRD.md`](./docs/PRD.md). Расхождение кода с PRD трактуется как ошибка кода, пока PRD не изменён явно.

## Источники правил и их приоритет

Каноническими источниками считаются этот файл, `docs/PRD.md` и документы `web/docs/**`. Файлы `CLAUDE.md`, `.claude/*`, `.cursor/*` и прочих AI-продуктов — **только адаптеры**: настройки инструмента, права доступа, точки входа. Отдельных правил разработки в них не заводить и текст канонических источников не дублировать.

При конфликте применять в таком порядке:

1. Явные инструкции текущей задачи и ограничения среды.
2. Код, конфиги и фактические соглашения затронутой части репозитория.
3. `docs/PRD.md`, затем этот файл, затем `web/docs/**`.
4. Личные настройки агента и внешние плагины — только в части, которая не ослабляет правила репозитория.

В `.claude/CLAUDE.md` подключён внешний плагин (oh-my-claudecode) со своими протоколами: делегирование субагентам, память, формат коммитов, набор скиллов. Применять их только тогда, когда они не расходятся с каноническими источниками и когда нужный runtime реально развёрнут в текущей сессии. Протокол плагина не отменяет требования PRD и не является основанием плодить субагентов там, где задача решается напрямую.

## Порядок изучения проекта

1. Этот файл и `docs/PRD.md` в части, относящейся к задаче.
2. Документы, которые требует таблица ниже, если задача попадает под условие.
3. Сверить выводы с исходным кодом, `package.json`, `go.mod`, конфигами сборки, `tsconfig`, правилами линтера и фактической структурой каталогов.

Не делать выводов об архитектуре, командах и правилах проекта только по общим best practices или по знаниям о стеке. Не уверен — открыть файл.

## Когда читать документы фронтенда

Гайды `web/docs/guides/*` объёмные, поэтому читаются по условию, а не все подряд. Условие обязательное: если оно выполнено, документ читается **полностью** до внесения правки.

| Читать полностью перед тем, как                           | Документ                                                                                                       |
| --------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| создавать или менять прикладной код в `web/src`           | [Architecture&Style.md](./web/docs/guides/Architecture&Style.md) — FSD, Public API, нейминг, компоненты, стили |
| создавать или менять стор, селектор, любой код состояния  | [StateManagement.md](./web/docs/guides/StateManagement.md)                                                     |
| писать fetch-функцию, query-ключ, хук запроса или мутацию | [Query.md](./web/docs/guides/Query.md)                                                                         |
| писать форму или Zod-схему                                | [Form&Validation.md](./web/docs/guides/Form&Validation.md)                                                     |
| писать или править тесты                                  | [UnitTesting.md](./web/docs/guides/UnitTesting.md)                                                             |
| сдавать фронтовую правку                                  | [ReviewChecklist.md](./web/docs/guides/ReviewChecklist.md) — пройти по чеклисту                                |

Разделы с пометкой `TODO` в этих документах обязательными правилами не являются.

При расхождении документа с фактическим кодом, конфигом или правилом линтера — сообщить о противоречии и согласовать решение, а не мигрировать код молча.

## Размещение технических знаний

Один факт — один дом. В остальных местах ссылка на источник, а не копия. Слой выбирается по тому, сколько знание стоит в контексте и как часто нужно:

| Слой      | Где живёт                                                       | Цена                             | Что туда идёт                                                           |
| --------- | --------------------------------------------------------------- | -------------------------------- | ----------------------------------------------------------------------- |
| Контракт  | типы, сигнатуры, схемы, тесты; TSDoc/godoc                      | всегда под рукой, вместе с кодом | поведение и ограничения, которые нельзя однозначно вывести из сигнатуры |
| Правило   | этот файл и вложенные `AGENTS.md`                               | всегда в контексте               | постоянно действующее требование к репозиторию или его части            |
| Документ  | `web/docs/**`, `docs/*`                                         | по условию из таблицы            | объёмные тематические правила                                           |
| Решение   | `docs/adr/*`; требования и уже принятые решения — `docs/PRD.md` | по ссылке                        | почему система устроена именно так, какие варианты отвергнуты           |
| Долг      | [`docs/TechDebt.md`](./docs/TechDebt.md)                        | по ссылке                        | известные компромиссы и что с ними делать                               |
| Процедура | `.claude/skills/*`                                              | по триггеру                      | повторяемый сценарий, нужный не всегда                                  |

TSDoc и godoc не пересказывают реализацию построчно — только то, чего не видно из сигнатуры.

Решения, не относящиеся к требованиям — устройство стенда, обход ограничения платформы, выбор инструмента, — оформляются как ADR в `docs/adr/` скиллом `create-adr`. Статус `Accepted` ставит владелец репозитория, агент создаёт черновик `Proposed`. Решения, уже зафиксированные в приложениях A.* PRD, отдельными ADR не дублируются; если решение меняет требование — правится PRD.

Рабочие заметки по ходу задач лежат в `.omc/plans/*`, эти файлы **не в git** — ссылаться на них в коммитах, документации и коде нельзя.

## Принципы изменений

- Следовать архитектуре, нейминг-конвенциям и стилю затронутой части репозитория, а не привносить свои.
- Ограничивать правки требованиями задачи, держать diff минимальным и понятным.
- Не делать unrelated refactor, массовых переименований, лишнего форматирования и обновления зависимостей без явной просьбы.
- Не вводить новые абстракции и зависимости, если задача решается существующими средствами проекта.
- Сохранять изменения пользователя и не откатывать их без разрешения. Если файл изменился на диске — это обычно намеренно; сообщить, а не возвращать своё.
- Прямо говорить о рисках, компромиссах и техническом долге. Не приукрашивать состояние кода.

## Общее

- При работе с библиотеками, фреймворками и их API используй MCP Context7. Сервер объявлен в `.mcp.json`, ключ подставляется из переменной `CONTEXT7_API_KEY` — заведи свой на context7.com и положи его в `.claude/settings.local.json` (файл в `.gitignore`):

  ```json
  { "env": { "CONTEXT7_API_KEY": "твой-ключ" } }
  ```

  В сам `.mcp.json` ключ не вписывать — файл коммитится.

- Линтеры и тесты запускай сам, результат приводи как есть — не пересказывай.
- Новая зависимость — только когда без неё нельзя; аргументируй.
- Версии зависимостей фиксируются точно, без `^` и `~`: диапазон даёт разные деревья у разработчика и в CI. Установку держит `save-exact=true` в `web/.npmrc`, руками написанный диапазон ловит `pnpm -C web lint:deps` (шаг CI). Обновление версии — отдельное осознанное изменение.
- Версия pnpm — в поле `packageManager`, версия Node — в `.nvmrc`; оба файла читают и локальные инструменты (`corepack`, `fnm`, `nvm`), и CI. Второй файл под ту же версию (`.node-version`) не заводим.
- `web/src/schema.generated.ts` руками не правится — правится генератор. Запись в него закрыта в `.claude/settings.json`.
- Репозиторную документацию писать на русском.
- Личные настройки, которыми не делятся через git, класть в `AGENTS.local.md` (форматы ответа, свои триггеры, алиасы). Файл закрыт в `.gitignore` шаблоном `*.local.*`.

## Гигиена контекста

- Правила разработки живут только в `AGENTS.md`. В `.claude/*`, `.cursor/*`, `.vscode/*` — исключительно настройки инструмента: права, MCP, форматирование, точки входа.
- Не копировать правила репозитория в глобальные пользовательские инструкции агента и обратно.
- Не дублировать один и тот же список путей в нескольких конфигах без необходимости: сейчас права заданы в одном месте — `.claude/settings.json`.
- Внешние плагины подключать только когда их возможности реально нужны; их поведение в канонических источниках не описывать.
