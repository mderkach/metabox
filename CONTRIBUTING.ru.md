# Как вносить изменения

Здесь процесс: как прислать изменение, формат коммита, проверки, PR. Сборка и стенд — в [`docs/Development.ru.md`](./docs/Development.ru.md). Правила разработки — в [`AGENTS.md`](./AGENTS.md) и `AGENTS.md` каждого проекта. Требования — в [`docs/PRD.md`](./docs/PRD.md).

## Первый pull request

1. Сделайте форк репозитория и ветку от `main`: `<тип>/<кратко-через-дефис>`, например `fix/rule-reorder`.
2. Поставьте зависимости: `pnpm install`. Эта же команда ставит git-хуки.
3. Посмотрите панель без роутера: `make dev-mock`. Дев-сервер работает на тестовых данных (моках), демон и sing-box не нужны.
4. Внесите правку и прогоните [проверки](#проверки-перед-коммитом).
5. Откройте PR в `main`.

Первый PR из форка ждёт, пока мейнтейнер одобрит запуск CI. Это правило GitHub для новых участников.

## Формат коммита

Коммиты пишутся по [Conventional Commits 1.0.0](https://www.conventionalcommits.org/ru/v1.0.0/). Их проверяет commitlint, правила — в `commitlint.config.mjs`.

Сообщение коммита — одна строка заголовка, без тела и трейлеров. Так выглядит вся история.

```text
<тип>(<скоуп>): <что сделано>
```

- На английском.
- В повелительном наклонении: «add», а не «added» или «adds».
- Без точки в конце.
- До 72 символов.

У ломающего изменения после скоупа стоит `!`: `refactor(schema)!: rename generated Outbound fields`. Для изменений API демона и формата конфига это обязательно.

Примеры:

```text
feat(daemon): add config rollback on failed healthcheck
fix(fe): keep draft when websocket reconnects
build(deps): bump oxlint to 1.80.0
```

Плохо: `update code`, `fix bug`, `wip`, `правки после ревью`, `chore: разное`.

### Типы

| Тип        | Когда                                     |
| ---------- | ----------------------------------------- |
| `feat`     | новое поведение, видимое пользователю     |
| `fix`      | исправление дефекта                       |
| `refactor` | поведение то же, меняется устройство кода |
| `perf`     | оптимизация без смены поведения           |
| `test`     | только тесты и фикстуры                   |
| `docs`     | только документация                       |
| `build`    | сборка, зависимости, тулчейн              |
| `ci`       | пайплайны и их конфиги                    |
| `chore`    | всё остальное, что не попало в типы выше  |
| `revert`   | откат прежнего коммита                    |

### Скоупы

| Скоуп    | Что затрагивает                                                                                             |
| -------- | ----------------------------------------------------------------------------------------------------------- |
| `daemon` | `apps/metaboxd/`                                                                                            |
| `schema` | `tools/schemagen`, `apps/web/src/shared/api/generated.ts`, `apps/metaboxd/internal/mcp/fields.generated.go` |
| `fe`     | `apps/web/` кроме генерируемой схемы                                                                        |
| `docs`   | `docs/` и корневые документы, когда тип не `docs`                                                           |
| `ci`     | `.github/`                                                                                                  |
| `infra`  | `.devcontainer/`, `Makefile`                                                                                |
| `deps`   | обновление зависимостей и версий тулчейна                                                                   |
| `ai`     | `.claude/`, инструкции и скиллы агентов                                                                     |

Тот же список — в `scope-enum` файла `commitlint.config.mjs`.

Скоуп не пишется, если изменение задевает весь репозиторий. Не пишется он и у коммита `docs`, который правит только `docs/` и корневые документы: `docs(docs)` повторял бы тип. Документация проекта — его гайды, `AGENTS.md`, `README.md`, комментарии в коде — идёт со скоупом проекта: `docs(daemon)`, `docs(fe)`.

### Один коммит — одна тема

Если в коммите смешаны несвязанные правки, разделите его. Перенос или переименование файлов и правка их содержимого — разные коммиты, иначе diff не читается. Добавляйте в индекс только то, что относится к теме, и сверяйтесь с `git status` перед коммитом.

## Что не коммитим

- Ручные правки `apps/web/src/shared/api/generated.ts` и `apps/metaboxd/internal/mcp/fields.generated.go`. Правится генератор, файлы пересобираются `make schema`.
- Ручные правки `apps/web/src/shared/api/daemon.generated.ts`. Правится демон, файл пересобирается `make schema-daemon`.
- Секреты, ключи, дампы конфигов с реальных устройств.
- `dist/`, `apps/web/dist/`, `node_modules/`.

## Проверки перед коммитом

| Что                     | Команда                             |
| ----------------------- | ----------------------------------- |
| Go: тесты демона        | `cd apps/metaboxd && go test ./...` |
| Go: тесты генератора    | `make test-schemagen`               |
| Go: линт                | `make lint`                         |
| Линт (весь репо)        | `pnpm lint`                         |
| Формат (весь репо)      | `pnpm format:check`                 |
| Типы и сборка фронта    | `pnpm --filter web build`           |
| Браузерные тесты фронта | `pnpm --filter web test:browser`    |
| Всё вместе              | `make test`                         |

Команды запускаются из корня репозитория. Исключение — тесты демона: Go-модуля в корне нет, поэтому `go test ./...` работает только из `apps/metaboxd`. `pnpm lint` работает только из корня: плагин Tailwind ищет конфиг фронта от текущего каталога.

Красное не коммитим.

## Хуки

`pnpm install` ставит git-хуки (lefthook, конфиг в `lefthook.yml`); `make hooks` ставит их заново.

| Хук          | Что делает                                                                                                            |
| ------------ | --------------------------------------------------------------------------------------------------------------------- |
| `pre-commit` | gofmt, линт и формат файлов из индекса; `go vet`, если есть Go-файлы; генерируемые файлы — только вместе с источником |
| `commit-msg` | commitlint                                                                                                            |
| `pre-push`   | весь репозиторий: `pnpm lint`, `make lint`, `pnpm format:check`, `make test`, сборка фронта с проверкой типов         |

Коммит проверяет только то, что в него попало, и проходит быстро. Push проверяет всё, потому что правка одного файла может сломать типы в другом.

`git commit --no-verify` — только когда изменение не может пройти проверку; причину объясните в PR.

## Документация в коммите

Документы правятся тем же коммитом, что и код:

| Что меняется в коммите                             | Что правится                                                     |
| -------------------------------------------------- | ---------------------------------------------------------------- |
| выполнен критерий приёмки                          | отмечается чекбокс AC в разделе 5 PRD                            |
| принято новое техническое решение                  | ADR в `docs/adr/`; PRD правится, только если меняется требование |
| переехал файл или каталог, упомянутый в документах | пути в документах                                                |

Чекбокс AC (критерия приёмки) отмечается, только когда критерий подтверждён прогоном: тестом, CI или замером.

Технические решения оформляются ADR (записями об архитектурных решениях) в [`docs/adr/`](./docs/adr/README.md). Приложение A PRD закрыто для новых записей.

## PR

В описании — что изменилось и зачем, со ссылками на PRD или ADR, если решение записано там.

CI запускается на каждый PR и должен быть зелёным до мержа. Он проверяет:

- то же, что `pre-push`, плюс браузерные тесты фронта;
- commitlint по всем коммитам PR;
- интеграционный прогон на стенде: Apply, доступность из сетей, перехват трафика LAN.

## Специфика частей

**Демон (`apps/metaboxd/`).** Владеет файлами конфига и циклом Apply. Изменение API или формата хранения — ломающее: пометьте его `!` и поправьте PRD. Перед правкой прочитайте гайд из таблицы в [`apps/metaboxd/AGENTS.md`](./apps/metaboxd/AGENTS.md). Перед сдачей пройдите [чеклист ревью](./apps/metaboxd/docs/guides/ReviewChecklist.md).

**Схема (`tools/schemagen`).** Генератор — источник. `apps/web/src/shared/api/generated.ts` и `apps/metaboxd/internal/mcp/fields.generated.go` собираются из него. Правка генератора коммитится вместе с пересобранными файлами.

**Контракт демона.** `apps/web/src/shared/api/daemon.generated.ts` печатает `apps/metaboxd/cmd/contractgen` по структурам демона. Он коммитится вместе с правкой демона.

**Фронт (`apps/web/`).** Перед правкой прочитайте гайд из таблицы в [`apps/web/AGENTS.md`](./apps/web/AGENTS.md). Перед сдачей пройдите [чеклист ревью](./apps/web/docs/guides/ReviewChecklist.md).

**Стенд (`.devcontainer/`).** Команды и переменные — в [`docs/Development.ru.md`](./docs/Development.ru.md#стенд).
