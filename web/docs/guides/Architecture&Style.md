# Архитектура и стайлгайд фронтенда

Документ фиксирует структуру `web/src` и правила написания кода. Стек и его обоснование — в [PRD, A.10](../../../docs/PRD.md).

## Методологии

1. [Feature-Sliced Design](https://feature-sliced.design/ru/docs/get-started/overview) — структура
2. GRASP, SOLID — распределение ответственности
3. DDD в части языка: имена слайсов совпадают с доменными понятиями конфига sing-box (`Inbound`, `Outbound`, `Route`, `RuleSet`)

## FSD

### Слои

Экранов шесть, поэтому берём урезанный набор слоёв. Пустые слои не заводим авансом — слой появляется, когда в него есть что положить.

| Слой        | Назначение                                                                        | Заводим            |
| ----------- | --------------------------------------------------------------------------------- | ------------------ |
| `app/`      | запуск: роутер, провайдеры, глобальные стили, точка входа                         | сразу              |
| `pages/`    | экраны роутера (Editor, Overview, Proxies, Connections, Apply, Settings)          | сразу              |
| `widgets/`  | самодостаточные куски экрана: дерево конфига, панель дифа, таблица соединений     | по мере надобности |
| `features/` | действия пользователя: `ApplyConfig`, `RuleAdd`, `RuleReorder`, `ConnectionClose` | по мере надобности |
| `entities/` | доменные сущности: `Config`, `Rule`, `Outbound`, `Proxy`, `Connection`            | сразу              |
| `shared/`   | переиспользуемый код без доменной специфики: примитивы UI, http-клиент, хелперы   | сразу              |

`app` и `shared` слайсов не имеют — они состоят из сегментов напрямую.

### Слайсы

Слайс — предметная область. Слайсы **не импортируют другие слайсы того же слоя**: `features/RuleAdd` не может импортировать `features/RuleReorder`.

Для родственных слайсов заводится группирующая папка: `features/Rule/{RuleAdd,RuleReorder,RuleDelete}`. Группа — не слайс, публичного API у неё нет.

Если кросс-импорт всё-таки нужен, используется правило FSD 2.1 — сегмент `@x`:

```
entities/Outbound/@x/rule/index.ts   // что Outbound разрешает импортировать слайсу Rule
```

```ts
// entities/Outbound/@x/rule/index.ts
export { OUTBOUND_TYPE } from "../../model"
export type { OutboundRef } from "../../model"
```

Импортирующая сторона пишет `import { OUTBOUND_TYPE } from "@entities/Outbound/@x/rule"`. Всё, что не вынесено в `@x`, для соседнего слайса закрыто.

### Сегменты

| Сегмент  | Что внутри                                             |
| -------- | ------------------------------------------------------ |
| `ui`     | компоненты, форматтеры для отображения                 |
| `api`    | запросы к демону: fetch-функции, query-опции, типы DTO |
| `model`  | схемы, типы, сторы, константы, бизнес-логика           |
| `lib`    | вспомогательный код слайса: хуки, чистые функции       |
| `config` | конфигурация и фиче-флаги (по надобности)              |

### Public API

`index.ts` слоя/слайса/сегмента — **единственный вход**. Обращение внутрь глубже публичного API запрещено.

**Любой код в `index.ts`, кроме реэкспортов, запрещён.**

```ts
// entities/Rule/index.ts
export * from "./api"
export * from "./lib"
export * from "./model"
export * from "./ui"
```

Баррель работает только вместе с `"sideEffects": ["**/*.css"]` в `web/package.json`: без флага Rollup считает модули side-effectful и тянет весь слайс целиком — на `shared/ui` это лишние 24 kB.

### Исключения из FSD

Два каталога живут вне слоёв — так зафиксировано в PRD, A.10:

- `src/schema.generated.ts` — артефакт `tools/schemagen`, руками не правится, в git-диффе шумит целиком;
- `src/adapters/` — слой адаптеров к сериализации форка; при ломающем изменении API форка правится только он.

Оба потребляются из `entities/*` и `shared/*`.

`src/shared/ui/**` — вендорная зона shadcn/ui: файлы генерирует CLI, правила нейминга к ним **не применяются**, переименовывать нельзя. После переименования `shadcn add` кладёт рядом файл со старым именем и битыми ссылками; на macOS расхождение регистра маскирует файловая система, ломается в Linux-CI.

Наружу зона видна через `src/shared/ui/index.ts`, прикладной код импортирует `@shared/ui`. После каждого `shadcn add` правим руками две вещи: реэкспорт в барреле (CLI его не дописывает) и импорт `@shared/lib/utils` на относительный. Второе ловит `pnpm lint`, первое — нет.

### Дополнительные требования

1. UI-компоненты в `shared` — [dumb components](https://habr.com/ru/companies/epam_systems/articles/519856/): никакого доменного состояния, только `props`.
2. Если в сегменте `ui` несколько компонентов, которые используются вместе, применяется [compound components](https://habr.com/ru/companies/alfa/articles/647013/): `ConfigTree.Root`, `ConfigTree.Node`.
3. Сложное или доменное состояние компонента выносится в хук в `lib`.

## Стайлгайд

### Экспорты

- Все экспорты именованные.
- `export default` — только для `lazy()`.
- Экспорт наружу — из `index.ts`.

### Импорты

Порядок: внешние библиотеки → внутренние модули → стили. Порядок групп и сортировка внутри них — на `oxfmt` (`sortImports` в `web/.oxfmtrc.json`) — руками не выравнивать.

Алиас слоя — это вход снаружи. Внутри своего слоя и слайса ходим относительными путями: так [требует FSD](https://feature-sliced.design/docs/reference/public-api) и так модуль не тянет сам себя через собственный баррель.

Алиас на каждый слой: `@app`, `@pages`, `@widgets`, `@features`, `@entities`, `@shared`, `@adapters`, плюс `@schema` на генерируемый файл схемы. Общего `@/` нет: путь начинается со слоя, направление импорта видно в строке. Объявлены в `tsconfig.json`, `tsconfig.app.json` и `vite.config.ts`.

```ts
import { useQuery } from "@tanstack/react-query" // внешнее
import { Button } from "@shared/ui" // другой слой — алиас
import { RULE_QUERY } from "../model" // свой слайс — относительный путь
```

### Нейминг

`kebab-case` и `snake_case` для сущностей и файлов запрещены. Исключения: вендорная зона `shared/ui/**` и конфиги в корне.

**Файлы сущностей:** `<Имя>.<сущность>.<расширение>`

```
Rule.api.ts
Rule.model.ts
Rule.store.ts
Rule.constants.ts
Rule.schema.ts
```

Файлы сегмента `ui` — просто имя компонента: `RuleRow.tsx`.

**Константы** — `UPPER_CASE` / `SCREAMING_SNAKE_CASE`. Логически связанная группа заключается в объект: имя объекта в `SCREAMING_SNAKE_CASE`, ключи в `PascalCase`.

```ts
const DEFAULT_LISTEN = "127.0.0.1:9090"

const APPLY_STAGE = {
  Check: "check",
  Write: "write",
  Restart: "restart",
  Healthcheck: "healthcheck",
} as const
```

Всё, что повторяется больше двух раз, выносится в константу. Магических чисел и строк в коде нет.

Пользовательские логи — в верхнем регистре и в квадратных скобках: `console.warn("[APPLY] rollback triggered")`.

### Компоненты

```tsx
function RuleRow({
  rule,
  onSelect,
}: {
  rule: RuleModel
  onSelect: (id: string) => void
}) {
  return <div>...</div>
}
```

1. Объявляются как **Function Declaration** — иначе в отладчике `Anonymous`.
2. `React.FC` / `React.VFC` не используются — [деприкейт](https://github.com/facebook/create-react-app/pull/8177) и ломаная типизация `children`.
3. `props` деструктурируются прямо в аргументах, без промежуточного алиаса типа. Правило действует для компонентов поверх shadcn-примитивов; когда тип нужен снаружи — объявляем интерфейс и экспортируем.
4. Мемоизированный компонент объявляется с суффиксом `Proto`, наружу уходит `memo`:

```tsx
function RuleRowProto({ rule }: { rule: RuleModel }) { ... }

export const RuleRow = memo(RuleRowProto)
```

**Мемоизируем не всё подряд.** `memo` оправдан в списках и узлах дерева, на единичной форме он только добавляет сравнение пропсов. Функции в `props` мемоизированного компонента оборачиваются в `useCallback` — иначе `memo` бесполезен.

### Производительность

- Вызовы функций вынесены из тела рендера.
- Компоненты не объявляются внутри других компонентов.
- Отписки — в `useEffect` через возвращаемый cleanup.
- Спред `props` — только когда он осмыслен, не «на всякий случай».

### Поддерживаемость

- `any` запрещён. Не знаем тип — `unknown` плюс сужение.
- `@ts-expect-error` / отключение правил линтера — только с комментарием, объясняющим причину. `@ts-ignore` не используется вовсе.
- `TODO` / `FIXME` — только с пояснением и ссылкой на задачу.
- Нет вложенных тернарников и длинных цепочек `if...else`.
- Приведения типов — только уточняющие; расширяющий каст ловит `typescript/no-unsafe-type-assertion`. Исключение — адаптерный слой, где строковые пути по определению не типобезопасны (PRD, A.10): там каст закрывается `// oxlint-disable-next-line typescript/no-unsafe-type-assertion -- причина`. Голый disable без причины запрещён отдельным правилом.

## Стили

Tailwind v4, вход — `src/app/styles/index.css`: глобальные стили живут в слое `app`. Токены темы объявляются в `@theme inline`.

- Классы пишутся в `className`; сортировку делает `oxfmt` (`sortTailwindcss`).
- Условные классы — через `cn()` из `@shared/lib/utils`, никакой ручной конкатенации строк.
- Варианты компонента — через `cva`, а не через набор булевых пропсов с ветвлением внутри.
- Произвольные значения (`w-[137px]`) — по исключению; сначала ищем токен шкалы.
- Отдельные `.css` файлы не заводим. Единственное место для сырого CSS — `src/app/styles/index.css`: токены, `@custom-variant`, база.
- Жёсткие `width`/`height` не проставляем — компонент занимает выделенное место по сетке.

## Инструменты

| Что                 | Чем                           | Команда                    |
| ------------------- | ----------------------------- | -------------------------- |
| Линт                | oxlint                        | `pnpm --filter web lint`   |
| Формат              | oxfmt                         | `pnpm --filter web format` |
| Типы                | tsc                           | `pnpm --filter web build`  |
| Тесты               | Vitest                        | `pnpm --filter web test`   |
| Версии зависимостей | `tools/checkExactVersions.js` | `pnpm lint:deps`           |

Форматирование не обсуждается и не правится руками — конфиг в `web/.oxfmtrc.json`. В VS Code формат и автофиксы работают на сохранении: `.vscode/settings.json` назначает `oxc.oxc-vscode` форматтером для TS/JS, JSON, CSS и Markdown, иначе встроенные форматтеры разойдутся с `format:check`. Конфиги лежат в `web/`, расширение находит их по близости к файлу.

Линт типозависимый: `strict` в обоих tsconfig и `options.typeAware` в `.oxlintrc.json` (нужен пакет `oxlint-tsgolint`). Через `jsPlugins` подключены ESLint-плагины для TanStack Query, Testing Library, jest-dom, Tailwind и `check-file`, а границы FSD проверяет локальный `fsd/boundaries` — `web/tools/fsdBoundaries.js`: он знает слой и слайс файла, поэтому ловит импорт вверх по слоям, соседний слайс мимо `@x`, обход Public API и относительный путь за пределами слайса. Перечень правил и исключений — в самом конфиге, здесь не дублируется; риски `jsPlugins` — в [`docs/TechDebt.md`](../../../docs/TechDebt.md).

На ревью по [чеклисту](./ReviewChecklist.md) остаётся то, чего линтер не видит: состав `index.ts`, формат логов, оправданность `memo`, `useCallback` и спреда `props`. «Слайс используется одной страницей» не ловит и он — это [`steiger`](https://github.com/feature-sliced/steiger) отдельным шагом CI, когда слайсов станет много.
